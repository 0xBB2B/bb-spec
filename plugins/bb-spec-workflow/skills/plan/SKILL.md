# Plan 实施计划生成

读取本分支 PRD + 项目代码结构，产出**自包含、分文件、函数级**的实施计划。`/prd` 输出"做什么、为什么"，`/plan` 输出"怎么做"。可标 PRD 子文档 `name` 溯源，但**必须内联复述**相关约束，禁"详见 PRD"式弱引用。

## 核心原则（兼反面案例）

1. **不再单独批准**：需求已在 `/prd` 批准，本 skill 不进 plan 模式、不等批准，产出后直接调用 `/exec`；唯一停顿点是需要新增第三方依赖（❌ 再请用户批准一次拆分方案）
2. **一文一单元**：每份 plan 只解决一个独立实施问题（❌ 一份同涉数据库/业务/HTTP 三层）
3. **自包含可执行**：仅凭该文件 + 项目现有代码即可正确编码（❌ "先完成 plan A 才能理解本文档"）
4. **过程式代码只到函数级**：写函数名 + 文件路径 + 职责，**不写参数签名和函数体**（❌ 写参数/返回类型/实现）
5. **声明式产物写成品**：SQL DDL/迁移、API 契约（OpenAPI/proto/路由表）、配置文件等"成品即设计"的内容，**必须内联最终成品**——完整代码块、带注释（如字段 COMMENT、索引说明），exec 阶段原样落盘（❌ 把 `CREATE TABLE` 压成"两张新建表：字段 A、B、C…"的散文转述）
6. **尊重现有代码**：基于真实代码路径和命名风格，非凭空设计
7. **按关注点拆分**：一份 PRD 子文档可对应多个 plan，按实施关注点拆（❌ 一对一固定映射）
8. **单文件 ≤ 200 行**（不含 frontmatter 与声明式成品代码块），超过则拆分
9. **可断点恢复**：进度持久化到 `PROGRESS.md`，跨会话 / `/clear` 后从断点继续（❌ 执行时不读/不更新）
10. **只在执行期间存在**：plan 内联复述了 PRD 约束，执行完由 `/exec` 删除整个主题目录，避免与 PRD 重复；历史靠 git 追溯

## 输出目录与命名

格式：`{DOCS_DIR}/plan/<YYYY-MM-DD>.<主题>/<序号>-<名称>.md`。`<主题>`：取 git 分支名（去 `feature/`、`fix/` 等前缀）；`<序号>`：两位数字（`01-`、`02-`…）表执行顺序；`<名称>`：kebab-case 关注点描述。禁扁平放在 `plan/` 根目录。

**文件体系**：

| 文件 | 职责 | 规模 |
|---|---|---|
| `plan/<主题>/INDEX.md` | 主题内阶段分组 + plan 列表 + 依赖 | < 30 行 |
| `plan/<主题>/PROGRESS.md` | 执行断点唯一事实源，跨会话 / `/clear` 后据此恢复 | — |

## 工作流

### 步骤 0：定位 plan 现场 + 读取配置 + 找到本分支 PRD

**先定位 plan 现场（worktree 感知）**：git-workflow 默认用 worktree 隔离开发——新 PRD 随功能分支落在 `~/.bb-spec/worktrees/` 下的某棵 worktree，主仓库目录始终停在 main。`/clear` 后新会话打开的往往是主仓库目录，直接把 cwd 当 plan 现场会得到空 diff，误判「无需 plan」终止。所以读任何文件前先跑：

```bash
git branch --show-current
git worktree list --porcelain
```

- **已在 linked worktree 或非 main/master 功能分支** → cwd 即 plan 现场，继续
- **在主仓库且 HEAD 为 main/master** → 逐棵检查非 main 分支的 worktree（`${DOCS_DIR}` 按该 worktree 内 `.bb-spec.yaml` 解析，缺省 `.bb-spec`）：本分支有新增的 PRD（判定方法见下文）的即候选：
  - 恰一棵 → 它就是 plan 现场，**后续所有步骤——读 PRD、产出 plan、更新索引、commit——全部定位到该 worktree 内执行**（`cd` 进去或全程用其绝对路径）
  - 多棵 → AskUserQuestion 列出让用户选
  - 无 → 全新任务，按 git-workflow 先确定开分支方式再继续，**禁止把 plan 文档落在 main 工作区**

现场确定后，在**该目录**下 `cat .bb-spec.yaml 2>/dev/null` 取 `base_dir`（缺省 `.bb-spec`）；`${DOCS_DIR}` = `<base_dir>/docs`。**多仓库工作区**（`${DOCS_DIR}` 所在的 git 仓库与代码不是同一个，如工作区根不是 git 仓库、`docs/` 与各服务各自独立）：文档仓库 = `git -C ${DOCS_DIR} rev-parse --show-toplevel`，下文 PRD / plan 相关的 git 命令都在文档仓库里执行、路径相对文档仓库根；代码相关的 git 命令（测试、`git log -L`、commit）在各代码仓库里分别执行。

找本分支新增的 PRD 目录（基线分支是 master 时把 main 换成 master）：`git diff main...HEAD --name-only -- '${DOCS_DIR}/prd/'` 列出有改动的 PRD 目录，再逐个用 `git cat-file -e main:${DOCS_DIR}/prd/<目录>/OVERVIEW.md` 判定——失败的才是本分支新增（成功的是已合并 PRD，不作为本次输入）：

- **非 git / 无基线分支 / 无新增 PRD**：告知"建议先运行 `/prd`"后终止
- **有**：完整读该目录的 OVERVIEW 与全部子文档（约束、验收、验证路径、决策记录）；读项目根 `AGENTS.md` 的项目约束——拆分与函数设计不得违背。PRD 要改已有行为时，按 OVERVIEW `features:` 与各代码仓库里的 `git log --grep "Requirement: <相关目录>"` 找到现有实现，读代码确认现状

### 步骤 1：摸清项目现状

技术栈（`go.mod` / `package.json` / `Cargo.toml`）→ 目录结构（`find` 或 codegraph）→ 可复用基础设施 → 命名风格。新项目跳过已有代码分析，按 AGENTS.md 与已激活的技术栈约束推断结构。

**冲突检测**：PRD 的约束无法在不违背 AGENTS.md 项目约束或现有关键设计（读相关函数的 `git log -L` 与对应 PRD「决策记录」确认）的前提下实现时，停下列出冲突请用户裁决：

```
## 冲突：<一句话描述>
- PRD 要求：<约束原文>
- 冲突对象：<AGENTS.md 条目 / 现有设计（文件:行号 + 当时的设计原因）>
- 方案 A：<改 PRD（本分支 PRD 可改）> — 代价：<…>
- 方案 B：<改项目约束或现有设计> — 代价：<…>
- **建议**：<推荐方向> — <一句话理由>
```

### 步骤 2：拆分策略 + 根源质检

按层 → 按功能 → 按横切关注点拆分。宁可多拆小文件，简单子需求（< 5 函数）可合并。

定稿前自问：① 是否最优实施路径？② 是否触及根源（非绕过既有不合理设计）？③ 有无 PRD 未要求的过度设计？

### 步骤 3：盘点新增依赖 + 进行中的 plan

- **新增第三方依赖**：列出每项「库名 + 用途 + 版本策略」（版本策略写选版规则如「最新稳定版」「最新 LTS」，具体版本号由 exec 落盘前经官方渠道查询）。**有新增 → 用 AskUserQuestion 请用户同意该清单**，同意即授权（version-policy 要求的新增第三方库同意流程在此一次完成），exec 引入依赖不得超出该清单；用户不同意 → 改用标准库 / 已有依赖重新设计，做不到则停下说明。无新增 → 不问，直接继续
- **进行中的 plan**：`${DOCS_DIR}/plan/` 下其他主题目录中 `PROGRESS.md` 含非 `done` 行的是进行中的 plan，检查与本次有无文件冲突，有冲突则停下告知用户。根 `plan/INDEX.md` 和其中登记的主题目录（不论 `PROGRESS.md` 状态）、全部 `done` 的主题目录都是旧版本留下的，不算进行中、不做冲突检查，提示用户可以 `git rm -r` 清掉

### 步骤 4：产出 plan 文档

每份含 frontmatter + 正文六块（见下方模板）。**函数清单**：函数名 + 文件路径 + 职责一句话 + 调用关系 + 外部接口依赖；**不写**参数列表、返回值、实现；命名风格与项目一致。**验证方式**：必须写出 Test Agent 可见的稳定测试契约，包括公开入口、输入、预期输出或副作用、错误场景；不得要求读取函数清单或实现路径才能写测试。**成品定义**：涉及声明式产物（SQL DDL/API 契约/配置）时增设该块，直接给出可落盘的最终内容，exec 阶段原样使用、不得改写。**新增第三方依赖**：把用户同意的清单中归属本 plan 的依赖写入该块（库名 + 用途 + 版本策略），exec 引入新库以此为界；本 plan 无新增则省略该块。

### 步骤 5：写索引与进度文件

- **主题 INDEX.md**：每条 `- [<name>](<文件名>) — <description>`；`## <阶段>` 分组；依赖标 `[依赖: <name>]`
- **PROGRESS.md**：所有步骤初始标 `pending`

### 步骤 6：自检

- [ ] 拆分质检 3 项全过？
- [ ] 每份 plan ≤ 200 行（成品代码块除外），函数清单无参数和实现，验证方式含 Test Agent 可见的稳定测试契约，声明式产物已内联成品而非散文转述，无"详见 PRD"式引用？
- [ ] 新增第三方依赖已经用户同意（无新增则未询问），同意的项逐条落入对应 plan 文档？
- [ ] 索引 / PROGRESS 已同步？

### 步骤 7：本地 commit

先 `git branch --show-current` 确认分支（**在 main 上则跳过自动 commit**，提示按 git-workflow 先建分支）；只提交本次涉及文件（主题目录内的 plan 文档 + 主题 INDEX + PROGRESS）；message 遵循仓库历史风格（先 `git log --oneline -10`），不硬编码类型前缀，带 `Requirement: <本次 PRD 目录名>`（`Requirement:` 写在 commit 说明最后一段，与 `Co-Authored-By:` 等尾注同段、中间不空行，否则 git 认不出）；多仓库时 plan 提交在文档仓库；**仅本地不自动 push**。

### 步骤 8：简报 + 自动执行

```
## Plan 完成简报
- 主题：<YYYY-MM-DD.主题>
- 产出：N 份 plan，分 M 个阶段
- 文件清单：<序号>-<名称>.md — <一句话描述>
- PRD 覆盖：<全部约束与验收已覆盖 / 未覆盖项列表>
- 待解决：<问题列表 / 无>
- 下一步：自动运行 /exec <主题>
```

输出简报后**直接调用 `Skill bb-spec-workflow:exec`**，参数为本次主题 `<YYYY-MM-DD>.<主题>`，不再询问用户。

## 模板

**单文档模板**：

```markdown
---
name: <kebab-case，与文件名一致>
description: <一句话概括，≤ 80 字>
---
# <实施单元标题>
## 目标
<一句话：完成后系统具备什么能力>
## 业务规则（来源：PRD）
<内联复述 PRD 子文档的约束、验收与相关决策理由 3-10 行，标子文档 name 溯源但内容自包含>
## 涉及文件
<路径，每行标"新建"或"修改">
## 成品定义（仅声明式产物时存在）
<SQL DDL / API 契约 / 配置的最终成品：完整代码块 + 注释，exec 原样落盘>
## 新增第三方依赖（仅本 plan 引入新库时存在）
| 库名 | 用途 | 版本策略 |
|---|---|---|
| `<module/pkg>` | 一句话 | 最新稳定版 / 最新 LTS |
## 函数清单
### <文件路径>
| 函数名 | 职责 |
|---|---|
| `FuncA` | 一句话 |
## 协作关系
<函数调用关系 + 外部依赖（DB/MQ/第三方 API）>
## 验证方式
- 测试入口：<公开命令/API/Hook/页面操作/包级可调用入口；不写内部实现路径>
- 测试输入：<参数、请求、文件、环境或前置数据>
- 预期结果：<输出、状态变化、副作用或错误响应>
- [ ] <验证项>
```

**主题 INDEX.md** + **PROGRESS.md**：

```markdown
# <主题名> 实施计划
## 阶段 1：基础设施
- [project-bootstrap](01-project-bootstrap.md) — 脚手架与基础依赖
## 阶段 2：核心业务
- [domain-types](02-domain-types.md) — 领域模型 [依赖: project-bootstrap]
```

```markdown
# 执行进度

|---|---|---|---|
| 01 | project-bootstrap | done | 2026-05-25 |
| 02 | domain-types | in-progress | — |
## 当前
正在执行 `02-domain-types.md`：函数清单 3/5。
## 阻塞
（无）
```
