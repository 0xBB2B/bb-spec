# 界面原型

本规程是调度：主对话把活派给原型子代理，再把子代理的报告转给用户、把用户的答复转回去。出原型和对比的做法都写在子代理的定义里，这里不重复。

下文的"外壳"是所有原型共用的外框，"框"是外壳中间显示正式页面的区域，只有框里的内容要做进产品。"原型子代理"是 `bb-spec-workflow:prototype-designer`。"派工说明"是主对话发给它的任务说明，它只看得到派工说明，看不到这次对话。

## 两种模式都先做

运行 `${CLAUDE_PLUGIN_ROOT}/scripts/bbspec-paths.sh`，`${CACHE_DIR}` 取输出的 `cache_dir`。给了 `--file` 或 `--compare`、且这个文件在 `ui-preview/` 目录下的，`${CACHE_DIR}` 改取这个 `ui-preview/` 的上一级。其余情况下，项目没有 `.bb-spec/` 和 `.bb-spec.yaml` 时，`${CACHE_DIR}` 改用会话临时目录，不创建 `.bb-spec/`。写入 `${CACHE_DIR}` 前确保 `${CACHE_DIR}/.gitignore` 存在：不存在就连目录一起创建，内容写单行 `*`，把整个缓存目录排除出 git。

## 模式

| 调用 | 模式 |
|---|---|
| `/prototype <主题>` | 单独出原型，用户确认后结束 |
| `<主题> --file <路径>` | 被 `/prd`、`/revise` 调用出原型，用户确认后回到调用方 |
| `--compare <路径>` | 拿实际界面和原型对比，返回结果给调用方 |

## 主对话做什么

- 出原型和对比都用 Agent 工具派 `bb-spec-workflow:prototype-designer`。改动再小（只换一个按钮文字、一个颜色值）也派
- 主对话不读项目源码，不读、不写、不改原型文件的内容，不写 DESIGN.md，只派工和传话
- 子代理不能直接问用户，要问的事都写在报告的「待用户确认的问题」里，由主对话转给用户
- 子代理派不出去（Agent 工具报错、找不到这个子代理，比如账号用不了 `fable` 模型）时停下，把报错原文告诉用户，由用户决定怎么办，不自己接手出原型或对比

## 出原型

1. 确定文件位置。调用方给了 `--file` 就用它，否则是 `${CACHE_DIR}/ui-preview/<YYYY-MM-DD>.<主题>.html`（主题 kebab-case）
2. 写派工说明，必须写全 6 项，缺一项就先补齐再派：
   - 模式：`design`，对应子代理的 `mode`
   - 主题：对应 `topic`
   - 原型文件：第 1 步确定的完整路径，对应 `prototype_file`
   - 调用方是谁：`prototype`（单独运行）、`prd`、`revise` 或 `exec`，对应 `caller`
   - 需求结论：这次要设计的界面、调用方已经和用户确认的内容，对应 `requirement`。用户的原话照抄，不改写
   - 路径：DESIGN.md 应在的完整路径（`bbspec-paths.sh` 输出的 `docs_repo` 的根目录，`docs_repo` 为空时取 `root`），对应 `design_md_path`；设计规范草稿的完整路径（原型文件名的 `.html` 换成 `.DESIGN.draft.md`），对应 `design_draft_path`。原型文件旁边已有 `.DESIGN.draft.md` 或 `.DESIGN.md` 时，在这一项里写明已有的是哪个：旁边有哪个临时文件就写哪个的路径

   6 项之外，再附上模板目录 `${CLAUDE_PLUGIN_ROOT}/templates` 的完整路径，对应 `templates_dir`（里面有外壳模板 `${CLAUDE_PLUGIN_ROOT}/templates/ui-preview-shell.html` 和 DESIGN.md 模板 `${CLAUDE_PLUGIN_ROOT}/templates/DESIGN.md`）
3. 原型文件已存在时，派工说明里再写一句"原型文件已存在，接着改"，并把用户的原话照抄进去，对应 `resume_note`
4. 派 `bb-spec-workflow:prototype-designer`，等它交回报告
5. 每轮收到报告，按下面处理：
   - 把子代理的报告原样给用户看，不删、不改写其中「待用户确认的问题」；报告里有「待用户确认的问题」时，问用户，再把用户的答复发给子代理
   - 原型文件第一次生成后（报告的「这一轮改了什么」写了原型文件），用 `open <原型文件路径>` 在浏览器里打开原型；之后每轮提醒用户刷新页面
   - 用户的答复和修改意见用 `SendMessage` 发给同一个原型子代理，可以在原话后面补充说明，但不改写原话
6. 用户明确说"可以"后，用 `SendMessage` 告诉同一个原型子代理"用户已确认"，它会交回确认内容清单
7. 发不到原来的子代理（没有 `SendMessage` 工具、找不到那个子代理、已经换了会话）时，新派一个原型子代理：派工说明照第 2、3 步写全，用户的原话照抄。用户已经说"可以"时，派工说明再写明"用户已确认"，新子代理读完原型文件后交回确认内容清单

## 确认后

收到确认内容清单后：

- 单独运行（`/prototype <主题>`）：告诉用户原型文件路径，到此结束。不写 PRD，不改产品代码
- 被 `/prd`、`/revise` 调用（`<主题> --file <路径>`）：把确认内容清单和原型文件路径交给调用方，回到调用方继续。`/prd` 照清单写约束和验收，`/revise` 把清单当作期望行为

## 对比（--compare）

1. 写派工说明，必须写全 3 项，缺一项就先补齐再派：
   - 模式：`compare`，对应 `mode`
   - 原型文件：`--compare` 给的完整路径，对应 `prototype_file`
   - 截图目录的完整路径：`${CACHE_DIR}/ui-compare/<日期>.<主题>/`，对应 `screenshots_dir`
2. 每次新派一个原型子代理，不复用出原型的那个
3. 需要跑项目、运行命令时，子代理会把完整命令、出处、端口占用情况写进「待用户确认的问题」，主对话照「出原型」第 5 步转给用户、传回答复。答复发不到原来的子代理时，新派一个原型子代理，3 项之外附上用户的答复，对应 `resume_note`
4. 子代理交回「一致」「不一致」「没跑起来」三种结果之一，把结果原样交给调用方，后续怎么处理由调用方决定
