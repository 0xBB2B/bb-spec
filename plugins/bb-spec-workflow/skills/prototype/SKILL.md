# 界面原型

用统一的外壳出 HTML 原型给用户确认，做完后拿实际界面和原型对比。

下文的"外壳"是所有原型共用的外框，"框"是外壳中间显示正式页面的区域。只有框里的内容要做进产品。

## 两种模式都先做

运行 `${CLAUDE_PLUGIN_ROOT}/scripts/bbspec-paths.sh`，`${CACHE_DIR}` 取输出的 `cache_dir`。给了 `--file` 或 `--compare`、且这个文件在 `ui-preview/` 目录下的，`${CACHE_DIR}` 改取这个 `ui-preview/` 的上一级。其余情况下，项目没有 `.bb-spec/` 和 `.bb-spec.yaml` 时，`${CACHE_DIR}` 改用会话临时目录，不创建 `.bb-spec/`。写入 `${CACHE_DIR}` 前确保 `${CACHE_DIR}/.gitignore` 存在：不存在就连目录一起创建，内容写单行 `*`，把整个缓存目录排除出 git。

## 模式

| 调用 | 模式 |
|---|---|
| `/prototype <主题>` | 单独出原型，用户确认后结束 |
| `<主题> --file <路径>` | 被 `/prd`、`/revise` 调用出原型，用户确认后回到调用方 |
| `--compare <路径>` | 拿实际界面和原型对比，返回结果给调用方 |

## 设计规范（DESIGN.md）

DESIGN.md 是项目的设计规范。出原型、写界面代码、审查界面代码都以它为准。它放在 `bbspec-paths.sh` 输出的 `docs_repo` 的根目录，`docs_repo` 为空时放在输出的 `root`：单仓库就是项目根目录，多仓库工作区是文档仓库根目录。新建和修改都要用户明确同意后才写入这个位置；还没确认的草稿只贴在对话里。被 `/prd` 调用时，用户同意的新建或修改先写进和原型文件同名的草稿：原型文件名的 `.html` 换成 `.DESIGN.draft.md`，放在同一个目录（如 `2026-11-04.order-export.DESIGN.draft.md`）；内容是改完后的完整 DESIGN.md（修改时先复制项目里的 DESIGN.md 再改），由 `/prd` 落盘 PRD 时一起写入项目。原型文件旁边的草稿存在时，后面再出原型以它为准，不重新起草，也不重复报已确认过的问题。被 `/revise` 调用或单独运行时，用户同意即写入，不留草稿文件（`/revise` 传的原型文件名以 `revise-` 开头，可以据此区分调用方）。

**写法标准**（起草和检查都按这几条）：

- 必须有 10 节：风格定位、颜色、字体与字号、间距、「圆角、边框、阴影」、布局与断点、组件、动效、无障碍、终端界面；项目用不上的一节写"不适用"和一句原因。结构照 `${CLAUDE_PLUGIN_ROOT}/templates/DESIGN.md`
- 颜色按用途命名（如主色、背景色、次要文字色、错误色），每个颜色写具体色值；项目支持深色模式时明暗两套都写
- 颜色对比度符合 WCAG 2.2 AA：正文文字对背景至少 4.5:1；大号文字（24px 及以上，或 18.66px 及以上加粗）、图标、输入框和按钮的边框对相邻背景至少 3:1。对比度按 WCAG 的相对亮度公式算出来，不凭感觉判断
- 间距和圆角的每个值都是 4 的倍数（0 也算）；表示全圆角（胶囊形按钮、圆形头像）时写 9999px，不算违规
- 字号、行高、间距、圆角、阴影、动效时长都写具体数值和单位（px、ms 等），不写"简洁""大方""适中"这类形容词代替数值
- 「组件」一节至少写按钮、输入框、表格、卡片、弹窗、提示条，每种写写法（HTML 结构和类名）和默认、悬停、按下、禁用、聚焦 5 种状态的样子；项目里用不到的组件写"不适用"
- 「布局与断点」一节写页面框架：顶栏、侧边栏、导航的位置、尺寸和写法（HTML 结构和类名），以及不同断点下怎么变
- 「终端界面」一节写命令行输出用的颜色（按用途命名、写具体值）、符号、表格和进度条格式；不是命令行项目写"不适用"
- 已记在「无障碍」一节「例外」表里的项，检查时不再报

**出原型前先过一遍 DESIGN.md**：

1. 第一步先读 DESIGN.md，读完才开始设计
2. 没有 DESIGN.md、项目已有界面代码：读项目的全局样式、布局组件和组件代码，复制模板起草 DESIGN.md，如实记录现状，包括页面框架和组件的写法；同时列出不达标的地方和修改建议，请用户确认。确认前不出原型；用户这次不想建 DESIGN.md 时，按草稿出这一次原型，不写入项目（草稿只留在对话里），下次出原型时再问；这一次用到的规范外样式和源码补充只记在 `openQuestions` 里，不提议写入 DESIGN.md
3. 没有 DESIGN.md、项目还没有界面代码：按项目类型（如后台管理、面向大众的网站、命令行工具）设计 2～3 套达标的风格，作为 `schemes` 放在同一份原型里对比：按下面第 2～4 步建好原型文件，按第 8、9 步打开给用户看、按意见改；每套风格画一页风格样张：图形界面项目展示配色和 6 种组件，命令行项目展示「终端界面」一节的颜色、符号、表格和进度条（页面设 `terminal: true`）。每套风格的样式写在该方案 `html` 开头的 `<style>` 里，`css` 只写各方案共用的基础样式，至少放一条（如 `body { margin: 0; }`），免得混进默认页面样式。用户选定后写成 DESIGN.md，删掉其余方案和风格样张页，把选中风格的样式移进 `css`（命令行项目移进各终端页的 `terminalCss`），再出要设计的页面。选定前不出要设计的页面；用户选定风格但不想建 DESIGN.md 时同第 2 条
4. 已有 DESIGN.md 但缺项或不达标：出原型前列出每个问题和修改建议，用户确认后先改 DESIGN.md，再出原型
5. 用户不接受某条修改建议：在 DESIGN.md「无障碍」一节的「例外」表记下哪一项、实际值、用户确认的日期，按现状继续
6. 原型里用到 DESIGN.md 没有的颜色、字号、间距、圆角、阴影或组件样式：在 `openQuestions` 里逐个标出，问用户。用户同意 → 写进 DESIGN.md 对应的一节；不同意 → 原型改用 DESIGN.md 里有的

## 取证顺序

照什么画，按下面的顺序找依据，前一步够用就不往下走：

1. **DESIGN.md**：这次涉及的页面框架和每个组件，DESIGN.md 都写了样子和写法 → 只按 DESIGN.md 画，不读源码
2. **源码**：DESIGN.md 缺这次涉及的某部分（页面框架、某个组件，或终端输出的格式）→ 只读这一部分对应的源码（如入口、路由、布局组件、导航、全局样式、组件库、改动所在页面里的相关代码）。读完把缺的样子和写法整理成 DESIGN.md 的补充内容，问用户，同意才写入
3. **问用户要不要跑**：读完源码仍定不下来样子（如组件库运行时才生成的结构、运行时计算的样式、画布绘制的内容）→ 列出哪些部分定不下来，问用户要不要把项目跑起来看。问用户之前先确认有能打开网页的工具，没有就不问，直接按源码画，`fake` 里写明"没有能打开网页的工具"。用户不同意 → 按源码尽量画，`fake` 里写明哪些部分可能不准

**跑服务**（只在用户同意后）：

- 先列出完整的启动命令和它的出处（哪个文件、哪一行），依赖没装时一并说明要装什么；用户再次同意才执行
- 启动前先看要用的端口有没有被占用；被占用时问用户能不能直接用现有的服务，用现有服务时不关它；用户不同意 → 按源码画，`fake` 写明端口被占用
- 跑起来后打开要改的页面，抓下渲染后的 HTML 和最终生效的样式当底稿；放进框里之前去掉其中的 `<script>`、内联事件属性（如 `onclick`）、登录凭据和 token、真实用户数据（换成假数据）；只改这次要改的部分，不改的部分保持原样
- 抓完底稿，立即关掉为出原型启动的服务，并确认端口已不在监听（只确认自己启动的）
- 启动失败、2 分钟内打不开要改的页面、或者页面要登录时，也立即关掉为出原型启动的服务，改按源码画，`fake` 里写清卡在哪一步

**画什么**：

- 框里画出改动所在的整个页面，包括顶栏、侧边栏、导航、页面标题和周围的组件，不只画改动的那一块
- 组件和页面框架照 DESIGN.md 的写法写；DESIGN.md 没写的，照项目源码里的 HTML 结构和类名写
- `note` 写明依据：用到了 DESIGN.md 的哪几节、读了哪些源码文件（写文件路径），用了底稿时写底稿来自哪个地址

**终端界面**：按 DESIGN.md「终端界面」和项目的输出代码还原颜色、符号、表格和进度条；定不下来时同样按上面第 3 步问用户要不要实际运行命令看输出（运行命令不需要能打开网页的工具）；运行前同样先列出完整命令和出处，依赖没装时一并说明，用户再次同意才执行；输出里的真实数据换成假数据。项目配色写进这一页的 `terminalCss`；外壳默认终端配色只在项目没有命令行输出代码时使用。

## 出原型

界面包括两类：

- 图形界面：网页、桌面或手机 App 的页面、组件、样式、布局、交互
- 终端界面：命令行输出的排版、颜色、表格、进度条、交互提示

改动再小（只换一个按钮文字、一个颜色值）也要出原型。

1. 按「设计规范（DESIGN.md）」先过一遍 DESIGN.md，再按「取证顺序」找齐依据。全新项目对比风格方案时才会在这一步创建原型文件，其余情况这一步做完才进入下一步
2. 确定文件位置。调用方给了 `--file` 就用它，否则是 `${CACHE_DIR}/ui-preview/<YYYY-MM-DD>.<主题>.html`（主题 kebab-case）
3. 文件不存在时，把 `${CLAUDE_PLUGIN_ROOT}/templates/ui-preview-shell.html` 复制到这个位置。文件已存在时直接改它，用户确认过的内容留着
4. 只改文件里 `PROTOTYPE-START` 到 `PROTOTYPE-END` 之间的填写区，格式按那里的说明写，外壳一律不改。正式页面只放进框里，框里禁止放说明或切换控件；说明写进 `note`（这个画面的说明）、`fake`（只在原型里成立）、`openQuestions`（还没确认的问题）
5. 写页面样式：按 DESIGN.md 写 `css`（用了底稿时就用底稿里抓到的样式），照实还原；写了 `css` 后默认页面样式完全不生效
6. 图形界面：按「取证顺序」画出改动所在的整个页面，画出正常、空数据、加载中、出错这几种状态，有交互的地方做成可点击的，框里的跳转用 `data-go`。终端界面：页面设 `terminal: true`，项目配色写进 `terminalCss`，多步交互每一步写成一个状态，并设 `stateLabel: '步骤'`
7. 同一次设计有多个方案时，都放进同一份原型的 `schemes`，不拆成多个文件；用户选定方案后，把没选中的方案删掉，再请用户确认
8. 用 `open <文件路径>` 在浏览器里打开给用户看
9. 用户提了意见就先改原型，再请用户看，直到用户明确说"可以"

确认后：

- 单独运行：告诉用户文件路径，到此结束。不写 PRD，不改产品代码；DESIGN.md 只按「设计规范（DESIGN.md）」经用户同意后写入
- 被调用：回到调用方继续

## 对比（--compare）

需要跑项目时，同样先列出完整命令和出处（哪个文件、哪一行），用户同意才跑；启动前先看端口有没有被占用，被占用时告诉用户占用它的服务是从哪个目录起的，问能不能用；对比完立即关掉为对比启动的服务并确认端口已不在监听（用户现有的服务不关）；用户不同意时返回「没跑起来」并写明原因。跑起来后，和原型框里的内容逐项对比：布局、文案、每种状态、每个交互操作后的结果。外壳的左栏、框上方提示、底部说明不参与对比；「只在原型里成立」写明的假数据和假操作，与实际界面不同不算不一致。

网页或 App 打开对应页面截图；终端界面运行命令看输出（同样先经用户同意）；截图放 `${CACHE_DIR}/ui-compare/`。

只返回结果，后续怎么处理由调用方决定：

- 一致
- 不一致：逐条写原型里是什么、实际是什么，附截图路径
- 没跑起来：写清卡在哪（缺服务、缺账号等）
