# 产出修订（Revise）：诊断 → 定向修正 → 回归验证

对 PRD→plan→exec 流水线产出与预期的偏差做**根因归类 → 定向修正 → 回归验证**，覆盖修 bug、产出优化、需求变更三类场景。所有 review 发现问题需修正时，统一走此流程。

> 仅处理"对既有产出的修正"。与对错无关的**纯新增需求**走 `/prd`，不进本流程。用户要的行为变了（再小也算，例如把超时从 120 秒改成 600 秒、把按钮文字从'提交'改成'保存'），而相关 PRD 已合并或没有 PRD 时，同样走 `/prd` 新开一份，让这次的取舍写进新 PRD 的决策记录。

## 核心原则（兼硬约束）

1. **先读代码再诊断**：现状以代码为准；诊断前必须读出问题相关的实现与测试（或调查子代理交回的结论），给出 `文件:行号`，禁止凭 PRD 或函数名推断现状
2. **先诊断再修正**：禁止跳过归因直接改代码；诊断结果必须向用户通报（不阻断——通报后直接进入步骤 3），诊断阶段仅三种情况停下：期望行为本身有分歧、需附「冲突分析简报」时等用户裁决；修复会改变界面时等用户确认 HTML 预览；某个同根因位置有多种合理修法、用户看到的结果不同时，只就这一处提问
3. **三类归因**：每个问题必须归入 prd-defect / impl-defect / requirement-change 之一
4. **TDD 修正**：涉及代码修改时必须先有失败测试（Red）再改实现（Green），测试须能暴露 bug
5. **PRD 改不改看是否合并**：本分支新增的 PRD 可改（判定：`${CLAUDE_PLUGIN_ROOT}/scripts/branch-prds.sh <基线分支>` 输出的 `new=` 行里有它；不在 `new=` 里的都已合并）；已合并的 PRD 冻结不改——需求层的问题（prd-defect / requirement-change）退出转 `/prd`；只有 impl-defect 留在本流程，期望行为以用户确认为准，修订原因写进 commit 正文，`git log -L` 会把它和代码一起找出来
6. **修正闭环**：修正后必须验证——全量测试通过 + 期望行为合规 + 文档同步
7. **决策必须落盘**：修订过程中定下的取舍——步骤 0 带入的讨论结论、冲突分析简报的裁决、3c 的确认问答——写明选了什么、否掉了哪些做法及理由、由谁在哪天定的；改了本分支 PRD 时记进它的「决策记录」；没改 PRD 时（impl-defect）写进 commit 正文的「决策」段，这是它唯一的记录处
8. **最小影响**：只改必须改的层，不借修正之名扩展功能或重构（额外需求走 `/prd`）；同根因位置（步骤 2「同根因搜索」表里处理为「一起修」的）属于必须改的范围，和用户报的那一处同一轮修完，改它们不用另外请用户批准
9. **plan 只在执行期间存在**：`/exec` 完成后会删除整个 plan 主题目录，`${DOCS_DIR}/plan/` 下 `PROGRESS.md` 含非 `done` 行、且未登记在根 `plan/INDEX.md`（旧版本留下的索引）里的才是进行中的 plan，允许原地修正以保证断点续接；找不到对应 plan 说明已完成，修复由本流程直接驱动、不新建 plan
10. **三 Agent 串行强制派发**：涉及代码修改时必须按 Test → Impl → Review 顺序派 `bb-spec-workflow:test-engineer` / `bb-spec-workflow:impl-engineer` / `bb-spec-workflow:prd-reviewer` 三个 subagent，**禁止主 agent 自己写测试、写实现、做合规检查**；唯一例外是「轻量修复判断」（见步骤 3）通过且用户同意后允许主 agent 直接 TDD 修复
11. **Agent 隔离同 exec**：Test 不看实现，Impl 不看 PRD，Review 只读不写
12. **输出中文**

## 三类归因

| 类型 | 含义 | 修复起点 |
|---|---|---|
| **prd-defect** | PRD 或 plan 没有正确描述用户要的行为（写错、写漏、互相矛盾） | 本分支 PRD → 改 PRD（含决策记录）→ 级联 plan → TDD；已合并 PRD → 退出转 `/prd` 新开一份 |
| **impl-defect** | 期望行为描述正确，实现不符合 | 补测试(Red) → 改实现(Green) → 验证；修订原因与决策写进 commit 正文 |
| **requirement-change** | 用户现在要的行为与当初的需求不同（再小也算，例如把超时从 120 秒改成 600 秒、把按钮文字从'提交'改成'保存'） | 本分支 PRD → 确认新行为、改 PRD（含决策记录）→ 级联 plan → TDD；已合并 PRD 或没有 PRD → 退出转 `/prd` 新开一份 |

## 工作流

### 步骤 0：收集问题信息

有参数直接用，无参数向用户提问；已讨论过的结论要带入。

走到这一步先读 `references/collect.md`（相对本 skill 目录）。

### 步骤 1：定位修复现场 + 读取配置 + 定位关联资产

定位修复现场（找到进行中的 worktree），再读 AGENTS.md，定位代码、测试、相关 PRD 和 plan。

走到这一步先读 `references/locate.md`（相对本 skill 目录）。

**调查交给子代理**：要弄清"系统现在怎么做"或"问题出在哪"时——

- 不知道答案在哪个文件，或预计要读 3 个以上源码文件 → 派 `bb-spec-workflow:code-investigator`，prompt 给出要回答的问题、已知线索（功能名、相关 PRD 目录、报错文字）、项目根路径、细节文件目录 `${CACHE_DIR}/reports/`；主窗口不自己搜索和翻读
- 已经知道文件和大概位置 → 主窗口自己读那一段（定点读）
- 留在主窗口的读取：PRD、plan、AGENTS.md 等文档；看 `git diff` 验收子代理的改动；定点读
- 调查子代理交回的带 `文件:行号` 的结论算本次实际读过的代码，可以直接用于回答和讨论
- 要写进 PRD 的现状、要据此改代码的根因：先按行号定点读，确认和报告一致才能用；不一致以读到的代码为准，这条结论作废，重新调查这一点

**流程归属判定**（进步骤 2 前必做）：**满足以下任一条件应退出 revise，转 `/prd`**：

- 需要先拆解、协商或定义新协议才能落地（如"做快 auth 流程"、"打通 X 服务可观测性"、跨服务通信契约调整）
- 新增或删除子需求、改目标或非目标，或变更面横跨多个功能且涉及新设计决策
- 跨 ≥ 2 个 repo 且**不止是被动跟随的机械级联**（proto 字段改名后 consumer 跟着改属机械级联，反之属协调式）

判定退出时必须停下，提示用户改走 `/prd`，禁继续 revise 流程。

### 步骤 2：诊断归因

按决策树归因，搜全同根因位置，通报诊断结果。

走到这一步先读 `references/diagnose.md`（相对本 skill 目录）。

**界面预览**：修复会改变用户看到的界面时（改动再小，只换一个按钮文字、一个颜色值也算），进步骤 3 之前先出原型，用户明确说"可以"后再改代码。调用 `Skill bb-spec-workflow:prototype`，参数 `<主题> --file ${CACHE_DIR}/ui-preview/<YYYY-MM-DD>.revise-<主题>.html`（主题 kebab-case），原型画出修好之后的样子。

确认过的原型里框中的内容就是这次的期望行为，外壳不算：要改本分支 PRD 时（3a、3c）写进它的约束和验收，PRD 里不写预览页路径；派 test-engineer、prd-reviewer 时把它作为期望行为传过去。

### 步骤 3：按类型修复

按 Test → Impl → Review 顺序派三个子代理修复。

走到这一步先读 `references/fix-by-type.md`（相对本 skill 目录）。

### 步骤 4：回归验证

**跑脚本**：会自己结束的脚本（测试、构建、类型检查、审查）——

- 预计 2 分钟内能跑完 → 主窗口用前台 Bash 直接跑
- 预计超过 2 分钟，或拿不准 → 派 `bb-spec-workflow:script-runner`，prompt 给出命令、工作目录、要摘取的内容、输出文件目录 `${CACHE_DIR}/reports/`
- 主窗口不执行循环等待脚本结束的命令；子代理等待期间做不依赖这次结果的事，没有可做的就结束回合，报告交回后继续
- 常驻服务（dev server、watch、`tail -f`）由主窗口自己用后台方式启动

1. **全量测试**：运行项目全量测试，确认无回归（按上面「跑脚本」分流）
2. **期望行为合规**：检查修复是否引入新的违规；修复改变了本分支 PRD 描述的任一行为而 PRD 未同步，说明归因漏判，回到 3a 补改 PRD 后才允许 commit
3. **界面对比**：出过界面预览时，调用 `Skill bb-spec-workflow:prototype`，参数 `--compare <预览页路径>`。全部一致 → 删掉预览页和本次截图；有不一致 → 逐条写进完成简报（预览里是什么、实际是什么），保留预览页和截图，回到步骤 3 修；实际界面跑不起来 → 简报里写清卡在哪，保留预览页，请用户自己对比
4. **文档同步**：调用 `Skill bb-spec-workflow:doc-update`，参数 `--tail`，让本分支 PRD 与 README、AGENTS.md 等文档追平代码；已合并的 PRD 不碰
5. **本地 commit**：先 `git branch --show-current` 确认分支（**在 main 上则跳过**并提示按 git-workflow 先建分支），只提交本次涉及文件（PRD / plan / 实现 / 测试 + doc-update 收尾改动 + 本次经用户同意新建或改过的 DESIGN.md；多仓库时各仓库分别提交，每个 commit 都带标记），message 遵循仓库历史风格（先 `git log --oneline -10`）、不硬编码类型前缀；**正文写清修订原因（改前什么行为、改后什么行为、为什么改）**；本次没改 PRD 而有取舍时再写「决策」段（改了 PRD 的取舍记在它的「决策记录」里，commit 正文写一份就重复了）：选了什么、否掉了哪些做法及理由、由谁在哪天定的（按核心原则 7 收集）；末尾单独一行带 `Requirement: <相关 PRD 目录名>`（修已合并功能写原需求目录；找不到相关 PRD 写 `none`）；**仅本地、不自动 push**

收尾时删掉 `${CACHE_DIR}/reports/` 下本次产生的细节文件。

### 步骤 5：完成简报

输出修订完成简报。

走到这一步先读 `references/brief.md`（相对本 skill 目录）。

### 无关发现

和这次问题不是同一个根因的问题，只记不改，收尾合成一张清单。

走到这一步先读 `references/unrelated-findings.md`（相对本 skill 目录）。
