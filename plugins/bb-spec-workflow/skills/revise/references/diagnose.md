> 用在 /revise 步骤 2：诊断归因、同根因搜索、诊断结果与冲突分析模板。

安全、鲁棒性问题（出错时崩溃、泄露、报错看不懂等 PRD 没写到的故障处理）：用户要的"别出错"没变，归 impl-defect，PRD 已合并也留在本流程；本分支 PRD 写了相关行为的，按步骤 4 第 2 条同步改。

找不到相关 PRD（老代码）→ 先判断用户要的行为是不是代码本来就该有的：是（代码出错、安全、鲁棒性问题）→ 期望行为以用户确认为准，跳过下面第 1、2 步，从第 3 步开始；不是（要改设计、加新行为）→ requirement-change，按下方「按归因分流」转 `/prd`。

```
1. 相关 PRD 是否正确描述了用户要的行为？
   ├─ 否 → PRD 当初就写错 / 写漏 / 互相矛盾？
   │   ├─ 是 → prd-defect
   │   └─ 否（用户现在要的变了）→ requirement-change
   └─ 是 →
2. plan 是否正确翻译了 PRD？（plan 已删除则跳过）
   ├─ 否 → prd-defect
   └─ 是 →
3. 实现是否符合 PRD？
   ├─ 否 → impl-defect
   └─ 是 →
4. 测试是否覆盖了出问题的场景？
   ├─ 否（测试遗漏）→ impl-defect
   └─ 是（测试断言有误）→ impl-defect
```

**同根因搜索**（归因完成、去向是留在 `/revise` 时做；去向是转 `/prd` 的跳过）：动手修之前，把同一个根因牵连的其他位置一次搜全。

- **什么算同根因位置**（满足任一条）：① 调用了出问题的那段代码，或读了出问题的那份数据，会受同一个缺陷影响；② 没有调用它，但在别处独立写了同样的错误写法。同一个文件里的另一种缺陷不算
- **搜哪里**：出问题的代码所在的整个仓库（调用处用 codegraph 或 grep 函数名，同样写法用 grep 关键写法）；多仓库工作区里，每个用到这段代码的代码仓库都搜；要搜的范围超过 SKILL.md 步骤 1「调查交给子代理」的门槛时，同样派 `bb-spec-workflow:code-investigator` 去搜
- **逐个读代码判断**：搜到的每个位置都读过代码再下结论（调查子代理交回的位置算读过；处理为「一起修」的，先按行号定点读确认），带 `文件:行号` 和一句理由。处理只有三种：
  - **一起修**：受同一缺陷影响，和用户报的那一处同一轮修完
  - **不用修**：读代码确认不受影响（如调用前已自己做过检查），理由带那段代码的 `文件:行号`
  - **另开需求**：要新增设计、或要改变用户原本想要的行为才能修（位置在另一个仓库、且要两边协调着改的也算）；本轮不改它，其他位置照常修
- **只为取舍停下**：某个位置有不止一种合理修法、且不同修法下用户看到的结果不一样时，在通报诊断结果之后、进步骤 3 之前，用 AskUserQuestion 只问这一处，问完和其他位置同一轮修完。其余情况通报后直接进步骤 3

结果写进诊断结果的「同根因位置」一节，用户报的那一处不进表；没有搜到其他位置时，这一节只写一行 `同根因位置：搜过了，没有其他位置（搜了：<函数名或关键词>）`。

**向用户通报诊断结果**（不阻断——展示后直接进入步骤 3；诊断阶段仅三种情况停下：附「冲突分析简报」时等用户裁决方向；修复会改变界面时等用户确认下方的界面预览；某个同根因位置要用户取舍时，通报之后只就这一处提问）：

```
## 诊断结果
- 归因：<prd-defect / impl-defect / requirement-change>
- 证据：
  - PRD 要求：<原文 + 目录名，标明本分支 / 已合并；找不到写「无，以用户确认为准」>
  - plan 说：<原文 / 已删除>
  - 代码做了：<实际行为 + 文件:行号>
  - 测试验了：<覆盖情况>
- 结论：<一句话说明哪层出了什么问题>
- 影响范围：<受影响的文件/功能列表>
- 去向：<留在 /revise / 转 /prd — 一句话原因>

## 同根因位置（去向是转 /prd 时不写这一节）
根因：<一句话>
搜了：<函数名或关键词>

| # | 位置 | 类别 | 处理 | 理由 |
|---|---|---|---|---|
| 1 | <文件:行号> | 调用处 / 同样写法 | 一起修 / 不用修 / 另开需求 | <一句话> |

共 N 处：一起修 A 处，不用修 B 处，另开需求 C 处。
```

**按归因分流**：归因为 prd-defect 且相关 PRD 已合并，或归因为 requirement-change 且相关 PRD 已合并或没有 PRD → 通报诊断结果后**停下**，提示用户改走 `/prd` 新开一份 PRD（功能名沿用原 PRD 的 `features:`），并附上诊断结果与步骤 0 带入的讨论结论，供 `/prd` 澄清时直接使用；禁继续本流程。其余情况进入步骤 3。

**冲突分析简报**（代码行为与 PRD 存在可争议分歧时附上；明确的实现 bug 无需此简报）：

```
## 冲突分析：<一句话描述>
| | 代码现状 | PRD 要求 |
|---|---|---|
| 行为 | <代码实际做了什么> | <PRD 要求做什么> |
- 保留代码：<理由——如已上线验证、覆盖了 PRD 遗漏的边界>
- 遵循 PRD：<理由——如更贴合业务意图、更安全、当前代码是历史妥协>
- **建议**：<推荐方向> — <一句话理由>
- **代价**：<选该方向的改动范围与风险>
确认修复方向后开始修复？
```

用户裁决为「保留代码」等于 PRD 写错（prd-defect）：PRD 已合并时同样按「按归因分流」停下转 `/prd`。
