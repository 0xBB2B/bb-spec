# PRD：质疑 → 澄清 → 拆解 → 落盘 → 自动实施

一次对话把一个需求从想法推进到落地：对话阶段只读对齐，用户批准一次后落盘 PRD，接着自动跑 `/plan` → `/exec`，`/exec` 收尾时自动跑 `/doc-update`。

## 三样东西各管什么

| 来源 | 回答什么 | 谁改 |
|---|---|---|
| **代码（含测试）** | 系统**现在**做什么。唯一事实来源 | `/exec`、`/revise` |
| **PRD** `${DOCS_DIR}/prd/<YYYY-MM-DD>.<主题>/` | 这个需求**为什么**做、要什么、取舍了什么 | 本分支新增的 PRD 可改；合并到基线分支后冻结，谁都不改 |
| **AGENTS.md**（项目根；多仓库工作区为文档仓库根） | 对整个项目都生效的约束，如"禁止泛型""SQL join 不超过 3 张表"；以及查功能、查问题的规矩 | `/prd`（经用户确认） |

代码和 PRD 用 git 连起来：每个 commit 说明带一行 `Requirement: <PRD 目录名>`（如 `Requirement: 2026-10-08.order-export`，只写目录名、不带路径前缀）。想知道某段代码为什么这样写，`git log -L` 查改过它的 commit，读标记指向的 PRD。

**标记的位置**：`Requirement:` 单独占一行，写在 commit 说明末尾。查标记一律在说明全文里找以 `Requirement:` 开头的行，不用 git 的尾注（trailer）解析——GitHub squash 合并会把 `Co-authored-by` 挪到最后单独成段，`Requirement:` 就不在最后一段了，`%(trailers:key=Requirement)` 读不到。

**仓库布局**（所有 skill 共用这一节的定义）：

- **单仓库**：PRD 与代码在同一个 git 仓库，`${DOCS_DIR}` 就在这个仓库里
- **多仓库工作区**：`${DOCS_DIR}` 所在的 git 仓库（`git -C ${DOCS_DIR} rev-parse --show-toplevel`）与代码不在同一个仓库，常见为工作区根目录不是 git 仓库、`docs/` 与各服务各自是独立仓库。此时：
  - **文档仓库** = `${DOCS_DIR}` 所在仓库；**代码仓库** = 工作区里其他 git 仓库（go.work 的 `use`、pnpm workspace 成员、或根目录下含 `.git` 的子目录）
  - 涉及 PRD 的 git 命令都在文档仓库里执行（`git -C <文档仓库>`），路径用相对文档仓库根的写法，下文记作 `<PRD 根>`（单仓库时就是 `${DOCS_DIR}/prd`）
  - 查代码历史的 git 命令（`git log -L`、`git log --grep "Requirement: …"`）在每个相关代码仓库里分别执行
  - 本次需求涉及的每个仓库（文档仓库 + 改动的代码仓库）都按 git-workflow 开同名功能分支，各自的 commit 都带 `Requirement:` 标记

**本分支 PRD 的判定**（所有 skill 共用这一条）：`git -C <文档仓库> cat-file -e <基线分支>:<PRD 根>/<目录>/OVERVIEW.md` 失败（基线分支 main 或 master 上还没有它）= 本分支新增 = 可改；成功 = 已合并 = 冻结。单仓库时 `<文档仓库>` 就是当前仓库。

**一条约束放哪**：问"删掉相关功能后这条约束还成立吗？"——还成立 → 项目级，进 AGENTS.md；随功能一起消失 → 功能约束，进本次 PRD。已被某个已激活 skill（如 golang-constraints、database-constraints）覆盖的通用约束，两边都不写。

## 核心原则

1. **方案先对齐再落盘**：启动即 `EnterPlanMode`，质疑、澄清、拆解全程只读，`ExitPlanMode` 批准后才写文件（❌ 澄清没结束就先建文件）
2. **质疑前置**：先评判值不值得做，再讨论怎么做；结论允许是"不值得做"，此时不落盘、不往下跑
3. **禁止脑补**：用户没明说的每个细节都是未定项，必须问出来，不用"常见做法"替用户拍板
4. **现状以代码为准**：了解系统现在怎么做，读代码，不读旧 PRD；旧 PRD 只用来了解当时为什么这样设计
5. **约束必须可测**：每条约束能写成"什么输入 → 什么结果"，并在「验收」里有对应项——`/plan` 据此生成测试，测试就是能执行的规则
6. **写清为什么**：每个关键取舍问清"为什么选这个、不选那个"，连同被否决的方向写进「决策记录」
7. **只写行为不写实现**：PRD 写用户能看到的行为与约束，不写架构 / 库 / 表结构 / API 形态
8. **同一内容只写一处**：功能约束只在 PRD，项目级约束只在 AGENTS.md；PRD 子文档之间互不引用，背景 / 目标 / 非目标只在 OVERVIEW 写一次
9. **功能名统一**：OVERVIEW 的 `features:` 必须复用已有功能名，新功能名经用户确认——查功能时按这个字段搜，名字不统一就搜不到
10. **术语单一权威源**：`${DOCS_DIR}/prd/GLOSSARY.md` 登记全项目术语（英文锚点 + 可判定定义 + 多语言别名），只由本 skill 维护；只登记本次实际触及的术语；用户混用的多语言写法经锚点归一理解，产出文档里同一术语只用当前工作语言的一种写法
11. **语言跟随用户**：正文用用户的工作语言，标识符/API 名/错误码保持英文

## 工作流

> 步骤 0~5 在 plan 模式内（只读），步骤 6~10 在 plan 模式外（落盘 → commit → 自动实施）。

### 步骤 0：进入 plan 模式 + 读取配置 + 现状扫描

**立即调用 `EnterPlanMode`**。

```bash
cat .bb-spec.yaml 2>/dev/null
```

有 `base_dir` → 用其值作为 bb-spec 根目录；文件不存在或无该字段 → 缺省 `.bb-spec`。`${DOCS_DIR}` = `<base_dir>/docs`，后续所有路径基于此值。旧版本留下的 `${DOCS_DIR}/spec/`、`${DOCS_DIR}/prd/.archive/`、根 `plan/INDEX.md` 照常保留、不拦截，除下面的旧术语表外都不读。

```bash
cat AGENTS.md 2>/dev/null                                      # 项目级约束与查询规矩
cat ${DOCS_DIR}/prd/GLOSSARY.md 2>/dev/null || cat ${DOCS_DIR}/spec/GLOSSARY.md 2>/dev/null  # 术语权威源；没有时读旧版本留在 spec/ 的术语表
grep -h '^features:' ${DOCS_DIR}/prd/*/OVERVIEW.md 2>/dev/null  # 已有功能名
```

**了解相关功能的现状**：按本次涉及的功能名搜 `features:` 找到相关 PRD 目录，在各代码仓库里用 `git log --grep "Requirement: <目录名>" --name-only` 查出改过的文件，**读这些代码**确认现在的行为（搜不到 PRD 的是接入 bb-spec 之前的老代码，直接在代码里搜）；需要了解当时为什么这样设计时，只读最新那份相关 PRD 的「决策记录」。

**重叠判定**：

- **重复**：代码已经具备这个能力 → 不该开新需求，告诉用户现状（附 `文件:行号`）
- **改已有行为**：继续；把"现在的行为（附 `文件:行号`）→ 要改成什么"列入澄清
- **冲突**：与 AGENTS.md 的项目约束相反 → 显式列出，先与用户裁决方向再继续
- **独立**：直接继续

即便无冲突也向用户简报，证明已检查：

```
## 现状扫描
- 相关功能：<features 命中的功能名与 PRD 目录，或"无">
- 相关代码现状：<文件:行号 + 一句话行为，或"无">
- 相关项目约束：<AGENTS.md 中相关条目，或"无">
- 判定：<重复 / 改已有行为 / 冲突 / 独立> — <一句话说明>
```

### 步骤 1：意图定性

用一句话复述**要解决的问题**（不是功能描述）请用户确认。例：用户说"我要一个导出按钮"，复述为"运营每周要手工整理报表数据，耗时且易错——对吗？"

### 步骤 2：质疑（对用户可见）

- 这解决**谁**的**什么**问题？有真实场景或证据吗？
- 不做会怎样？严重程度如何？
- 有没有更便宜的替代——现有功能、人工流程、买现成的？

判断"不值得做"或"有更便宜替代" → 输出否决理由并结束，**不落盘**。用户坚持 → 把质疑结论记入「决策记录」后继续。

### 步骤 3：澄清与发散

**怎么问**：每轮锁定 1 个维度，问 1-3 个递进问题；回答还不够具体到能写成可验证的验收项 → 继续追问同一维度；够了 → 切下一个维度。

**覆盖什么**：

- 用户故事：覆盖所有受影响的角色，不只主角色；主动补充用户没想到的边界场景、异常路径、与既有功能的交互
- 维度检查表（保持领域无关，数据库/事务/语言专属约束由对应 skill 承担）：角色与场景 / 数据约束（类型·范围·必填·唯一）/ 边界（空·极值·越界）/ 并发与一致性 / 失败处理（错什么·怎么报·可否重试）/ 依赖（上下游·外部服务）
- 设计取舍：每个关键选择的理由与被否决的方向

**能自查的不问**：先查代码与 AGENTS.md 能否自答——能自答的呈现"结论 + 依据（`文件:行号`）"请用户确认或推翻，不开放式提问。

**术语锚定**：触及的每个专有名词先对照 GLOSSARY——已登记 → 沿用；未登记、或缺当前工作语言别名 → 与用户对齐定义/写法（禁自行翻译不经确认），记入术语变更队列。

**怎么呈现选项**：每个问题给 1-3 个候选 + 标记推荐项。

- 选项名写**具体行为**，禁用抽象词（❌ "标准 / 灵活" ✅ "refresh 失败时让用户重新登录"）
- 所有选项用**同一组维度**描述（行为 / 代价 / 适用场景）
- 推荐项前缀 `✅` + 一句**根因式**理由（为什么是它，不是它有什么优点）
- 两选项行为相近时显式写"**差异仅在 X**"

**收敛信号**：每个维度的回答都已具体到能写进验收；用户对某维度说"不重要 / 按默认" → 记录决定、跳过。

### 步骤 4：收敛与拆解

- 钉死**目标**与**非目标**（非目标必须显式列出，防范围蔓延）
- 用户故事标优先级 P0 / P1 / P2（P0 = 缺了它需求不成立）；每条 P0 至少一个主路径用例
- 按子需求切分：一个子需求 = 一条可独立成立的能力线，各一份子文档；每份子文档的约束都可测、都在验收里有对应项
- 提炼每个子需求的端到端验证路径 + 一条跨子需求的整体验证路径（黑盒、有序、可观察）
- 按「一条约束放哪」把约束分为项目级（进 AGENTS.md）与功能级（进 PRD）
- 确定 `features:`：复用已有功能名，新功能名列入待批方案

### 步骤 5：方案质检 → ExitPlanMode

展示方案**之前**逐条自问：

1. **是否解决根源问题**：需求描述的是根本问题，还是在绕过表面症状？是后者就主动提出更根源的方案
2. **有无更简单的表达**：能一条约束讲清的不拆成两条
3. **是否值得写**：已被语言/框架/工具天然保证的不写
4. **是否可证伪**：写不出"什么输入 → 什么结果"的约束（如"要健壮/友好"）重新定义或删除

质检通过后展示待批方案并调用 `ExitPlanMode`：

- PRD：目录名 + `features:` + 子需求清单（每项一句话 + 优先级）
- AGENTS.md 变更：新增 / 修改 / 删除的项目约束；要新建 AGENTS.md、或在项目根 `CLAUDE.md` 加 `@AGENTS.md` 导入行（含新建 CLAUDE.md）时逐项写明；无变更写"无"
- 术语表变更（无则写"无"）
- 说明：批准后自动运行 `/plan` → `/exec`，`/exec` 收尾自动 `/doc-update`；中途只在需要新增第三方依赖或遇到设计判断时停下问你

驳回则在 plan 模式内调整后重新呈现。

### 步骤 6：确认落盘现场

```bash
git branch --show-current
```

在 main/master 上 → 按 git-workflow 用 AskUserQuestion 选开分支方式（默认 worktree），切过去后**后续所有落盘、commit、自动实施都在新现场进行**；已在功能分支或 linked worktree → 直接继续。多仓库工作区：检查的是文档仓库与本次要改动的代码仓库，按 git-workflow 的多 repo 规则给它们开同名功能分支。

### 步骤 7：落盘

**7a. PRD**：写入 `${DOCS_DIR}/prd/<YYYY-MM-DD>.<主题>/`（主题 kebab-case）——`OVERVIEW.md` + 每个子需求一份 `<序号>-<子需求>.md`（`01-`、`02-`…）。

**7b. GLOSSARY.md**：`${DOCS_DIR}/prd/GLOSSARY.md` 不存在而 `${DOCS_DIR}/spec/GLOSSARY.md` 存在时，先把旧表整份复制过来（旧表不动），表头说明里的「仅 /spec 维护」改成「仅 /prd 维护」；再按术语变更队列增行、并别名、改定义，删除不再被使用的术语；所有定义冲突必须已经用户裁决，禁静默覆盖。

**7c. AGENTS.md**：

- 位置：单仓库放项目根；多仓库工作区放文档仓库根（随文档一起提交——工作区根目录不受 git 管）
- 不存在 → 按模板新建，路径写成实际的 `${DOCS_DIR}`
- 已存在 → 「查功能、查问题的规矩」节整节按模板覆盖（这一节由插件维护，旧版本写进去的查法要随插件更新）；「项目约束」节只做本次的增删改；其他内容不动
- 确保会话启动目录（单仓库为项目根，多仓库为工作区根）的 `CLAUDE.md` 含导入行 `@<AGENTS.md 相对它的路径>`（单仓库为 `@AGENTS.md`，多仓库如 `@docs/AGENTS.md`；Claude Code 只读 CLAUDE.md，靠这一行把 AGENTS.md 一起加载）：没有 CLAUDE.md → 新建只含这一行的文件；有但缺这一行 → 加在文件最前面

### 步骤 8：自检

- [ ] 步骤 0~5 全程在 plan 模式内，`ExitPlanMode` 批准后才落盘？
- [ ] 质疑已完成；OVERVIEW 有背景、目标、非目标、子需求清单、整体验证路径、决策记录；frontmatter 含 name + description（≤ 80 字）+ date + 单行写法的 `features: [a, b]`？
- [ ] 每份子文档：每条约束可测且在验收里有对应项；每条 P0 有主路径用例；有验证路径；全文无实现方案；没有引用其他文档？
- [ ] `features:` 复用了已有功能名，新功能名已经用户确认？
- [ ] 项目级约束只在 AGENTS.md、功能约束只在 PRD，没有一条写在两处？AGENTS.md 有查询规矩节？CLAUDE.md 已含指向 AGENTS.md 的导入行？

### 步骤 9：本地 commit

只提交本次涉及的文件（PRD 目录 + GLOSSARY + AGENTS.md + 受 git 管的 CLAUDE.md；多仓库时在文档仓库提交），message 遵循仓库历史风格（先 `git log --oneline -10`），**末尾单独一行带 `Requirement: <本次 PRD 目录名>`**，**仅本地、不 push**。`/plan` 靠 `git diff <基线分支>...HEAD` 发现本次 PRD，不提交就检测不到。

### 步骤 10：简报 + 自动实施

```
## PRD 完成简报
- PRD：prd/<YYYY-MM-DD>.<主题>/（OVERVIEW + N 份子需求）
- 功能：<features 列表>（新功能名：<列表 / 无>）
- 项目约束（AGENTS.md）：新增 X / 修改 Y / 删除 Z（无则写"无"）
- 术语表：新增 X / 新别名 Y / 修改 Z / 删除 K（无则写"无"）
- 下一步：自动运行 /plan
```

输出简报后**直接调用 `Skill bb-spec-workflow:plan`**，不再询问用户。

## 模板

### `OVERVIEW.md`

```markdown
---
name: <kebab-case，与目录主题一致>
description: <一句话，≤ 80 字>
date: <YYYY-MM-DD>
features: [<功能名>, ...]  # 必须单行写法，查询规矩按行 grep
---

# <需求标题>

## 背景与问题
<谁、在什么场景、遇到什么问题、现在怎么应对、痛点在哪。>

## 目标
- <可衡量的目标>

## 非目标
- <明确不做的事>

## 子需求清单
| 序号 | 子需求 | 解决的子问题 | 优先级 |
|---|---|---|---|
| 01 | [<子需求>](01-<子需求>.md) | <一句话> | P0 |

## 依赖与交付顺序
<如 01 → {02, 03 可并行}；只有一个子需求写"单一子需求，无依赖"。>

## 整体验证路径
1. <操作 → 可判定结果>

## 决策记录
- <关键取舍：选了什么、为什么；被否决的方向及理由；质疑环节的结论>
```

### 子需求 `<序号>-<子需求>.md`

```markdown
---
name: <kebab-case，与文件名一致>
description: <一句话，≤ 80 字>
date: <YYYY-MM-DD>
---

# <子需求标题>

## 用户故事
### P0：作为 <角色>，我想要 <能力>，以便 <价值>

**用例（主路径）**
- 场景：<具体人物在具体情境下>
- 操作：<一步步做了什么，含具体输入 / 数据>
- 预期：<可判定的具体结果>

**用例（边界 / 异常，按需）**
```

### `AGENTS.md`

```markdown
# AGENTS.md

## 查功能、查问题的规矩
> 本节由 /prd 按 bb-spec 插件模板整节维护，手改会被覆盖；项目自己的规矩写进「项目约束」。

1. 先读代码再回答：凡是"系统现在怎么做"的结论，必须来自本次实际读过的代码，并给出 `文件:行号`；还没读到代码就说"还没确认"，不许猜。
2. 按功能找代码：`grep -l '^features:.*<功能名>' <DOCS_DIR>/prd/*/OVERVIEW.md` 找到相关需求目录，再在每个代码仓库里用 `git log --grep "Requirement: <目录名>" --name-only` 查出改过的文件。
3. 查为什么：在该文件所在的仓库里执行 `git log -L :<函数名>:<文件> -s --format='%h %s%n%b' | grep -e '^[0-9a-f]\{7,40\} ' -e '^Requirement:'` 列出改过这个函数的 commit 和各自的 `Requirement` 行，最新的在前；按函数名报 "no match"（如缩进的类方法）时，先读文件确认行号，改用 `git log -L <起始行>,<结束行>:<文件>`。读最新那个 commit 的 `Requirement` 指向的 PRD「决策记录」和 commit 说明正文（squash 合并的 commit 可能有多行 `Requirement`，逐个读）；更早的 PRD 只在需要追溯时才读。commit 没有 `Requirement` 标记的是接入 bb-spec 之前的老代码，没有对应 PRD，只读 commit 说明；查不到原因就如实说"查不到"。
4. PRD 和代码不一致时以代码为准，并在回答里指出哪里不一致。
5. 改代码前按第 3 条查清设计原因，改动不能违背；确实要改设计，新需求走 `/prd`、修正走 `/revise`。
6. 每个 commit 说明末尾单独一行带 `Requirement: <PRD 目录名>`；和任何需求都无关的改动写 `Requirement: none`，并在正文写一句原因。多仓库时每个仓库的 commit 都要带。

## 项目约束
- <约束>（原因：<一句话>）
```
