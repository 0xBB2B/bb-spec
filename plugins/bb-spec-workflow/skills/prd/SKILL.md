# PRD：质疑 → 澄清 → 拆解 → 落盘 → 自动实施

一次对话把一个需求从想法推进到落地：对话阶段只读对齐（涉及界面时先出 HTML 预览页请用户确认），落盘 PRD 后弹窗请用户读完确认，通过后自动跑 `/plan` → `/exec`，`/exec` 收尾时自动跑 `/doc-update`。

## 四样东西各管什么

| 来源 | 回答什么 | 谁改 |
|---|---|---|
| **代码（含测试）** | 系统**现在**做什么。唯一事实来源 | `/exec`、`/revise` |
| **PRD** `${DOCS_DIR}/prd/<YYYY-MM-DD>.<主题>/` | 这个需求**为什么**做、要什么、取舍了什么 | 本分支新增的 PRD 可改；合并到基线分支后冻结，谁都不改 |
| **AGENTS.md**（项目根；多仓库工作区为文档仓库根） | 对整个项目都生效的约束，如"禁止泛型""SQL join 不超过 3 张表"；以及查功能、查问题的规矩 | `/prd`（经用户确认） |
| **ARCHITECTURE.md**（项目根；多仓库工作区为文档仓库根） | 项目大纲：有哪些模块、各在哪、怎么协作；只写不常变的内容 | `/doc-update`（全仓模式起草，收尾模式追平代码） |

代码和 PRD 用 git 连起来：每个 commit 说明带一行 `Requirement: <PRD 目录名>`（如 `Requirement: 2026-10-08.order-export`，只写目录名、不带路径前缀）。想知道某段代码为什么这样写，`git log -L` 查改过它的 commit，读标记指向的 PRD。

**标记的位置**：`Requirement:` 单独占一行，写在 commit 说明末尾。查标记一律在说明全文里找以 `Requirement:` 开头的行，不用 git 的尾注（trailer）解析——GitHub squash 合并会把 `Co-authored-by` 挪到最后单独成段，`Requirement:` 就不在最后一段了，`%(trailers:key=Requirement)` 读不到。

**仓库布局与本分支 PRD 的判定**：PRD 在哪个仓库、可改还是冻结，定义在步骤 0 指到的文件里。

**一条约束放哪**：问"删掉相关功能后这条约束还成立吗？"——还成立 → 项目级，进 AGENTS.md；随功能一起消失 → 功能约束，进本次 PRD。已被某个已激活 skill（如 golang-constraints、database-constraints）覆盖的通用约束，两边都不写。

## 核心原则

1. **先对齐再落盘，读过再实施**：质疑、澄清、拆解全程只读代码和文档，PRD、AGENTS.md 等交付文件一个不写（❌ 澄清没结束就先建文件）；需求涉及界面时，只在 `${CACHE_DIR}/ui-preview/` 写 HTML 预览页和它的 DESIGN.md 草稿（预览页旁边的两个设计规范临时文件 `.DESIGN.draft.md`、`.DESIGN.md`）给用户看，这个目录不进 git；落盘后用户在弹窗里确认读过 PRD 并通过，才 commit 和实施
2. **质疑前置**：先评判值不值得做，再讨论怎么做；结论允许是"不值得做"，此时不落盘、不往下跑
3. **禁止脑补**：用户没明说的每个细节都是未定项，必须问出来，不用"常见做法"替用户拍板
4. **现状以代码为准**：了解系统现在怎么做，读代码，不读旧 PRD；旧 PRD 只用来了解当时为什么这样设计
5. **约束必须可测**：每条约束能写成"什么输入 → 什么结果"，并在「验收」里有对应项——`/plan` 据此生成测试，测试就是能执行的规则
6. **写清为什么**：每个关键取舍问清"为什么选这个、不选那个"，连同被否决的方向写进「决策记录」
7. **只写行为不写实现**：PRD 写用户能看到的行为与约束，不写架构 / 库 / 表结构 / API 形态
8. **同一内容只写一处**：功能约束只在 PRD，项目级约束只在 AGENTS.md；PRD 子文档之间互不引用，背景 / 目标 / 非目标只在 OVERVIEW 写一次
9. **功能名统一**：OVERVIEW 的 `features:` 必须复用已有功能名，新功能名经用户确认——查功能时按这个字段搜，名字不统一就搜不到
10. **术语单一权威源**：`${DOCS_DIR}/prd/GLOSSARY.md` 登记全项目术语（英文锚点 + 可判定定义 + 多语言别名），只由本 skill 维护；只登记本次实际触及的术语；用户混用的多语言写法经锚点归一理解，产出文档里同一术语只用当前工作语言的一种写法
11. **语言跟随用户**：正文用用户的工作语言，标识符/API 名/错误码保持英文

## 工作流

> 步骤 0~5 只对话，涉及界面时出 HTML 预览页；步骤 6~8 落盘并自检；步骤 9 请用户读 PRD 并在弹窗里确认；步骤 10 commit 后自动实施。

### 步骤 0：读取配置 + 现状扫描

```bash
${CLAUDE_PLUGIN_ROOT}/scripts/bbspec-paths.sh
```

输出 bb-spec 各目录的绝对路径（从仓库根往上找 `.bb-spec.yaml`，多仓库工作区的配置在工作区根）：`${DOCS_DIR}` 取 `docs_dir`，后续所有路径基于此值；`${CACHE_DIR}` 取 `cache_dir`，放界面预览页这类临时文件；`docs_repo` 是文档仓库，为空说明还没有文档目录。旧版本留下的 `${DOCS_DIR}/spec/`、`${DOCS_DIR}/prd/.archive/`、根 `plan/INDEX.md` 照常保留、不拦截，除下面的旧术语表外都不读。

读完上面的输出后先读 `references/repo-layout.md`（相对本 skill 目录）：它定义了后面要用的 `<PRD 根>`、文档仓库、代码仓库和本分支 PRD 的判定。

```bash
cat AGENTS.md 2>/dev/null                                      # 项目级约束与查询规矩
cat ${DOCS_DIR}/prd/GLOSSARY.md 2>/dev/null || cat ${DOCS_DIR}/spec/GLOSSARY.md 2>/dev/null  # 术语权威源；没有时读旧版本留在 spec/ 的术语表
grep -h '^features:' ${DOCS_DIR}/prd/*/OVERVIEW.md 2>/dev/null  # 已有功能名
```

**了解相关功能的现状**：有 `ARCHITECTURE.md` 时先读它，按模块地图定位相关模块和目录；再按本次涉及的功能名搜 `features:` 找到相关 PRD 目录，在各代码仓库里用 `git log --grep "Requirement: <目录名>" --name-only` 查出改过的文件，按下面「调查交给子代理」的分流读这些代码，确认现在的行为（搜不到 PRD 的是接入 bb-spec 之前的老代码，同样按下面的分流处理）；需要了解当时为什么这样设计时，只读最新那份相关 PRD 的「决策记录」；需求涉及"以前为什么没做 / 为什么不这样做"时，用关键词 `grep -rln '<关键词>' ${DOCS_DIR}/prd/` 找到提到它的 PRD，读命中的「非目标」和「决策记录」。

**调查交给子代理**：要弄清"系统现在怎么做"或"问题出在哪"时——

- 不知道答案在哪个文件，或预计要读 3 个以上源码文件 → 派 `bb-spec-workflow:code-investigator`，prompt 给出要回答的问题、已知线索（功能名、相关 PRD 目录、报错文字）、项目根路径、细节文件目录 `${CACHE_DIR}/reports/`；主窗口不自己搜索和翻读
- 已经知道文件和大概位置 → 主窗口自己读那一段（定点读）
- 留在主窗口的读取：PRD、plan、AGENTS.md 等文档；看 `git diff` 验收子代理的改动；定点读
- 调查子代理交回的带 `文件:行号` 的结论算本次实际读过的代码，可以直接用于回答和讨论
- 要写进 PRD 的现状、要据此改代码的根因：先按行号定点读，确认和报告一致才能用；不一致以读到的代码为准，这条结论作废，重新调查这一点

**重叠判定**：

- **重复**：代码已经具备这个能力 → 不该开新需求，告诉用户现状（附 `文件:行号`）
- **改已有行为**：继续；把"现在的行为（附 `文件:行号`）→ 要改成什么"列入澄清
- **冲突**：与 AGENTS.md 的项目约束相反 → 显式列出，先与用户裁决方向再继续
- **独立**：直接继续

即便无冲突也向用户简报，证明已检查：

```
## 现状扫描
- 相关功能：<features 命中的功能名与 PRD 目录，或"无">
- 相关代码现状：<文件:行号 + 一句话行为，或"无">
- 相关项目约束：<AGENTS.md 中相关条目，或"无">
- 判定：<重复 / 改已有行为 / 冲突 / 独立> — <一句话说明>
```

### 步骤 1：意图定性

用一句话复述**要解决的问题**（不是功能描述）请用户确认。例：用户说"我要一个导出按钮"，复述为"运营每周要手工整理报表数据，耗时且易错——对吗？"

### 步骤 2：质疑（对用户可见）

- 这解决**谁**的**什么**问题？有真实场景或证据吗？
- 不做会怎样？严重程度如何？
- 有没有更便宜的替代——现有功能、人工流程、买现成的？

判断"不值得做"或"有更便宜替代" → 输出否决理由并结束，**不落盘**。用户坚持 → 把质疑结论记入「决策记录」后继续。

### 步骤 3：澄清与发散

**怎么问**：每轮锁定 1 个维度，问 1-3 个递进问题；回答还不够具体到能写成可验证的验收项 → 继续追问同一维度；够了 → 切下一个维度。

**覆盖什么**：

- 用户故事：覆盖所有受影响的角色，不只主角色；主动补充用户没想到的边界场景、异常路径、与既有功能的交互
- 维度检查表（保持领域无关，数据库/事务/语言专属约束由对应 skill 承担）：角色与场景 / 数据约束（类型·范围·必填·唯一）/ 边界（空·极值·越界）/ 并发与一致性 / 失败处理（错什么·怎么报·可否重试）/ 依赖（上下游·外部服务）/ 界面（用户看到的页面或终端输出有变化就算，按下面「界面预览」做）
- 设计取舍：每个关键选择的理由与被否决的方向

**能自查的不问**：先查代码与 AGENTS.md 能否自答——能自答的呈现"结论 + 依据（`文件:行号`）"请用户确认或推翻，不开放式提问。

**术语锚定**：触及的每个专有名词先对照 GLOSSARY——已登记 → 沿用；未登记、或缺当前工作语言别名 → 与用户对齐定义/写法（禁自行翻译不经确认），记入术语变更队列。

**怎么呈现选项**：每个问题给 1-3 个候选 + 标记推荐项。

- 选项名写**具体行为**，禁用抽象词（❌ "标准 / 灵活" ✅ "refresh 失败时让用户重新登录"）
- 所有选项用**同一组维度**描述（行为 / 代价 / 适用场景）
- 推荐项前缀 `✅` + 一句**根因式**理由（为什么是它，不是它有什么优点）
- 两选项行为相近时显式写"**差异仅在 X**"

**界面预览**：需求改变用户看到的界面时，界面这个维度用原型来问，改动再小（只换一个按钮文字、一个颜色值）也要出。调用 `Skill bb-spec-workflow:prototype`，参数 `<主题> --file ${CACHE_DIR}/ui-preview/<YYYY-MM-DD>.<主题>.html`，文件名和步骤 7 的 PRD 目录名一致（`/exec` 收尾时按这个名字找到它，拿实际界面逐项对比）。

预览获用户确认后才进步骤 4。预览页是澄清用的草稿：PRD 里不写它的路径，确认过的内容在步骤 4 写进约束和验收。

**收敛信号**：每个维度的回答都已具体到能写进验收；用户对某维度说"不重要 / 按默认" → 记录决定、跳过。

### 步骤 4：收敛与拆解

- 钉死**目标**与**非目标**（非目标必须显式列出，防范围蔓延）
- 用户故事标优先级 P0 / P1 / P2（P0 = 缺了它需求不成立）；每条 P0 至少一个主路径用例
- 按子需求切分：一个子需求 = 一条可独立成立的能力线，各一份子文档；每份子文档的约束都可测、都在验收里有对应项
- 提炼每个子需求的端到端验证路径 + 一条跨子需求的整体验证路径（黑盒、有序、可观察）
- 按「一条约束放哪」把约束分为项目级（进 AGENTS.md）与功能级（进 PRD）
- 确定 `features:`：复用已有功能名，新功能名列进步骤 9 的简报，随 PRD 一起确认
- 需求涉及界面时，把确认过的预览里框中的内容写成约束和验收，外壳不写成产品功能：每块界面的布局和文案、每种状态（正常、空数据、加载中、出错）下用户看到什么、每个交互操作后发生什么

### 步骤 5：方案质检

展示方案**之前**逐条自问：

1. **是否解决根源问题**：需求描述的是根本问题，还是在绕过表面症状？是后者就主动提出更根源的方案
2. **有无更简单的表达**：能一条约束讲清的不拆成两条
3. **是否值得写**：已被语言/框架/工具天然保证的不写
4. **是否可证伪**：写不出"什么输入 → 什么结果"的约束（如"要健壮/友好"）重新定义或删除

质检通过后直接进步骤 6 落盘。

### 步骤 6：确认落盘现场

```bash
git branch --show-current
```

在 main/master 上 → 按 git-workflow 用 AskUserQuestion 选开分支方式（默认 worktree），切过去后**后续所有落盘、commit、自动实施都在新现场进行**；已在功能分支或 linked worktree → 直接继续。步骤 3 出过界面预览、又切到了新现场时，在新现场重新运行 `bbspec-paths.sh` 取 `cache_dir`，把预览页移到新现场的 `ui-preview/` 下；预览页旁边同名的 `.DESIGN.draft.md`、`.DESIGN.md` 存在的都一起移过去（写入前确保 `${CACHE_DIR}/.gitignore` 存在：不存在就连目录一起创建，内容写单行 `*`），后面的简报写新路径。多仓库工作区：检查的是文档仓库与本次要改动的代码仓库，按 git-workflow 的多 repo 规则给它们开同名功能分支。

### 步骤 7：落盘

把 PRD、术语表、AGENTS.md、DESIGN.md 写到各自的位置。

走到这一步先读 `references/write-files.md` 和 `references/templates.md`（相对本 skill 目录）。

### 步骤 8：自检

落盘后按清单逐项自检。

走到这一步先读 `references/write-files.md`（相对本 skill 目录）。

### 步骤 9：简报 + 弹窗确认

先输出简报，列出每份 PRD 文件的完整路径，方便用户逐份打开阅读：

```
## PRD 完成简报
- PRD：<PRD 根>/<YYYY-MM-DD>.<主题>/
  - <OVERVIEW.md 的完整路径>
  - <每份子需求文档的完整路径，一行一份>
- 功能：<features 列表>（新功能名：<列表 / 无>）
- 项目约束（AGENTS.md）：新增 X / 修改 Y / 删除 Z（无则写"无"）；新建了 AGENTS.md、或在 CLAUDE.md 加了导入行（含新建 CLAUDE.md）时逐项写明
- 术语表：新增 X / 新别名 Y / 修改 Z / 删除 K（无则写"无"）
- DESIGN.md：新建 / 修改了哪几节 / 无
- 界面预览：<用户确认过的预览页完整路径 / 无>
- 下一步：请阅读上面的 PRD 文件，在弹窗里确认
```

接着调用 AskUserQuestion，问题写「我已阅读上面列出的 PRD 文件，PRD 通过并开始执行吗？」，三个选项按下面的顺序：

| 选项 | 选项说明 | 选了之后 |
|---|---|---|
| 已阅读，通过并执行（标推荐） | 提交 PRD，然后自动跑 /plan → /exec → /doc-update；中途只在需要引入新技术或遇到设计判断时停下问你 | 进步骤 10 |
| 需要修改 | 告诉我要改哪里，改完重新给你看、重新弹窗确认 | 问清要改什么，就地改文件；重新出过原型、预览页旁边又有 `.DESIGN.md` 时，按 7d 再写入一次；重跑步骤 8 自检，再回到本步骤重新简报、重新弹窗 |
| 不做了 | 删除本次新建的 PRD 文件，撤销对 AGENTS.md / CLAUDE.md / 术语表 / DESIGN.md 的改动 | 删掉本次新建的文件（PRD 目录、界面预览页、设计规范临时文件（`.DESIGN.draft.md`、`.DESIGN.md`），以及本次新建的 AGENTS.md / CLAUDE.md / GLOSSARY.md），本次新建的 DESIGN.md 删掉，本次改过的已有文件用 `git checkout -- <文件>` 恢复（多仓库时在文档仓库里执行；工作区根不受 git 管的 CLAUDE.md 手动删掉本次加的导入行）；步骤 6 开的分支或 worktree 不删，告诉用户它在哪；不 commit、不往下跑 |

用户在「其他」里直接写意见时，按「需要修改」处理。

### 步骤 10：本地 commit + 自动实施

只提交本次涉及的文件（PRD 目录 + GLOSSARY + AGENTS.md + 受 git 管的 CLAUDE.md + 7d 写入的 DESIGN.md；多仓库时在文档仓库提交），message 遵循仓库历史风格（先 `git log --oneline -10`），**末尾单独一行带 `Requirement: <本次 PRD 目录名>`**，**仅本地、不 push**。`/plan` 靠 `git diff <基线分支>...HEAD` 发现本次 PRD，不提交就检测不到。
