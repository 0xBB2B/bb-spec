# Claude Code 插件

> 一条 PRD 驱动的 Claude Code 流水线，把模糊需求一路带到可交付的代码。

每个阶段可追溯、可断点恢复、经对抗验证。

安装在 GitHub 上查看
claude
❯ /plugin marketplace add 0xBB2B/bb-spec
❯ /plugin install bb-spec-core@0xbb2b
❯ /plugin install bb-spec-workflow@0xbb2b

## 它解决什么问题

每次交接物都是磁盘上的文档，不是会话里的临时记忆。所以它能断点续、能换 AI 接手、能逐级追溯。

01 三 Agent 隔离执行

写实现的 Agent 看不到 PRD，只看测试，没法“照着意图蒙混”。测试、实现、审查由互相看不见的三方分别完成。

02 磁盘文档是唯一交接物

每个阶段交接的是文件，不是会话记忆。跨会话、/clear 之后，甚至换一个模型接手，都能无损续接。

03 代码和 PRD 经 git 双向可查

代码是唯一事实来源，PRD 只写为什么。每个 commit 带需求标记，从功能能找到代码，从函数能查回当时的需求与取舍。

## 流水线怎么走

你读完 PRD 批准需求；要用新技术时先问你，plan 里新增或修改表结构、接口、数据格式、配置时再确认一次，其余自动跑完。/git-push 由你手动触发。

/prd做什么

质疑、澄清、拆解，落盘 PRD，请你读完确认。

↓ 自动衔接
/plan怎么做

把 PRD 变成函数级实施计划。要用新技术时先问你；新增或修改表结构、接口、数据格式、配置时，列成清单请你确认。

↓ 自动衔接
/execRed → Green → Review

三个互相隔离的 Agent 依次写测试、写实现、做审查。进度写进 PROGRESS.md，中断后能接着跑。

↓ 自动衔接
/doc-update文档追平代码

代码是事实，让本次 PRD 和 README 等文档追平实际交付。

↓ 由你手动触发
/git-pushpre-review + 开 PR

分支规范自查，推送，开 PR。

自动衔接由你手动触发

/revise 随时介入：有 bug 或结果和预期不符时，按根因诊断、定向修正、回归验证。

## 安装

在 Claude Code 里执行这三行：

claude
❯ /plugin marketplace add 0xBB2B/bb-spec
❯ /plugin install bb-spec-core@0xbb2b
❯ /plugin install bb-spec-workflow@0xbb2b

这两个子插件给你纪律和工作流。后端、前端的技术栈约束按需再装。

子插件装了得到什么
bb-spec-core 推荐基座TDD / 版本策略 / Git 纪律，加 3 个被动 hook
bb-spec-workflow 核心功能prd → plan → exec → doc-update → revise → git-push，加 8 个 subagent
bb-spec-backendGo / REST API / 数据库 / 认证 / 授权 / 可观测性 / 服务治理 / 配置约束
bb-spec-frontendVue 3 + TS + Vite + Tailwind + bun 技术栈与工程约定
