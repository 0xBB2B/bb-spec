# 清单外的新技术先停下问

## 用户故事
### P0：作为用 bb-spec 做项目的用户，我想让 Claude 在任何时候要用没批准过的新技术都先问我，以便不会事后才发现项目里多了东西

**用例（主路径：执行计划时碰到清单外的库）**
- 场景：`/exec` 执行到登录功能，发现需要一个 JWT 库，它不在 plan 的「新增技术」表里。
- 操作：Claude 停下。用户看完后选"全部同意，继续"。
- 预期：Claude 在正文里列出这 1 项，名称、类别、来源、用途、现有手段为什么不够、替代方案为什么不选、版本策略七项齐全，弹窗问"上面 1 项新技术，你同意引入吗？"。弹窗之前，`go.mod` 等依赖文件没有任何改动，代码里没有引入它。用户同意后，这一项补进 plan 的「新增技术」表，再继续执行。

**用例（用户不同意）**
- 场景：同上。
- 操作：用户在"其他"里写"不要加新库"。
- 预期：Claude 改用标准库或项目已有的依赖实现，继续执行。做不到时停下，说明卡在哪里，不引入这个库。

**用例（普通对话里用户点名）**
- 场景：用户没走任何流程，直接说"加个缓存，用 Redis"，项目里还没有 Redis。
- 预期：Claude 先列出 Redis 这一项，来源标"用户点名"，七项内容齐全，弹窗等批准。用户同意前，不改任何文件。

**用例（修 bug 时）**
- 场景：`/revise` 修一个时间解析的 bug，Claude 想换用一个第三方时间库。
- 预期：和主路径一样先停下、列出、弹窗，同意前不改依赖文件。

## 约束
- 新技术指项目里原来没有的外部东西，包括第三方库、框架、编程语言、运行时、数据库、中间件、构建或测试工具、容器镜像、CI Action、外部服务接口；语言标准库、项目已在用的东西、升级已在用依赖的版本都不算。
- 执行计划、修 bug、不走流程的普通对话里，只要要用的新技术不在用户已经批准的清单里，Claude 先停下，在回复正文里逐项列出，每项写齐七项内容：名称、类别、来源（插件默认栈 / 用户点名 / Claude 提议三选一）、用途、现有手段为什么不够、替代方案为什么不选、版本策略。两条理由要写具体原因，只写"业界常用""更优雅""更流行"不算。然后只弹一次窗问"上面 N 项新技术，你同意引入吗？"，选项同样是"全部同意，继续"和"否决其中几项"。
- 用户点名的新技术同样要列出、写理由、等批准。
- 用户同意之前，不改依赖文件和配置文件（如 `go.mod`、`package.json`、`Dockerfile`、`compose.yaml`、`.github/workflows/*`），不写引入这项技术的代码。
- 执行计划时用户同意后，先把这一项补进 plan 的「新增技术」表，再继续执行。
- 用户不同意时，Claude 改用标准库或项目已有的技术完成；做不到就停下，说明卡在哪里，不引入。
- `/exec` 检查每一步写出的改动：引入了「新增技术」表以外的新技术时，这一步不算完成，先按上面的方式停下问用户。

## 验收
- [ ] 执行计划时碰到清单外的新技术，Claude 停下，在正文写齐七项内容，只弹一次窗，问题和选项文字与约束一致。
- [ ] 弹窗前和用户同意前，依赖文件、配置文件没有改动，代码里没有引入它。
- [ ] 用户同意后，这一项先补进 plan「新增技术」表，再继续执行。
- [ ] 用户不同意时改用现有手段；做不到时停下说明，不引入。
- [ ] 普通对话里用户点名一项新技术，Claude 仍然列出、写理由、弹窗等批准。
- [ ] `/revise` 修 bug 时要用新技术，同样先停下问。
- [ ] `/exec` 发现某一步引入了表外的新技术时，这一步不算完成，先停下问用户。

## 验证路径
1. 在 plan 的「新增技术」表里不放 JWT 库，执行需要 JWT 的登录功能 → Claude 停下列出 JWT 库并弹窗，此时 `git diff go.mod` 为空。
2. 选"全部同意，继续" → plan「新增技术」表多出 JWT 库一行，执行继续。
3. 另起一次，在弹窗"其他"里写"不要加新库" → Claude 改用标准库实现，`go.mod` 没有新增项。
4. 在普通对话里说"加个缓存，用 Redis" → Claude 列出 Redis（来源"用户点名"）并弹窗，同意前工作区没有改动。
