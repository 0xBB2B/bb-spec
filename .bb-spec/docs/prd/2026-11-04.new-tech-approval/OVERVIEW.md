# 引入新技术先批准

## 背景与问题
用户用 bb-spec 做项目时，Claude 会自己拍板用上项目里原来没有的东西，比如 Redis、Docker、一个新框架、一门新语言。用户往往事后看代码才发现，也不知道 Claude 为什么非用它不可。

插件现在只管住了一部分：
- 只管"第三方库"。数据库、中间件、构建工具、容器镜像、CI Action、外部服务、编程语言和框架，都没有要求先问。
- 理由只要求写"标准库、已有依赖为什么不够"和"候选库是什么"。不要求说明替代方案为什么不选。`/plan` 的依赖清单只有"库名、用途、版本策略"三栏。
- 用户在对话里点名的库、插件规则里定好的默认技术栈（如新前端项目用 Vue 3 + Vite + Tailwind + bun），都直接用、不问。用户这次想换一套（比如用 Java 和 MongoDB）时，没有机会提出来。

## 目标
- 项目里原来没有的外部东西，引入前一律逐项列出，用户批准后才能用。
- 每一项都写清用途、现有手段为什么不够、替代方案为什么不选，用户看完就能判断该不该用。
- 一份清单只弹一次窗，用户可以只否决其中几项。

## 非目标
- 不管升级项目已在用的依赖：升级只换版本号，不是引入新东西，版本怎么选沿用现有规则。
- 不管删除依赖。
- 不回头审查项目里已经在用的技术。
- 不改插件默认技术栈本身的内容：默认栈照常作为 Claude 的首选推荐，只是也要列出来等用户批准。

## 子需求清单
| 序号 | 子需求 | 解决的子问题 | 优先级 |
|---|---|---|---|
| 01 | [做计划时的新技术清单](01-plan-tech-list.md) | 做实施计划时，新技术没有逐项列出、没有说清为什么非它不可就被采用 | P0 |
| 02 | [清单外的新技术先停下问](02-unlisted-tech-stop.md) | 执行计划、修 bug、平时写代码时，Claude 自己用上没批准过的新技术 | P0 |

## 依赖与交付顺序
01 → 02。02 沿用 01 定下的清单格式和批准方式。

## 整体验证路径
1. 在一个空项目里让 Claude 走 `/prd` 做一个图书馆系统，PRD 通过后进入 `/plan` → `/plan` 在正文里逐项列出前端框架、后端语言、数据库等新技术，每项写齐七项内容，插件默认栈也在其中，然后只弹一次窗问整份清单。
2. 在弹窗里否决数据库那一项，写"这次想用 MongoDB" → Claude 只把数据库换成 MongoDB，把整份清单再列一遍，再弹一次窗。
3. 选"全部同意，继续" → plan 文档里出现七栏的「新增技术」表，内容和清单一致，然后 `/exec` 开始执行。
4. 执行过程中需要一个清单外的库 → Claude 停下，用同样格式列出这一项并弹窗；同意前依赖文件没有任何改动。
5. 在不走任何流程的普通对话里说"加个缓存，用 Redis" → Claude 仍然先列出 Redis 的七项内容，弹窗等批准。

## 决策记录
- **范围是"项目里原来没有的外部东西"**：用户选的。只管库和框架的话，Redis、Docker、新 CI Action 这类同样会被直接用上，问题还在。标准库和项目已在用的不算，否则每次写代码都要问。
- **官方扩展库和直接引用的间接依赖也算新技术**：执行中的审查发现定义有两处模糊，用户确认都算。`golang.org/x/*` 不在标准库里，要单独写进 `go.mod`，和其他库一样先问；项目以前没直接用过的间接依赖，直接引用就是新增了一项依赖。否决了"官方出的直接用""在 lockfile 里就算已在用"。
- **插件默认栈也要列出、等批准**：用户的原话："用户可能会想要做个图书馆系统，那么必定会涉及到前端后端数据，这个时候可以按照用户的习惯或者 skill 来选择，例如前端用 vue，后端用 go，数据库用 sql。但是这些必须明确告诉用户，并且用户确认之后才能使用，不然万一用户这次想用 java 和 mongodb 就不对了。"否决了"默认栈算已批准"，因为每个项目的需求可能不同。
- **用户点名的也要写理由、等确认**：用户选的。点名之后让 Claude 写出理由，用户能看到 Claude 认不认同这个选择，代价是多停一次。否决了"点名即批准"。
- **理由写三点**：用途、现有手段为什么不够、替代方案为什么不选。用户选的。只写前两点的话，看不出 Claude 有没有比较过别的选择。"业界常用""更优雅""更流行"不算理由，因为这些话对任何选择都成立，帮不了用户判断。
- **一份清单一次弹窗，否决的项写编号**：用户先选了一次批，又试了"一项一问"的原型，最后改回一次批。一项一问能直接点按钮，但 Claude 的提问工具一次最多问 4 个问题，清单超过 4 项就要连着弹好几次窗。
- **否决后只替换被否决的项，整份清单再列一遍**：已同意的项不动，用户再看整份清单时能对照各项是否搭配得上。
- **不算破坏性变更**：用户确认的。没有删除或改名公开接口，使用者不用改配置、不用迁移，只是会多停下来几次。按普通 feat 发版。
- **否决默认栈后，插件的强制检查也要放行**：分支规范自查发现，前端的 bun 钩子会直接拒绝没有 lockfile 的新项目里的 npm / yarn / pnpm 安装命令，前端规则里也还有无条件的禁令，用户否决默认栈后 Claude 仍然做不到。用户在 2026-11-04 选择"真能否决"：钩子在没有 lockfile 时改成弹权限确认窗问用户（官方文档写明 PreToolUse 钩子返回 ask 会弹确认窗，原因文字显示给用户），已有 lockfile 的项目照旧跟着 lockfile 走；禁令改成只约束 Claude 不主动使用。否决了"前端默认栈保持强制、写成 PRD 例外"，因为用户这次可能就想用别的。权限窗的按钮文字由 Claude Code 显示，用户截图确认是英文，插件只能决定原因文字。
- **质疑结论**：插件规则原文证明缺口确实存在。用户选了补进插件，没选只写进个人全局 CLAUDE.md，这样所有用插件的项目都受益。值得做。
