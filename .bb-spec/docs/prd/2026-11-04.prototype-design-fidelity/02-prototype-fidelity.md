# 原型照项目整体还原

"原型"是改界面前给用户确认的 HTML 页面，由 `/prototype` 产出。"外壳"是所有原型共用的外框；"框"是外壳中间显示正式页面的区域；"底部说明"是外壳底部写说明的区域，分「这个画面的说明」「只在原型里成立」「还没确认的问题」三栏。"DESIGN.md"是放在用户项目根目录的设计规范文档。"页面框架"是页面最外面那一层：顶栏、侧边栏、导航的位置和尺寸。"写法"是组件和页面框架的 HTML 结构和类名。"底稿"是从项目真实页面抓下来的 HTML 和最终生效的样式。

## 用户故事

### P0：作为确认原型的用户，我想要框里就是项目真实页面的样子，以便确认的就是上线后的效果

**用例（主路径：DESIGN.md 够用）**
- 场景：一个 Vue 后台项目，DESIGN.md 写了页面框架（顶栏 56px、左侧菜单 220px、面包屑）以及按钮、表格、筛选区的样子和写法。用户要在订单列表的工具栏加一个「导出」按钮。
- 操作：运行 `/prototype 订单导出`。
- 预期：只读 DESIGN.md，不读源码。框里画出整个订单列表页：顶栏、左侧菜单、面包屑、筛选区、表格，工具栏里多了「导出」按钮；结构和类名照 DESIGN.md 的写法。「这个画面的说明」写明依据的是 DESIGN.md 的哪几节。

**用例（主路径：DESIGN.md 缺一部分）**
- 场景：同一个项目，DESIGN.md 没写"标签页"组件，而订单列表页上方有一排标签页。
- 操作：运行 `/prototype 订单导出`。
- 预期：其余部分按 DESIGN.md 画，只读标签页组件的源码；读完把标签页的样子和写法整理成 DESIGN.md 的补充内容，问用户要不要写进去。「这个画面的说明」列出依据的 DESIGN.md 章节和读过的源码文件路径。

**用例（边界：源码定不下来）**
- 场景：订单列表的表格是第三方组件库运行时生成的，源码里只有一行 `<DataTable :columns="cols" />`，看不出最终结构和样式；DESIGN.md 也没写表格的写法。
- 操作：运行 `/prototype 订单导出`。
- 预期：列出"表格的结构和样式在源码里定不下来"，问用户要不要把项目跑起来看。用户同意 → 先列出完整的启动命令和它写在哪个文件哪一行，用户再同意才跑；跑起来后抓下表格部分的真实 HTML 和样式当底稿，去掉其中的脚本和真实数据，抓完立刻关掉服务。用户不同意 → 按源码尽量画，「只在原型里成立」写明表格的样子可能不准。

### P0：作为命令行工具的维护者，我想要终端原型和真实输出一样，以便确认的就是用户在终端里看到的

**用例（主路径）**
- 场景：一个用 Go 写的命令行工具，DESIGN.md「终端界面」写了成功信息用青色 `#4ec9b0`、表格用 `│` 分隔。
- 操作：运行 `/prototype 导出命令`。
- 预期：按 DESIGN.md「终端界面」还原；框里终端的颜色、符号、表格格式和项目实际输出一致，不是外壳的默认四色。

## 约束

**取证顺序**
- C1：先读 DESIGN.md。这次涉及的页面框架和每个组件，DESIGN.md 都写了样子和写法 → 只按 DESIGN.md 画，不读源码。
- C2：DESIGN.md 缺这次涉及的某部分（页面框架、某个组件，或终端输出的格式）→ 只读这一部分对应的源码（如入口、路由、布局组件、导航、全局样式、组件库、改动所在页面里的相关代码），读完把缺的样子和写法整理成 DESIGN.md 的补充内容，问用户；同意才写进 DESIGN.md。
- C3：读完源码仍定不下来样子（如组件库运行时才生成的结构、运行时计算的样式、画布绘制的内容）→ 列出哪些部分定不下来，问用户要不要把项目跑起来看；用户不同意 → 按源码尽量画，「只在原型里成立」写明哪些部分可能不准。

**跑服务（只在用户同意后）**
- C4：用户同意跑 → 先列出完整的启动命令和它的出处（哪个文件、哪一行），依赖没装时一并说明要装什么；用户再次同意才执行。
- C5：跑起来后 → 打开要改的页面，抓下渲染后的 HTML 和最终生效的样式当底稿；放进框里之前去掉其中的 `<script>`、内联事件属性（如 `onclick`）、登录凭据和 token、真实用户数据（换成假数据）；只改这次要改的部分。「这个画面的说明」写明底稿来自哪个地址。
- C6：问用户要不要跑之前，先确认有能打开网页的工具；没有就不问，直接按源码画，「只在原型里成立」写明原因。为出原型启动的服务，抓完底稿后立即关掉，并确认端口已不在监听；启动失败、2 分钟内打不开要改的页面、页面要登录、或者没有能打开网页的工具时，也立即关掉，改按源码画，「只在原型里成立」写清卡在哪一步。

**画什么**
- C7：框里画出改动所在的整个页面，包括顶栏、侧边栏、导航、页面标题和周围的组件，不只画改动的那一块。
- C8：组件和页面框架照 DESIGN.md 的写法写；DESIGN.md 没写的，照项目源码里的 HTML 结构和类名写。
- C9：「这个画面的说明」写明依据：用到了 DESIGN.md 的哪几节、读了哪些源码文件（文件路径），用了底稿时写底稿地址。

**终端原型**
- C10：命令行项目的终端原型按 DESIGN.md「终端界面」和项目的输出代码还原颜色、符号、表格和进度条；定不下来时按 C3、C4 问用户要不要实际运行命令看输出：先列出完整命令和出处，用户再次同意才执行；输出里的真实数据换成假数据。
- C13：做完后拿实际界面和原型对比（`--compare`）需要跑项目时，同样先列出完整命令和出处、用户同意才跑，对比完立即关掉；用户不同意时对比结果返回"没跑起来"并写明原因。
- C11：原型可以给终端页面指定项目自己的配色；指定了 → 框里的终端用项目配色；没指定 → 用外壳默认终端配色。指定配色不影响同一份原型里的其他页面。
- C12：外壳默认终端配色只在项目没有命令行输出代码时使用。

## 验证路径

1. 在 DESIGN.md 写全了页面框架和所需组件的项目里运行 `/prototype` → 没读源码，框里是整个页面，说明里列出 DESIGN.md 章节。
2. 删掉 DESIGN.md 里某个组件的写法后再运行 → 只读了这个组件的源码，并被问要不要把它补进 DESIGN.md。
3. 改动涉及运行时才生成结构的组件 → 先列出定不下来的部分并被问要不要跑；同意后先看到完整命令和出处，再同意才跑；抓完底稿服务已关闭，框里没有 `<script>`。
4. 在一个命令行项目里出终端原型并给终端页面指定项目配色 → 框里终端用项目配色；去掉指定 → 变回外壳默认配色。
