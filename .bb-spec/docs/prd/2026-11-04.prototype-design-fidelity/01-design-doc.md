# DESIGN.md 设计规范

"DESIGN.md"是放在用户项目根目录（多仓库工作区放在文档仓库根目录）的设计规范文档。"原型"是改界面前给用户确认的 HTML 页面，由 `/prototype` 产出；`/prd`、`/revise` 需要出原型时都调用 `/prototype`。

## 用户故事

### P0：作为维护项目的用户，我想要项目有一份统一的设计规范，以便每次界面设计风格一致

**用例（主路径：已有界面代码，没有 DESIGN.md）**
- 场景：一个 Vue 后台项目已有十几个页面，根目录没有 DESIGN.md，用户要加一个导出按钮。
- 操作：运行 `/prototype 订单导出`。
- 预期：先读项目的全局样式、布局组件和组件代码，起草一份 DESIGN.md，如实记录项目现在用的颜色、字号、间距、页面框架和组件的样子与写法；列出不达标的地方（比如次要文字对比度只有 3.2:1）和修改建议；请用户确认。用户确认后 DESIGN.md 写进项目根目录，再开始出原型。

**用例（主路径：全新项目）**
- 场景：一个刚建好、还没有任何页面的项目，用户要做第一个登录页。
- 操作：运行 `/prototype 登录页`。
- 预期：按项目类型出 2～3 套都达标的风格，放在同一份原型里切换对比；用户选定一套后写成 DESIGN.md，再按它出登录页原型。

**用例（边界：已有 DESIGN.md 但不合格）**
- 场景：项目根目录有 DESIGN.md，缺「动效」一节，主按钮文字对比度 3.8:1，卡片内边距写的是 14px。
- 操作：运行 `/prototype`。
- 预期：出原型前列出 3 个问题和修改建议，用户确认后先改 DESIGN.md，再出原型。

**用例（边界：用到规范外的样式）**
- 场景：DESIGN.md 里没有"警告色"，这次设计要一个黄色警告条。
- 操作：出原型。
- 预期：原型说明里标出警告色是规范外的，并问用户要不要加。用户同意 → DESIGN.md 的颜色一节多了警告色及其色值；用户不同意 → 原型改用规范里已有的颜色。

**用例（边界：用户不接受修改建议）**
- 场景：起草时发现次要文字色对比度 4.2:1，建议改深；用户说项目就要用这个颜色。
- 操作：用户拒绝这条建议。
- 预期：DESIGN.md 的「无障碍」一节记下这条例外（哪个颜色、实际对比度、用户确认的日期），按现状继续出原型；以后检查 DESIGN.md 时不再报这一条。

## 约束

**什么时候读、什么时候建**
- C1：每次出原型 → 第一步先读项目根目录的 DESIGN.md，读完才开始设计。
- C2：没有 DESIGN.md、项目已有界面代码 → 先读项目的全局样式、布局组件和组件代码，起草 DESIGN.md 如实记录现状（含页面框架和组件的写法），并列出不达标的地方和修改建议，请用户确认；确认前不出原型。
- C3：没有 DESIGN.md、项目还没有界面代码 → 按项目类型出 2～3 套达标的风格放在同一份原型里对比，用户选定后写成 DESIGN.md；选定前不出要设计的页面。
- C4：已有 DESIGN.md 但缺项或不达标 → 出原型前列出每个问题和修改建议，用户确认后先改 DESIGN.md，再出原型。
- C5：原型里用到 DESIGN.md 没有的颜色、字号、间距、圆角、阴影或组件样式 → 在原型说明里逐个标出，问用户；用户同意 → 写进 DESIGN.md 对应的一节；不同意 → 原型改用 DESIGN.md 里有的。
- C6：DESIGN.md 的新建和修改都要用户明确同意后才写入项目里的文件；草稿只放在对话里或缓存目录里。
- C16：被 `/prd` 调用出原型时 → 用户同意的 DESIGN.md 新建或修改先放在和原型预览页同名的草稿文件里（内容是改完后的完整 DESIGN.md）；`/prd` 落盘 PRD 时一起写进项目并一起提交；开分支或 worktree 时草稿随原型预览页一起搬到新现场；用户选「不做了」时一起删掉。被 `/revise` 调用或单独运行 `/prototype` 时，用户同意即写入项目，`/revise` 的 commit 一并提交。
- C17：没有 DESIGN.md、用户这次不想建 → 按对话里的草稿出这一次原型，不写入项目；下次出原型时仍会再问。
- C14：用户不接受某条不达标的修改建议 → 在 DESIGN.md「无障碍」一节记下这条例外（哪一项、实际值、用户确认的日期），按现状继续；以后检查时，已记为例外的不再报。

**写什么**
- C7：DESIGN.md 必须有 10 节：风格定位、颜色、字体与字号、间距、圆角边框阴影、布局与断点、组件、动效、无障碍、终端界面。项目用不上的一节写"不适用"和一句原因。
- C8：颜色按用途命名（如主色、背景色、次要文字色、错误色），每个颜色写具体色值；项目支持深色模式时明暗两套都写。
- C9：颜色对比度符合 WCAG 2.2 AA：正文文字对背景至少 4.5:1；大号文字（24px 及以上，或 18.66px 及以上加粗）、图标、输入框和按钮的边框对相邻背景至少 3:1。
- C10：间距和圆角的每个值都是 4 的倍数（0 也算）；表示全圆角（胶囊形按钮、圆形头像）时写 9999px，不算违规。
- C11：字号、行高、间距、圆角、阴影、动效时长都写具体数值和单位（px、ms 等），不写"简洁""大方""适中"这类形容词代替数值。
- C12：「组件」一节至少写按钮、输入框、表格、卡片、弹窗、提示条，每种写写法（HTML 结构和类名）和默认、悬停、按下、禁用、聚焦 5 种状态的样子；项目里用不到的组件写"不适用"。
- C15：「布局与断点」一节写页面框架：顶栏、侧边栏、导航的位置、尺寸和写法（HTML 结构和类名），以及不同断点下怎么变。
- C13：「终端界面」一节写命令行输出用的颜色（按用途命名、写具体值）、符号、表格和进度条格式；不是命令行项目时写"不适用"。

## 验收

- [ ] C1：`/prototype` 规程的第一步是读项目根目录的 DESIGN.md。
- [ ] C2：规程写明没有 DESIGN.md 且已有界面代码时，先如实起草并列出不达标项、用户确认前不出原型。
- [ ] C3：规程写明全新项目出 2～3 套风格在同一份原型里对比，选定后写成 DESIGN.md。
- [ ] C4：规程写明已有 DESIGN.md 缺项或不达标时先列问题、确认后先改 DESIGN.md。
- [ ] C5：规程写明规范外的样式要逐个标出并问用户，同意写进、不同意改用规范内的。
- [ ] C6：规程写明 DESIGN.md 的新建和修改都要用户同意后才写入项目文件，草稿只放对话或缓存目录。
- [ ] C7：插件提供的 DESIGN.md 模板有这 10 节标题，并写明用不上的写"不适用"和原因。
- [ ] C8：模板和规程要求颜色按用途命名、写具体色值，支持深色模式时写两套。
- [ ] C9：规程写明对比度的两档数值（4.5:1、3:1）和各自适用的对象，以及大号文字的界定。
- [ ] C10：规程和模板写明间距和圆角取 4 的倍数，全圆角写 9999px 不算违规。
- [ ] C11：规程写明所有尺寸和时长写具体数值和单位，禁用形容词代替。
- [ ] C12：模板的「组件」一节列出 6 种组件，每种有「写法」一栏和 5 种状态。
- [ ] C13：模板的「终端界面」一节列出颜色、符号、表格、进度条，并写明非命令行项目写"不适用"。
- [ ] C14：规程写明用户不接受修改建议时在「无障碍」一节记例外（项、实际值、日期）、按现状继续、以后不再报；模板「无障碍」一节有记例外的位置。
- [ ] C15：模板的「布局与断点」一节有页面框架的位置、尺寸、写法和断点变化。
- [ ] C16：`/prototype` 规程写明被 `/prd` 调用时 DESIGN.md 先放草稿；`/prd` 规程写明落盘时写入并提交草稿、搬现场时带上草稿、「不做了」时删掉草稿；`/revise` 规程的 commit 清单含本次经用户同意改过的 DESIGN.md。
- [ ] C17：规程写明用户不想建时按草稿出这一次原型、不写入项目、下次再问。

## 验证路径

1. 在一个有界面代码、没有 DESIGN.md 的项目里运行 `/prototype` → 先看到 DESIGN.md 草稿和不达标清单，没看到原型。
2. 确认草稿 → 项目根目录出现 DESIGN.md，10 节齐全，随后才出原型。
3. 把 DESIGN.md 里主按钮文字色改成对比度 3:1 的值后再运行 `/prototype` → 出原型前先列出这条不达标。
4. 设计里加一个规范外的颜色 → 被标出并询问；同意后 DESIGN.md 颜色一节多了这个颜色。
