# 原型照项目真实界面还原，设计风格统一

下文的"原型"是改界面前给用户确认的 HTML 页面；"外壳"是所有原型共用的外框；"框"是外壳中间显示正式页面的区域，只有框里的内容要做进产品。"DESIGN.md"是放在用户项目根目录的设计规范文档。

## 背景与问题

`/prototype` 出原型时，规则只要求把项目的样式抄进原型，没说要还原到多大范围。实际做出来常常只单独画改动的那一块，没有项目的顶栏、侧边栏、导航和周围组件，组件的结构也是凭印象写的。用户确认的是一个和真实界面差距很大的样子，等代码写完拿实际界面对比时才发现对不上。终端原型更是固定用外壳的四种颜色，不管项目自己的输出代码用了什么颜色和格式。

另外，每次界面设计都从零开始挑颜色、字号、间距，没有一份项目自己的设计规范，同一个项目里不同次的设计风格各不相同，写界面代码时也没有依据。

## 目标

- 原型框里画出的是改动所在的整个页面，结构、类名、样式和项目一致；项目能在本地直接跑起来时，底稿就是真实页面。
- 每个有界面的项目都有一份 DESIGN.md，写满 10 项内容、全部用具体数值，颜色对比度符合 WCAG 2.2 AA。
- 出原型、写界面代码、审查界面代码都以 DESIGN.md 为依据；用到规范外的样式必须经用户同意并写进 DESIGN.md。

## 非目标

- 不改外壳本身的样子（左栏、框上方提示、底部说明、明暗主题）。
- 不为 bb-spec 仓库自己写 DESIGN.md。
- 不自动修改项目代码去符合 DESIGN.md；代码和 DESIGN.md 对不上时只列出来请用户选。
- 项目需要登录、另配环境变量、数据库或外部服务才能打开页面时，不想办法绕过，直接改用读代码还原。
- 不提供 DESIGN.md 的可视化编辑工具。

## 依赖与交付顺序

01 → {02, 03 可并行}。02、03 都要读 DESIGN.md，先定它的内容和起草方式。

## 整体验证路径

1. 在一个已有界面代码、没有 DESIGN.md、能用现成命令直接跑起来的网页项目里运行 `/prototype` → 先起草 DESIGN.md 请用户确认，确认后才出原型。
2. 确认 DESIGN.md 后 → 原型框里是项目真实页面抓下来的底稿，只改了这次要改的部分，底部说明写着底稿来自哪个地址。
3. 原型里用到 DESIGN.md 没有的颜色 → 先问用户，同意后 DESIGN.md 多了这个颜色。
4. 走 `/exec` 实现这个界面 → 实现工程师拿到 DESIGN.md，审查员报告里有逐项对照 DESIGN.md 的结论。
5. 手动把代码里一个颜色改成规范外的值后运行 `/doc-update` → 列出这处不一致，请用户选改代码还是改 DESIGN.md。

## 决策记录

- **做不做**：值得做。本插件自己的会话里就出过一次：原型里凭印象画外壳，漏掉了左栏一行小标题，代码写完对比时才发现。插件里也没有任何设计规范文件可以复用。
- **能跑就跑、跑不了读代码（方向 B）**：用户选定。只读代码还原会漏掉运行时才有的东西，比如组件库生成的结构和动态样式；能跑起来时直接拿真实页面最准。否掉了"只改规则文字、一律读代码还原"（方向 A），因为它准确度上限低；也否掉了"永远要求跑起来"，因为很多项目缺后端或账号根本跑不了。
- **什么算能跑**：有现成启动命令、不用登录、不用另配环境变量、数据库或外部服务，2 分钟内能打开要改的页面。依赖没装时先问用户，因为装依赖要联网下载、会改动项目目录。用户选定，否掉了"每次先问用户怎么跑"，因为多数情况下能自己判断。
- **底稿怎么用**：抓真实 HTML 和最终生效的样式放进框里，只改要改的部分。否掉了"只截图做参考、框里仍手写"，因为手写仍会有偏差。
- **跑不起来时画多大**：画改动所在的整个页面，并列出照着哪些源码文件还原，方便用户核对依据。
- **文件名 DESIGN.md**：用户原话是 design.md，确认改用大写，和 README.md、AGENTS.md、ARCHITECTURE.md 一致。
- **首次创建**：先起草、用户确认后才出原型。否掉了"原型确认后再总结成 DESIGN.md"，因为那样第一份原型没有规范可依。已有界面代码的项目如实记录现状；全新项目按项目类型出 2～3 套风格给用户选，否掉了"一律以外壳默认页面样式为起点"，因为所有新项目会长得一样。
- **必写 10 项**：风格定位、颜色、字体与字号、间距、圆角边框阴影、布局与断点、组件、动效、无障碍、终端界面。用不上的写"不适用"和原因。否掉了只写前 5 项，因为组件和布局最容易各写各的。
- **"现代化"怎么判**：用可量的硬标准：对比度符合 WCAG 2.2 AA，间距和圆角取 4 的倍数，每项写具体数值，颜色按用途命名，不写形容词。否掉了"只要求写具体数值"，因为数值写全了也可能对比度不够。
- **规范外的样式**：先问用户，同意后写进 DESIGN.md，不同意就改用规范里有的。否掉了自动补进去，因为规范会悄悄膨胀；也否掉了完全禁止，因为新需求确实会带来新样式。
- **已有 DESIGN.md 不合格**：出原型前列出问题和修改建议，用户确认后先改 DESIGN.md。
- **代码和 DESIGN.md 对不上以谁为准**：问用户。DESIGN.md 是规范，和 AGENTS.md 里的约束同一性质，不能像 README 那样直接改成代码的样子。
- **谁读 DESIGN.md**：出原型和写界面代码都读，审查员也对照检查。否掉了只在出原型时读，因为原型对了代码仍可能写偏。
- **终端原型**：照项目实际输出还原，能跑就跑命令抓真实输出；外壳改成允许项目覆盖终端配色，项目没有输出代码时才用外壳默认配色。否掉了继续用外壳固定配色，因为那和项目真实输出对不上。
