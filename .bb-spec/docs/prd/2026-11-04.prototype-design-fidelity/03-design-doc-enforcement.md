# 写界面代码时守规范

"DESIGN.md"是放在用户项目根目录（多仓库工作区放在文档仓库根目录）的设计规范文档。"实现工程师"和"审查员"是 `/exec`、`/revise` 里分别负责写代码和对照要求检查代码的两个子代理。`/doc-update` 是让项目根目录的说明文档和代码保持一致的流程。

## 用户故事

### P1：作为维护项目的用户，我想要写出来的界面代码也符合 DESIGN.md，以便原型对了、代码也不跑偏

**用例（主路径）**
- 场景：项目有 DESIGN.md，主色是 `#2563eb`、卡片圆角 8px。`/exec` 在实现一个新页面。
- 操作：实现工程师写完页面，审查员检查。
- 预期：实现工程师收到的输入里有 DESIGN.md；审查员的报告里有一项"DESIGN.md 对照"，逐条列出用到的颜色、字号、间距、圆角是否都在规范里。代码里写了 `#2564ec` 这种规范外的色值时，审查员把它列为问题。

**用例（边界：项目没有 DESIGN.md）**
- 场景：一个纯后端项目，没有界面，也没有 DESIGN.md。
- 操作：`/exec` 实现一个接口。
- 预期：实现工程师和审查员的输入里都没有 DESIGN.md，审查报告里没有"DESIGN.md 对照"这一项，流程照常。

### P1：作为维护项目的用户，我想要代码和 DESIGN.md 对不上时由我决定以谁为准，以便规范不会悄悄被代码带偏

**用例（主路径）**
- 场景：有人直接在代码里把按钮圆角改成了 6px，DESIGN.md 写的是 8px。
- 操作：运行 `/doc-update`。
- 预期：列出这处不一致（代码文件和行号、DESIGN.md 里写的值），请用户选：改代码（转 `/revise`）、改 DESIGN.md、跳过。用户不选之前两边都不动。

## 约束

- C1：`/exec`、`/revise` 改动界面代码（页面、组件、样式文件，或命令行输出的颜色和格式）且项目有 DESIGN.md 时 → 派给实现工程师的输入里包含 DESIGN.md 的路径，并要求按它写。
- C2：同样情况下 → 派给审查员的输入里包含 DESIGN.md 的路径；审查员报告里有"DESIGN.md 对照"一项，列出代码用到的颜色、字号、间距、圆角、阴影是否都在规范里，规范外的每处给出文件和行号，算作需要修的问题。
- C3：项目没有 DESIGN.md，或本次改动不涉及界面代码 → 实现工程师和审查员的输入里都不带 DESIGN.md，审查报告里不出现"DESIGN.md 对照"。
- C4：`/doc-update` 把项目根目录的 DESIGN.md 纳入它维护的文档名单。
- C5：`/doc-update` 发现界面代码和 DESIGN.md 对不上 → 列出代码的文件和行号、DESIGN.md 里的值，请用户选：改代码（转 `/revise`）/ 改 DESIGN.md / 跳过；用户选之前两边都不改。

## 验收

- [ ] C1：`/exec`、`/revise` 的规程写明改动界面代码且有 DESIGN.md 时，给实现工程师的输入带 DESIGN.md 路径；实现工程师的说明里写明要按 DESIGN.md 写。
- [ ] C2：规程写明给审查员的输入带 DESIGN.md 路径；审查员的说明里有"DESIGN.md 对照"这一项，要求规范外的值给出文件和行号并算作问题。
- [ ] C3：规程写明没有 DESIGN.md 或不涉及界面代码时不带 DESIGN.md、报告里不出现这一项。
- [ ] C4：`/doc-update` 维护的根文档名单里有 DESIGN.md。
- [ ] C5：`/doc-update` 规程写明代码和 DESIGN.md 不一致时列出位置和值，请用户三选一，选之前不改。

## 验证路径

1. 在有 DESIGN.md 的项目里用 `/exec` 实现一个页面，故意让代码用一个规范外的颜色 → 审查报告里"DESIGN.md 对照"列出这个颜色的文件和行号。
2. 在纯后端项目里跑 `/exec` → 审查报告里没有"DESIGN.md 对照"。
3. 手动改一个组件的圆角让它和 DESIGN.md 不一致，运行 `/doc-update` → 看到这处不一致和三个选项。
