# bb-spec 介绍主页与 README 改版

## 背景与问题
第一次来到仓库 `0xBB2B/bb-spec` 的人，只能靠 README 了解 bb-spec。README 每种语言约 325 行，读者要往下翻很久才弄清它是什么、为什么值得用、怎么装：

- 最能说明"为什么选它"的三个差异点（三 Agent 隔离执行、磁盘文档是唯一交接物、代码和 PRD 经 git 双向可查）写在 README 倒数第二节「设计渊源」的末尾。
- 安装写了两遍：开头「30 秒上手」一遍，中间「安装」一节又一遍。
- 「阶段一览」一节约 60 行，夹着很细的内部机制（比如 GitHub / GitLab 合并方式的设置）。
- Hook 的信息分散在三处（「附带产物」一行、「默认启用的 Hooks」表、「Hook 开关速查」表）；写给贡献者看的「测试」和写给老用户的「从 13 及更早版本升级」插在正文中间。

项目没有自己的网站，想把 bb-spec 介绍给别人时只能甩一个仓库链接。

## 目标
- 打开 `https://0xbb2b.github.io/bb-spec/` 就能在一屏多一点的篇幅里看懂三件事：bb-spec 解决什么问题、流水线怎么走、怎么安装。
- 主页内容一合并到 main 就自动上线，不需要人手动发布。
- 五份 README 开头先讲清"是什么、为什么、怎么装"，同一件事只写一处，细节可以展开看但不挡路。

## 非目标
- 主页只有一页，不做文档站、博客、搜索、版本号展示，也不把 README 全文搬到主页；更多细节用链接指回 GitHub 上的 README。
- 主页只做中文、英文两种语言；繁體中文、日本語、한국어只有 README，没有主页。
- 主页只有深色一套配色，不做明亮主题和主题切换。
- 不用自定义域名，用 GitHub 默认的 `0xbb2b.github.io/bb-spec`。
- 不做访问统计，不加任何第三方脚本。
- README 改版只调整结构和写法，不删除任何功能说明、命令或链接。

## 依赖与交付顺序
01 → 02；03 可以和 01 并行。02 要有 01 的主页文件才能部署；03 只依赖主页地址，地址是固定的。

## 整体验证路径
1. 在本分支打开主页文件（不经服务器，直接用浏览器打开）→ 看到深色终端风主页，顶栏、标题区、「它解决什么问题」、「流水线怎么走」、「安装」、页脚依次出现。
2. 浏览器语言设为 `en-US`、清掉这个站点的存储后刷新 → 页面是英文；点「中文」→ 整页变中文；再刷新 → 仍是中文。
3. 把浏览器窗口缩到 390px 宽 → 页面没有横向滚动条，流水线变成竖排，三个面板上下排。
4. 跑 `bash tests/validate.sh` 和 `tests/*.sh` → 全部通过。
5. 打开五份 README → 开头紧跟着「它解决什么问题」和主页链接；`/plugin marketplace add 0xBB2B/bb-spec` 在每份里只出现一次；顶部导航每个链接都能跳到对应章节。
6. 在仓库设置里把 Pages 的来源设为 GitHub Actions，PR squash 合并到 main → Actions 里出现一次部署运行并成功；打开 `https://0xbb2b.github.io/bb-spec/` 看到和第 1 步一样的主页。
7. 之后再合并一个只改 `plugins/` 下文件的 PR → 没有新的部署运行，主页保持不变。

## 决策记录
- **质疑结论：做站点，也改 README**（用户 2026-11-17 要求）。更便宜的做法是只改 README；没有访问数据能证明站点一定带来更多用户。用户明确要站点，照做。为了控制以后的同步成本，主页只放三块内容，其余用链接指回 README。
- **选深色终端风，主色用 Claude Code 徽章橙 `#D97757`**（用户 2026-11-17 从 5 版设计里选定方案 B，并要求"颜色从绿色改成橙色""符合 claude code 的插件风格颜色"）。主色取自 README 顶部 Claude Code Plugin 徽章的颜色。链接和命令名保持蓝色 `#58A6FF`，让"能点的"和"强调的"分得开（用户 2026-11-17 同意）。否掉了极简文档风、杂志编辑风、明亮渐变 SaaS 风、蓝图图解风。
- **新建项目根 `DESIGN.md`**（用户 2026-11-17 选"要"）。这是项目第一个图形界面，以后改主页有统一的颜色、字号、组件规矩可依。
- **中英切换放在同一页里，不拆成两个地址**（用户 2026-11-17 选定）。代价是链接没法指定语言，搜索引擎只收录 HTML 里写死的那种语言。否掉了"`/` 中文、`/en/` 英文两个地址"。
- **默认语言按浏览器语言定，点过按钮后记住选择**（用户 2026-11-17 提出并确认规则）：浏览器语言以 `zh` 开头（简体、繁体都算）显示中文，其余显示英文；访客点过「中文 / English」后，下次按他上次的选择；浏览器关了脚本时显示中文。
- **合并到 main 后自动部署，只在主页文件或部署配置有改动时才部署**（用户 2026-11-17 提出"每次 main 合并之后自动部署"，并选了"主页文件有改动才部署"）。用户最初的说法是"每次一发版成功之后进行部署"。按项目规定，改主页文案用 `docs` 类型的 commit，release-please 不会为它发版，主页改动要等下一次 `feat` / `fix` 发版才能上线，本次 PR 合并后站点也不会首次上线，所以改成跟随 main。否掉了"只在发版后部署"和"发版后部署 + 手动部署按钮"。
- **部署做成单独的 workflow，不挂在 `release-please.yml` 下面**。部署不再跟随发版，和发版放在一起只会让两件事互相牵连。
- **主页不引用任何外部资源**（字体、脚本、样式、图片都是站内文件）。`DESIGN.md` 只用系统等宽字体，原型也没有外部依赖；不加外部资源，访客打开时就不会把访问信息发给第三方，也不会因为第三方服务挂了而页面坏掉。
- **复制失败时按钮保持「复制」不变，不另外提示**。原型确认的交互里没有失败状态；GitHub Pages 是 https 页面，现代浏览器在用户点击时写剪贴板基本都会成功，不为极少数情况新增界面。
- **README 压缩「阶段一览」时把细节放进可展开的折叠块，不删内容**（用户 2026-11-17 勾选"压缩阶段一览"）。README 是功能说明的完整来源，删掉的细节在别处找不到。
- **本次 commit 类型用 `docs`**。主页、部署 workflow、`DESIGN.md`、README 都不随插件交付，不改变插件对使用者的行为，按 `CLAUDE.md` 的规定用 `docs`，合并后不发新版本。
