# 无关发现收尾清单

## 用户故事
### P0：作为做完一件事等收尾的用户，我想一次看到所有顺带发现的问题并一次选完，以便选中的都在这个分支修掉，不用每件单独再开一个 PR

**用例（主路径：收尾时一次问）**
- 场景：`/exec` 做完一个需求。过程中 Claude 发现两件和这次需求无关的事：一个测试传了早已不存在的选项；README 有一句话说得不准。
- 操作：`/exec` 输出完成简报。
- 预期：简报里有「无关发现」清单，列出这 2 条，各带 `文件:行号`、问题、后果和估计用时。简报之后弹一次窗问"处理哪些"。用户选"全部处理"，Claude 在当前分支把两条都修掉并提交，没有新开分支。

**用例（只挑几条）**
- 场景：清单有 5 条。
- 操作：用户在弹窗的"其他"里填"1,3"。
- 预期：只修第 1、3 条。其余 3 条留在简报的"待解决"里。

**用例（都不处理）**
- 场景：同主路径。
- 操作：用户选"都不处理"。
- 预期：Claude 不改任何文件，2 条都留在简报的"待解决"里。

**用例（没有无关发现）**
- 场景：过程中没有碰到无关的问题。
- 操作：`/exec` 输出完成简报。
- 预期：简报写"无关发现：无"，不弹窗。

**用例（推送前又冒出新的）**
- 场景：`/revise` 收尾时已经问过 2 条。之后运行 `/git-push`，代码审查和分支自查又带出 1 条无关的问题。
- 操作：`/git-push` 走到推送之前。
- 预期：弹一次窗，只问新冒出来的这 1 条，之前问过的 2 条不再问。用户选处理，Claude 修完、重跑全量测试，再推送。合并之后的简报里没有"还有几件事要不要处理"。

**用例（要另开需求的发现）**
- 场景：发现的一条问题要改变已有功能的行为才能解决。
- 操作：收尾。
- 预期：这一条列在清单的"要另开需求"一段，不进弹窗；简报的"待解决"里写明它要走 `/prd`。

**用例（合并之后才发现）**
- 场景：PR 已经合并，Claude 在合并后的检查里又发现 2 条无关的问题。
- 操作：`/git-push` 输出最后的简报。
- 预期：2 条合成一张清单，一次弹窗问；选中的放进同一个新分支、同一个 PR，不是每条一个。

## 约束
- **什么算无关发现**：干活过程中碰到的、和这次要解决的问题不是同一个根因的问题。来源包括 Claude 自己读代码时看到的、子代理报告里提到的、审查报告备注里提到的。同根因位置不算无关发现。
- **发现时不动手**：碰到无关发现，Claude 和子代理都只记下来，不改它。
- **每条要有证据**：清单里每条写编号、位置（`文件:行号`）、一句话问题、不处理的后果、估计用时。还没验证的推测要标"未验证"，并写怎么验证。
- **清单分两段**：能在当前分支修的（修代码错误、清过期内容、改不准的文档）；要另开需求的（要新增功能，或者要改变已有功能的行为）。
- **清单写法**：

  ```
  ## 无关发现
  **能在当前分支修的**
  | # | 位置 | 问题 | 不处理的后果 | 估计用时 |
  |---|---|---|---|---|
  | 1 | <文件:行号> | <一句话> | <一句话> | <如 10 分钟> |

  **要另开需求的**
  - <文件:行号> <一句话问题> — <为什么要另开需求>
  ```
- **在哪问**：`/exec` 收尾、`/revise` 收尾各问一次，位置在完成简报之后；`/git-push` 在推送之前问一次。
- **不重复问**：同一个会话里已经问过的条目不再问，`/git-push` 推送前只问新冒出来的。
- **怎么问**："能在当前分支修的"一段不为空时，弹一次窗，问题是"上面 N 条无关发现，处理哪些？"，预设选项依次是"全部处理"（说明：在当前分支修完，进同一个 PR）和"都不处理"（说明：留在简报的待解决里）；要挑几条时，用户在"其他"里填编号，如 `1,3`。
- **清单为空**：两段都为空时，简报写"无关发现：无"，不弹窗。只有"要另开需求的"一段有内容时，也不弹窗。
- **选中的怎么修**：选中的条目一次全部交给 `/revise`，在当前分支修完并本地提交，不新开分支。
- **没选中的**：留在完成简报的"待解决"里，每条带位置。
- **要另开需求的**：不进弹窗，写进完成简报的"待解决"，标明要走 `/prd`。
- **推送前选了处理**：`/git-push` 等修完、重跑全量测试通过后再推送。
- **被别的环节调用的 `/revise`**：`/revise` 是被 `/exec` 或 `/git-push` 调用来修问题的时候，自己不弹这个窗，把它记下的无关发现交回调用它的环节，由那个环节合进自己的清单一起问。
- **修无关发现时又发现新的**：新的记进清单，等这一轮修完后再问一次，只问新的。
- **合并之后才发现的**：PR 已经合并时，新发现的条目同样合成一张清单一次问；选中的放进同一个新分支、同一个 PR。

## 验收
- [ ] 同根因位置没有出现在无关发现清单里；清单里的条目来源覆盖 Claude 自己看到的、子代理报告的、审查备注的。
- [ ] 无关发现在被问到之前没有被改动。
- [ ] 清单每条都有编号、`文件:行号`、问题、后果、估计用时；没验证的标了"未验证"和验证办法。
- [ ] 清单分成"能在当前分支修的"和"要另开需求的"两段。
- [ ] 清单的写法和约束里的一致。
- [ ] `/exec`、`/revise` 的弹窗出现在完成简报之后；`/git-push` 的弹窗出现在推送之前。
- [ ] 同一个会话里问过的条目，后面的环节没有再问。
- [ ] 弹窗的问题和两个预设选项与约束一致；在"其他"里填编号能只选其中几条。
- [ ] 两段都为空时简报写"无关发现：无"且没有弹窗；只有"要另开需求的"时也没有弹窗。
- [ ] 选中的条目是一次交给 `/revise` 修的，改动提交在当前分支上，没有新开分支。
- [ ] 没选中的条目带着位置留在"待解决"里。
- [ ] 要另开需求的条目没进弹窗，"待解决"里写了要走 `/prd`。
- [ ] `/git-push` 推送前选了处理时，修完并重跑全量测试通过之后才推送。
- [ ] 被 `/exec` 或 `/git-push` 调用的 `/revise` 没有自己弹窗，它记下的条目出现在调用环节的清单里。
- [ ] 修无关发现时新发现的条目，在这一轮修完后被单独问了一次。
- [ ] 合并之后才发现的多条被一次问完，选中的在同一个新分支、同一个 PR 里。

## 验证路径
1. 准备一个项目：除了要修的问题，另放 2 个无关的小问题（一个测试传了不存在的选项；README 有一句不准），再放 1 个要改已有行为才能解决的问题。
2. 运行 `/revise` 修主问题 → 完成简报里的「无关发现」清单，上段 2 条、下段 1 条；简报之后弹窗，问题是"上面 2 条无关发现，处理哪些？"。
3. 在"其他"里填 `1` → 只有第 1 条被修，提交在当前分支；第 2 条和下段那条在"待解决"里。
4. 运行 `/git-push` → 推送之前没有再问第 2 条；如果审查带出新的无关问题，弹窗只列新的。
5. 合并完成后看最后的简报 → 没有零散的"要不要处理"提问。
