# 审查附带同类位置，测试缺口当轮补

## 用户故事
### P0：作为等修复结果的用户，我想让审查一次把同类问题都指出来，以便不用修完一处、下一轮审查又冒出同样的一处

**用例（主路径：审查发现问题，别处也有）**
- 场景：这次改了 `user-interaction.ts` 第 229 行附近。审查子代理发现第 229 行出错后清掉了用户原话，建议却叫主代理直接重试。同一个文件第 269、275、297 行（这次没改到）也是同样的写法。
- 操作：`/revise` 修复后派审查子代理审查。
- 预期：审查报告里这条问题下面有"同类位置"，列出第 269、275、297 行，各带一句理由。Claude 读代码核实后，把这 3 处和第 229 行在本轮一起修完。

**用例（搜过了，没有同类位置）**
- 场景：审查子代理发现一个问题，别处没有同样的写法。
- 操作：同上。
- 预期：这条问题下面写"同类位置：已搜，无"。

### P0：作为等修复结果的用户，我想让审查指出的测试缺口当轮就补上，以便不用事后为一条测试单独再开一个 PR

**用例（主路径：测试缺口当轮补上）**
- 场景：审查报告写"补授权之后 PM 接手核对这一步，实现合规但没有测试覆盖"。
- 操作：`/exec` 或 `/revise` 处理审查结果。
- 预期：Claude 派测试子代理补上这条测试，跑通后再把这一条交给审查子代理复查。完成简报的"待解决"里没有这条测试缺口。

**用例（补出来的测试直接通过）**
- 场景：同上，补上的测试一跑就通过。
- 操作：同上。
- 预期：算补完。这说明行为本来就对，只是之前没有测试。

**用例（补出来的测试失败）**
- 场景：同上，补上的测试跑不过。
- 操作：同上。
- 预期：说明实现确实有问题。Claude 按"实现不符合期望行为"处理，在本轮改实现直到测试通过。

**用例（当轮补不了）**
- 场景：审查指出"裁决路径上没有测试"，但要造出一个待裁决事项，得先搭一整套多方会话环境。
- 操作：同上。
- 预期：Claude 停下，说明卡在哪，弹窗问用户"不补"还是"换个办法补"。用户选"不补"后，完成简报写明哪一条没补、为什么、用户在哪天定的。

## 约束
- **哪些问题要附同类位置**：审查子代理指出的"实现不符合期望行为"的问题，以及鲁棒性和安全问题。注释写法、代码风格这类代码纪律问题，以及设计规范对照的问题，不要求附。
- **同类位置怎么找**：审查子代理在这次变更文件之外搜整个仓库，找两类位置：调用了出问题那段代码、会受同一缺陷影响的位置；别处独立写的同样错误写法。
- **报告怎么写**：每条要附同类位置的问题下面多一行。有同类位置时逐个列出 `文件:行号` 和一句理由；没有时写"同类位置：已搜，无"。

  ```
  - ❌ 🔩 `<文件:行号>` <一句话问题> — 触发：<…> — 建议：<…>
    - 同类位置：`<文件:行号>` <一句理由>；`<文件:行号>` <一句理由>
  ```
- **审查子代理仍然只读**：它只列出同类位置，不改任何文件。
- **同类位置怎么处理**：`/exec` 和 `/revise` 拿到审查报告后，Claude 逐个读代码核实同类位置；核实成立的和问题本身在本轮一起修，每个位置至少一条测试。核实不成立的在完成简报里写明位置和不成立的理由。
- **测试缺口当轮补**：审查子代理指出的每一条测试缺口（"实现合规但没有测试覆盖"和报告"遗漏"一节里的条目），`/exec` 和 `/revise` 都在本轮派测试子代理补上，补完把这几条交给审查子代理复查。
- **补出来的测试直接通过**：算补完。
- **补出来的测试失败**：按"实现不符合期望行为"处理，在本轮改实现直到通过。
- **当轮补不了**：写不出能自动跑的测试时（例如要依赖真实的外部服务，或者要搭的环境超出这次改动的范围），Claude 停下，说明卡在哪，用一次弹窗问用户。问题是"这 N 条测试缺口当轮补不了，怎么办？"，预设选项依次是"不补"（说明：简报里记下没补和原因）和"换个办法补"（说明：你告诉我用什么办法测）。
- **用户选"不补"**：完成简报的"待解决"里写明哪一条没补、补不了的原因、用户在哪天定的。
- **完成简报里不留没处理的测试缺口**：`/exec` 和 `/revise` 完成简报的"待解决"里，除了用户选过"不补"的条目，不出现测试缺口。
- **推送前的分支自查也一样**：`/git-push` 的分支自查指出"有实现但没有测试"时，和违规项一起交给 `/revise` 在推送前补上，处理方式同上。

## 验收
- [ ] 审查报告里，每条"实现不符合期望行为"的问题、每条鲁棒性或安全问题下面都有"同类位置"一行；代码纪律和设计规范对照的问题下面没有这一行。
- [ ] 变更文件之外的同类位置（调用处、同样写法）能出现在审查报告里。
- [ ] "同类位置"一行的写法和约束里的一致；没有同类位置时写的是"同类位置：已搜，无"。
- [ ] 审查子代理没有改任何文件。
- [ ] 核实成立的同类位置和问题本身在同一轮修完，各有至少一条测试；核实不成立的在完成简报里有位置和理由。
- [ ] 审查指出的每条测试缺口，本轮都派了测试子代理去补，补完做了复查。
- [ ] 补出来的测试直接通过时，流程继续，没有当成错误。
- [ ] 补出来的测试失败时，本轮改了实现并最终通过。
- [ ] 当轮补不了时 Claude 停下并弹窗，问题和两个预设选项与约束一致。
- [ ] 用户选"不补"后，完成简报写了哪一条、原因和用户定的日期。
- [ ] 完成简报的"待解决"里没有用户没表过态的测试缺口。
- [ ] `/git-push` 分支自查指出"有实现但没有测试"时，推送前交给了 `/revise` 补。

## 验证路径
1. 准备一个项目：一个文件里有 4 处同样的错误写法；让 `/revise` 只修其中 1 处，并且故意留一条没有测试覆盖的行为。
2. 等审查子代理的报告 → 那条问题下面的"同类位置"列出另外 3 处；报告指出 1 条测试缺口。
3. 观察 Claude 的处理 → 3 处同类位置在本轮修完，各有测试；测试缺口被补上并复查。
4. 看完成简报 → "待解决"里没有测试缺口。
5. 再准备一条必须依赖真实外部服务才能测的行为，重复一次 → Claude 停下弹窗，选项是"不补"和"换个办法补"；选"不补"后，简报写明这一条、原因和日期。
