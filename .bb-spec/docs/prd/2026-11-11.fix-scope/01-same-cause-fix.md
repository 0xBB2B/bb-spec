# 同根因位置一次修完

## 用户故事
### P0：作为报问题的用户，我想只报一处症状就让同一个根因牵连的所有位置一起修好，以便不用一轮一轮地说"也一起修"

**用例（主路径：根因函数有多处调用）**
- 场景：函数 `readStore` 把"文件读不出来"当成"没有记录"。`startup.ts`、`settings.ts`、`daemon.ts` 都调用它。
- 操作：用户运行 `/revise`，只说"授信文件写坏后每次启动都弹窗"（这是 `startup.ts` 的症状）。
- 预期：诊断结果里有一张「同根因位置」表，列出 `settings.ts`、`daemon.ts` 的调用处，各带 `文件:行号` 和理由，处理写"一起修"。Claude 不停下等确认，直接修；三个位置在同一轮修完，每个位置至少一条测试，同一次提交。

**用例（别处有同样的错误写法）**
- 场景：同上，另外 `export.ts` 没有调用 `readStore`，但自己写了一段同样把"读不出来"当成"没有记录"的判断。
- 操作：同上。
- 预期：`export.ts` 那一处也出现在表里，类别写"同样写法"，一起修。

**用例（搜过了，没有其他位置）**
- 场景：出问题的函数只有一处调用，别处也没有同样写法。
- 操作：用户运行 `/revise` 报这个问题。
- 预期：诊断结果里写"同根因位置：搜过了，没有其他位置"，并写明搜了什么（函数名或搜索用的关键词）。

**用例（某一处要用户取舍）**
- 场景：同主路径，但 `daemon.ts` 那一处有两种合理的修法，用户看到的结果不一样（读不出来时"停下报错"还是"按没有记录继续"）。
- 操作：同上。
- 预期：Claude 只就 `daemon.ts` 这一处停下，用一次弹窗问用户选哪种；用户选完后，三个位置在同一轮修完。

**用例（某一处要新设计才能修）**
- 场景：同主路径，但 `daemon.ts` 那一处要先重新设计启动流程才能修。
- 操作：同上。
- 预期：表里这一行的处理写"另开需求"和一句原因。另外两处照常在本轮修完。这一处出现在完成简报的"另开需求"清单里。

**用例（搜到的位置其实不受影响）**
- 场景：同主路径，但 `settings.ts` 调用 `readStore` 之前已经自己检查过文件能不能读。
- 操作：同上。
- 预期：表里这一行的处理写"不用修"，理由带那段检查代码的 `文件:行号`。这一处不改。

## 约束
- **什么时候搜**：`/revise` 诊断定出根因、并且决定留在 `/revise` 修的时候，在动手修之前搜一次同根因位置。诊断结论是转 `/prd` 的不搜。
- **什么算同根因位置**：满足下面任意一条。
  - 调用了出问题的那段代码，或读了出问题的那份数据，会受同一个缺陷影响。
  - 没有调用它，但在别处独立写了同样的错误写法。
  同一个文件里的另一种缺陷不算。
- **搜哪里**：出问题的代码所在的整个仓库；多仓库工作区里，搜每个用到这段代码的代码仓库。
- **每个位置都要读代码判断**：搜到的每个位置都读过代码再下结论，结论带 `文件:行号` 和一句理由。处理分三种：一起修、不用修、另开需求。
- **怎么通报**：诊断结果里增加一节，写法如下。没有搜到其他位置时，这一节只写一行"同根因位置：搜过了，没有其他位置（搜了：<函数名或关键词>）"。

  ```
  ## 同根因位置
  根因：<一句话>
  搜了：<函数名或关键词>

  | # | 位置 | 类别 | 处理 | 理由 |
  |---|---|---|---|---|
  | 1 | <文件:行号> | 调用处 / 同样写法 | 一起修 / 不用修 / 另开需求 | <一句话> |

  共 N 处：一起修 A 处，不用修 B 处，另开需求 C 处。
  ```
- **通报后直接修**：通报完不等用户确认，把用户报的那一处和所有"一起修"的位置在同一轮修完。
- **什么时候停下问**：某个位置有不止一种合理修法、而且不同修法下用户看到的结果不一样时，只就这一处停下问用户；问完后和其他位置在同一轮修完。
- **什么时候另开需求**：某个位置要新增设计、或者要改变用户原本想要的行为才能修时，处理写"另开需求"，本轮不改它；其他位置照常修。
- **一起修的范围算用户要求之内**：处理为"一起修"的位置属于本次修复必须改的范围，Claude 改它们不需要另外请用户批准。代码纪律里"用户要求之外的改动先经用户批准"的规定，对同根因位置不适用。
- **每个位置都有测试**：每个"一起修"的位置至少有一条先失败、修完后通过的测试；审查逐个位置核对。
- **同一次提交**：用户报的那一处和所有"一起修"的位置在同一次本地提交里。
- **能不能跳过三个子代理直接修**：现有的判断条件"只改 1 个文件、不超过 10 行"，按全部"一起修"的位置合计。
- **用户一次报了多处**：先各自定根因；根因相同的合并成一个，只搜一次；根因不同的各搜各的。
- **子代理干活时发现表外的同根因位置**：写实现的子代理不自己改，在报告里写出位置和理由；Claude 读代码核实后补进表里，在本轮修完。
- **完成简报**：增加一行"同根因位置：共 N 处，修了 A 处，不用修 B 处，另开需求 C 处"；数字只算表里的位置，用户报的那一处不算在内；另开需求的逐条列出位置和原因。
- **用词**：`/revise` 的说明和输出里统一叫"同根因位置"和"用户报的那一处"。

## 验收
- [ ] `/revise` 决定留在本流程修时，动手前搜了同根因位置；结论是转 `/prd` 时没有搜。
- [ ] 调用处和同样写法两类位置都能被搜出来；同一个文件里的另一种缺陷没有被列进来。
- [ ] 搜的是整个仓库；多仓库工作区里每个用到这段代码的代码仓库都搜了。
- [ ] 表里每一行都有 `文件:行号`、类别、处理和理由，处理只有"一起修 / 不用修 / 另开需求"三种。
- [ ] 诊断结果里有「同根因位置」一节，格式和约束里的一致；没有其他位置时只写一行，并写明搜了什么。
- [ ] 通报之后没有等用户确认就开始修。
- [ ] 只有"多种修法、用户看到的结果不同"的位置触发了提问，而且只问那一处。
- [ ] 要新设计或改变原有期望行为的位置标成"另开需求"，本轮没有改它，其他位置照常修完。
- [ ] 修"一起修"的位置时，没有出现"这是范围外改动，要不要处理"之类的提问。
- [ ] 每个"一起修"的位置至少有一条测试，审查报告逐个位置给了结论。
- [ ] 用户报的那一处和所有"一起修"的位置在同一次本地提交里。
- [ ] 判断能不能跳过三个子代理时，文件数和行数是按全部"一起修"的位置合计的。
- [ ] 用户一次报多处时，相同根因只搜了一次，不同根因各搜了一次。
- [ ] 写实现的子代理报告了表外的同根因位置后，Claude 核实并在本轮修完，子代理自己没有改。
- [ ] 完成简报里有"同根因位置"那一行，另开需求的逐条列出。
- [ ] `/revise` 的说明和输出里没有"兄弟位点""主位点"。

## 验证路径
1. 准备一个项目：`readStore` 有 3 个文件调用，另有 1 个文件写了同样的错误判断，其中一个调用处已经自己做过检查。
2. 运行 `/revise`，只报 1 个调用处的症状 → 诊断结果的「同根因位置」表有 4 行：2 行"调用处 / 一起修"，1 行"同样写法 / 一起修"，1 行"调用处 / 不用修"。
3. 观察 Claude 的下一步 → 没有提问，直接开始写测试。
4. 修复完成后看提交 → 一次提交里包含用户报的那一处和 3 个"一起修"位置的改动，各有测试；做过检查的那一处没有改动。
5. 看完成简报 → 有"同根因位置：共 4 处，修了 3 处，不用修 1 处，另开需求 0 处"。
