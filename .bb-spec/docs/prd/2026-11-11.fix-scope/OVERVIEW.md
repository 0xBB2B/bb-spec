# 同一个根因一次查全、一次修完

## 背景与问题
用 bb-spec 修问题时，一个根因常常牵连好几处代码。现在 `/revise` 只修用户报的那一处，其他位置要等修完、提交之后才在简报末尾提一句"顺带发现……要不要处理"。用户每回答一次"一起修"，就要再跑一轮修复、全量测试、验收和 PR。

2026-11-10 在 one-company 项目里有两次实际经过：

- 读授信记录的函数把"读不出来"当成了"没有记录"。这个函数有 8 处调用。第 1 轮只改了启动弹窗；修完才报设置页等 4 处；第 2 轮修完又报守护进程 4 处。前后三轮，开了 3 个 PR。
- 解读失败后给主代理的建议写错了。第 1 轮修了 1 处，审查当场发现另外 3 处同样的问题，简报却写"属于范围外的发现，没有改"。之后又分几轮修，共开了 4 个 PR，其中一个只为补一条测试。

原因有四个：

1. `/revise` 诊断时不会自己去搜同一个根因牵连的其他位置。
2. 规则只说"用户要求之外的改动先经批准"，没说同根因的其他位置算不算用户要求之内，结果它们被当成范围外，放到最后才问。
3. 审查子代理只看这次改过的文件；它指出的测试缺口没人负责当轮补上。
4. 和这次问题无关的发现，一件一件零散地问，每件单独走一个 PR。

## 目标
- 同一个根因牵连的所有位置，在一轮修复里全部查出来、全部修完。
- 审查每指出一个问题，同时给出别处同样的问题；它指出的测试缺口在当轮补上。
- 和这次问题无关的发现，在收尾时合成一张清单，用户一次选完；选中的在当前分支修完，进同一个 PR。

## 非目标
- 不在实施计划（plan）里增加"注意事项"一栏。它只影响 `/exec` 阶段，之后另开需求做。
- 不把推送前的代码审查（ocr）提前到修复阶段。它查出的问题本来就交给 `/revise`，`/revise` 会搜同根因位置，已经能一次修全。
- 不改用户自己的全局 `~/.claude/CLAUDE.md`。它是用户的私有文件，不随插件交付。
- 不管没有走 `/exec`、`/revise`、`/git-push` 的普通对话里 Claude 怎么处理顺带发现的问题。
- 不让审查子代理把整个分支或整个仓库通读一遍，它只在指出问题时去搜同类位置。

## 依赖与交付顺序
01 → {02, 03 可并行}。02 和 03 都要用到 01 定下的"同根因位置"的判定方法。

## 整体验证路径
1. 准备一个项目：函数 `readStore` 把"文件读不出来"当成"没有记录"，有 3 个文件调用它；另有一个文件自己写了同样的错误判断；再放一个和它无关的小问题（某个测试传了早已不存在的选项）。
2. 运行 `/revise`，只报其中 1 个调用处的症状 → 诊断结果里出现「同根因位置」表，列出另外 2 个调用处和那个同样写法的文件，每行有 `文件:行号` 和理由；Claude 不停下等确认，直接开始修。
3. 修复完成 → 用户报的那一处和表里 3 个位置都改了，每个位置至少有一条测试，在同一次提交里；完成简报写"同根因位置：共 3 处，修了 3 处，不用修 0 处，另开需求 0 处"。
4. 审查子代理的报告里，每条问题下面都有"同类位置"一行；它指出的测试缺口已经补上，完成简报的"待解决"里没有测试缺口。
5. 完成简报之后弹一次窗，问那条无关发现处不处理 → 选"全部处理"，Claude 在当前分支修掉它，没有新开分支。
6. 运行 `/git-push` → 推送之前如果有新冒出来的无关发现，再弹一次窗；合并之后的简报里没有"还有几件事要不要处理"。

## 决策记录
- **同根因位置通报后直接全修，不等确认**（用户 2026-11-11 选定）。否掉了"每次都停下确认"：两次实际经过里用户每次的回答都是"一起修"，多停一次只是多等一次。只有某一处需要用户做取舍时才停下问那一处。
- **同根因位置算本次修复范围之内**（用户 2026-11-11 选定方案 B）。否掉了"只给 `/revise` 加搜索"（方案 A）：它解决不了"搜到了却被划到范围外"，第二次实际经过的第 1 轮就是这种情况。
- **测试缺口当轮补不了时停下问用户**（用户 2026-11-11 选定）。否掉了"写明原因后留在待解决"：那样缺口可能一直留着，或者像之前那样事后单独开一个 PR 来补。
- **无关发现在 `/exec`、`/revise` 收尾和 `/git-push` 推送前三个环节都问**（用户 2026-11-11 选定）。否掉了"只在推送前问一次"：那样选中的项要在推送环节再走一轮修复和全量测试。
- **无关发现超过 4 条时，弹窗只给"全部处理 / 都不处理"，挑几条在"其他"里填编号**。提问工具一个问题最多 4 个预设选项，`/git-push` 的代码审查结果已经用这种做法，这里保持一致。
- **被 `/exec`、`/git-push` 调用的 `/revise` 自己不弹无关发现的窗，把清单交回调用它的环节一起问**。这一条是 Claude 定的：否则一次推送里用户会被内层和外层各问一遍。
- **和这次问题无关的安全性、鲁棒性、性能问题也只记进清单，不直接改**（用户 2026-11-11 选定）。代码纪律原有"安全性 / 鲁棒性 / 性能修复可以直接改"的例外，和"无关发现只记不改"冲突；例外收窄到这次改动涉及的代码。否掉了"保留例外、无关的也直接改"：那样改动范围会悄悄变大，子代理直接改时也不一定有测试。
- **"同一次提交"在多仓库工作区里是每个仓库各一次**（用户 2026-11-11 选定）。一次 git 提交不能跨仓库，`/revise` 原有规则也是各仓库分别提交。
- **"兄弟位点""主位点"改叫"同根因位置""用户报的那一处"**。原来的叫法是生造词，用户要求文档用普通人一次能读懂的话。
- **不标破坏性变更，按小版本发布**（用户 2026-11-11 选定）。使用者不用改任何配置或用法，只是修得更全。
- **否掉"推送前的代码审查提前到修复阶段"**：它查出的问题本来就交给 `/revise`，有了同根因搜索就能一次修全，提前跑只是多跑一遍。
- **否掉"这次一起做实施计划的注意事项栏"**：两次实际经过都发生在 `/revise`，那时没有实施计划，注意事项栏帮不上；它另开需求做。
- **质疑结论**：值得做。两次实际经过各多花了 2～3 轮全量测试和真实模型验收（会话里记录验收一次 1 小时以上）。没有更便宜的替代：靠用户每次手动提醒"把同类的都搜出来"正是现在的做法。
