# 每一轮改完原型后切到原型页并刷新

## 背景与问题

出原型时，用户每提一次修改意见，AI 就改出一个新版本。现在的规程规定：同一个原型文件，主对话在一次对话里只用 `open` 命令在浏览器里打开一次，之后每一轮只提醒用户"刷新已经打开的页面"。

用户的反馈是：每次改完新版本浏览器都不会弹出来，得自己去找到旧页面、手动刷新才能看到最新版本，很不方便。

如果改成每轮都执行 `open`，又会回到上一版要解决的问题：对同一个文件每执行一次 `open`，Chrome 就新开一个标签页，不会刷新已经打开的那个。实测：对同一个测试文件连续执行 3 次 `open`，Chrome 里出现了 3 个相同的标签页；用户的 Chrome 里也同时开着同一个原型文件的 2 个标签页。

## 目标

- 每一轮原型改完、需要用户看页面时，浏览器自动切到原型页并显示最新版本，用户不用手动刷新
- 原型页已经开着时，标签页数量不增加
- 同一轮里最多做 1 次

## 非目标

- 不支持 Chrome 和 Safari 以外的浏览器切换和刷新已有标签页：其他浏览器照旧新开标签页
- 不关闭用户已经开着的、同一个原型文件的多余标签页
- 不让原型页面自己检测文件变化并自动刷新
- 不改对比（`--compare`）模式的做法
- 不改原型子代理的报告格式，包括「需要用户看页面」一行的填法

## 依赖与交付顺序

单一子需求，无依赖。

## 整体验证路径

1. 读 `/prototype` 规程「出原型」第 5 步 → 展示原型的条件是"这一轮原型文件改过、最后一份报告写'是'"，时机是这一轮交回给用户之前；搜不到"提醒用户刷新"和"只看主对话自己在本次对话里执行过的 `open`"。
2. 在 Chrome 里已经开着原型文件时，让规程里展示原型的那一步跑一次 → Chrome 切到这个标签页并刷新，内容是最新版本，这个文件的标签页数量不变。
3. 关掉这个标签页后再跑一次 → 新开 1 个标签页，内容是最新版本。

## 决策记录

- **质疑结论**：值得做。用户每改一版都要手动刷新，频率很高。
- **为什么先找已开着的标签页、切过去刷新**：用户提出。实测每次 `open` 都新开标签页（同一文件 3 次 `open` 出现 3 个标签页），只靠 `open` 做不到"不堆标签页"。实测在用户的 Chrome 里：没有开着时新开 1 个；把文件改成 v2 后找到这个标签页、切过去刷新，标签页仍是 1 个，标题变成 v2。
- **只支持 Chrome 和 Safari**：这两个浏览器在 macOS 上能被脚本列出标签页、切换、刷新；Firefox 没有这种接口。用户默认浏览器是 Chrome。Safari 这条路还没实测。
- **找不到或出错时新开**：第一次运行时 macOS 会弹窗问是否允许终端控制浏览器，用户可能拒绝；同时开着多个 Chrome（例如浏览器调试工具自己启动的 Chrome）时，脚本可能连到别的 Chrome 而找不到标签页，实测遇到过。这些情况下退回新开一个标签页，用户至少能看到最新版本。
- **被否决：每轮直接 `open`**：会一轮多一个标签页。
- **被否决：让页面自己检测文件变化并刷新**：要改所有原型共用的外壳；直接打开的本地 HTML 文件，浏览器一般不允许页面读取自己所在的文件（推测，没有验证）。
- **"一轮"的界定**：从用户发一条消息，到主对话把结果交还给用户为止。用户提出："AI 在一次对话里对原型进行自己修改不需要反复弹窗"。
- **原型文件这一轮没改过就不展示**：用户选定。例如用户只问了一句"为什么按钮放这里"，原型没有新版本。被否决的是"报告写'是'就展示"：没有新版本时也会打扰用户。
- **保留原有的不展示情况**：报告写"否"、对比模式、交回确认内容清单的那一轮都不展示；出原型模式下报告漏写「需要用户看页面」时按"是"处理。理由和上一版相同。
- **不标 BREAKING CHANGE**：`/prd`、`/revise` 调用 `/prototype` 的方式和参数都不变。
