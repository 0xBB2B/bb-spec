# 压缩主窗口的上下文

## 背景与问题
用 bb-spec 做一个需求，主窗口（用户直接对话的那个 Claude 会话）会被细节塞满。统计了 5xsdk 和 one-company 两个项目 2026-11-10 到 11-11 的 5 个会话：4 个涨到 93–97 万 token，3 个在约 96 万时被迫自动压缩，前面和用户对齐过的内容被摘要掉。一个需求内部就可能压缩 2 次，靠"做完一个需求就 `/clear`"解决不了。

占用按"进入模型的文字字符数"算，大户是这几样：

| 来源 | 占比（5 个会话的范围） | 实测细节 |
|---|---|---|
| 主窗口自己用命令读代码、搜索 | 22%–33% | 每个会话 155–351 次；其中读源码和搜索占 52%，读 PRD 和 plan 等文档 17%，看测试和脚本输出 16%，看 `git diff` 11% |
| 子代理往返 | 20%–34% | 交回报告平均 3,000–5,000 字符，最长 19,299；报告模板本身只有约 10 行 |
| skill 正文注入 | 2%–12% | 一个会话里 `git-push` 正文注入 5 次、`revise` 4 次 |
| 主窗口循环等后台脚本 | 约 1%–8% | 4 个会话各 109–261 次；连同每次的思考，在一个会话里占模型输出的 18% |

## 目标
- 子代理交回主窗口的报告：全部通过时不超过 800 字符，有问题时不超过 3,000 字符，调查报告不超过 2,000 字符。
- `git-push`、`revise` 两个 skill 的正文各不超过 12,000 字节，`prd` 不超过 18,000 字节。
- 主窗口把调查交给子代理，只收结论和 `文件:行号`。
- 主窗口不循环等待后台脚本，超过 2 分钟的脚本交给子代理跑。

## 非目标
- 不改 `/plan`、`/doc-update`、`/prototype` 里主窗口读东西的方式：本次只管 `/prd`、`/revise`、`/exec`。
- 不拆 `exec`、`prototype`、`plan` 等其他 skill 的正文：先看三个最大的效果。
- 不处理 codegraph 提示钩子：它不属于 bb-spec，用户没有同意纳入。
- 不改模型的思考量：思考会留在上下文里，但它由 Claude Code 的设置决定。
- 不保证等脚本期间屏幕一直显示工作中：子代理在后台跑，主窗口的回合会结束。
- 不做机械的长度拦截：报告超长时主窗口照常使用，上限靠子代理定义里的规定保证。

## 整体验证路径
1. 在一个有测试的项目里用本分支的插件跑完一个小需求（`/prd` → `/plan` → `/exec` → `/git-push`）→ 流程全部走通，PR 合并。
2. 用统计脚本读这次会话的记录文件 → 每份子代理交回报告的字符数：全部通过的不超过 800，有问题的不超过 3,000，调查报告不超过 2,000。
3. 同一份记录里数主窗口带 `sleep` 的循环等待命令 → 0 次。
4. 同一份记录里看每次注入的正文 → `git-push`、`revise` 各不超过 12,000 字节，`prd` 不超过 18,000 字节。
5. 对比改动前同规模需求的会话 → 主窗口上下文峰值下降（具体降多少没有预设目标，记录实测值）。

## 决策记录
- **质疑结论**：值得做。证据是 5 个会话的统计，4 个涨到 93–97 万 token。更便宜的替代只有"合并一个需求就 `/clear`"，它治不了单个需求内部的膨胀（一个需求就压缩了 2 次）。
- **报告上限定 800 / 3,000 / 2,000 字符**：按现有模板的长度估的，没有实测过够不够用。否决了"不定数字、只规定按模板写"：没有可检查的标准，实际长度容易漂回去。否决了更严的 400 / 1,500：有问题时主窗口更常需要再读细节文件，读文件本身也占上下文。
- **报告超长时照常使用**：报告已经进了主窗口，退回重写只会再多占一份。
- **只交调查，主窗口保留读文档、定点读、看 `git diff` 验收**：占用的大头是调查（读取量的 52%）。验收和文档是主窗口做决定的依据，交出去等于没人把关。否决了"连验收一起交"和"都不交、只限制每次读多少"：后者因为单次读取平均只有约 1,500 字符，问题在次数多。
- **子代理的结论算"读过代码"，关键结论主窗口定点核对**：子代理可能读错，定点读一段只花几百字符，能挡住错误结论进 PRD 或修复方案。
- **交出门槛定为"不知道答案在哪，或预计读 3 个以上源码文件"**：1–2 个文件时，派工加交回的开销（约 3,000 字符）比自己读还大。3 这个数没有数据支撑。
- **调查和跑脚本都新增 bb-spec 自己的子代理，用 sonnet**：报告格式和上限写在子代理定义里才限得住；Claude Code 自带的 Explore 实测报告平均约 17,000 字符，格式不归 bb-spec 管。sonnet 读错有主窗口定点核对挡着；等脚本不需要强模型，是用户指定的。
- **跑脚本的子代理自己启动脚本**：实测后台脚本 65 条里 55 条是测试，整件交出去比"主窗口启动、子代理盯进程"简单。
- **接受等脚本期间回合结束**：这改掉了 `2026-11-02.wait-background-scripts` 的两条规定——Stop 钩子提示里"用前台循环等"的那句，和 `/git-push` 用前台循环等 ocr。用户确认可以接受 Vibe42 提前报完成；等别的子代理时本来就是这样。钩子保留，改成提醒主窗口把脚本交给子代理。
- **2 分钟内能跑完的脚本主窗口前台直接跑**：Bash 默认超时就是 2 分钟，短脚本派子代理的开销比直接跑大。
- **卡死按"没有输出"判，不按总时长判**：用户指出脚本慢可能是模型限额（429）或网络原因，只要还有输出就不算卡死。连续 30 分钟没有任何新输出才算。
- **只拆 `git-push`、`prd`、`revise`**：这三个最大（约 21–24KB），且重复注入最多。风险是拆出去的内容模型可能漏读，没有实测过，放在整体验证里观察。
- **不算破坏性变更**：没有删除或改名公开接口、命令、配置项，使用者不用迁移，只是等脚本时回合会结束。用户确认按普通 feat 发版。
- **`/git-push` 的全量测试也按 2 分钟分界**：最初写的是全量测试一律交子代理，和 2 分钟分界对不上。几秒就能跑完的项目派子代理比直接跑开销大，用户确认以 2 分钟分界为准；ocr 审查一次可能超过 10 分钟，一律交子代理。
- **`prd` 的上限放宽到 18,000 字节**：按 12,000 字节做出来，`prd` 被拆成 12 个小文件（最小 430 字节），每次都要走的步骤也搬了出去，每次调用多读约 12 次文件，总读入量并不减少。实测 `prd` 一个会话只注入 1 次，瘦身的收益来自重复调用，它基本吃不到。用户确认 `prd` 只搬落盘时才用的内容。
