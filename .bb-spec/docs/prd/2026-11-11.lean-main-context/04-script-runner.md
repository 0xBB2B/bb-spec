# 脚本交给子代理跑

## 用户故事
### P0：作为用 bb-spec 做需求的用户，我想要耗时的脚本由子代理去跑和等，以便主窗口不被几百次循环等待占满

**用例（主路径：全量测试）**
- 场景：`/git-push` 走到跑全量测试这一步，全量测试要 12 分钟。
- 操作：主窗口派跑脚本的子代理，给出命令和工作目录。
- 预期：子代理自己启动测试、等到结束，交回不超过 800 字符的报告：通过、用例数量、耗时、完整输出文件的路径。等待期间主窗口没有执行任何循环等待命令，主窗口的回合可以结束；报告交回后主窗口接着往下走。

**用例（脚本失败）**
- 场景：全量测试有 2 条失败。
- 操作：子代理交回报告。
- 预期：报告不超过 3,000 字符：通过和失败的数量、2 条失败用例的名字和错误信息、完整输出文件的路径。主窗口不用读完整输出就能决定下一步。

**用例（短脚本）**
- 场景：`/exec` 里主窗口要跑一个 plan 自己的测试文件，预计 20 秒。
- 操作：主窗口跑这个测试。
- 预期：主窗口用前台方式直接跑一次拿到结果，不派子代理。

**用例（卡死）**
- 场景：子代理启动的脚本卡住，连续 30 分钟没有任何新输出。
- 操作：子代理发现满 30 分钟没有新输出。
- 预期：子代理停掉自己启动的这个脚本，交回报告：判定为卡死、已经运行多久、最后几行输出、完整输出文件的路径。

**用例（慢但有输出）**
- 场景：脚本因为模型请求限额反复重试，已经跑了 50 分钟，每隔几分钟打印一行重试日志。
- 操作：子代理继续等待。
- 预期：子代理不判定卡死，一直等到脚本结束再报告。

**用例（主窗口自己把脚本放到了后台）**
- 场景：主窗口用后台方式启动了 `npm test`，然后准备结束回合。
- 操作：Stop 钩子发现这条没提示过的后台命令。
- 预期：屏幕出现一次 Stop hook feedback 提示。主窗口不循环等待，直接结束回合，脚本结束时由系统通知主窗口；之后同类脚本主窗口交给子代理启动。

**用例（常驻服务）**
- 场景：主窗口要启动 dev server 给用户看页面。
- 操作：主窗口用后台方式启动 `npm run dev`。
- 预期：主窗口自己启动，不派子代理，服务一直运行。

## 约束
1. 插件新增一个跑脚本的子代理，使用 sonnet 模型：按主窗口给的命令和工作目录自己启动脚本，等到脚本结束，交回报告。除了运行给定的命令和写输出文件，不改项目文件，不操作 git。
2. 脚本的完整输出写进缓存目录下的一个文件，报告里给出它的完整路径。
3. 脚本成功 → 报告不超过 800 字符：结果、退出码、耗时、主窗口派工时要求摘取的内容（如用例数量）、输出文件路径。
4. 脚本失败 → 报告不超过 3,000 字符：退出码、失败条目的名字和错误信息、输出文件路径；通过的条目只报数量。
5. 主窗口要跑会自己结束的脚本（测试、构建、类型检查、审查）时：预计 2 分钟内能跑完 → 主窗口用前台方式直接跑；预计超过 2 分钟、或拿不准 → 派跑脚本的子代理。
6. 主窗口不执行循环等待脚本结束的命令。
7. 常驻服务（dev server、watch、`tail -f`）由主窗口自己用后台方式启动，不派子代理。
8. 子代理等待期间，脚本连续 30 分钟没有任何新输出 → 判定卡死：停掉自己启动的这个脚本和它带起来的进程，不动别的进程，报告"卡死"、已运行时长、最后几行输出、输出文件路径。
9. 脚本持续有新输出 → 不判定卡死，不设总时长上限，等到脚本结束。
10. 脚本启动不了（命令不存在、目录不存在）→ 子代理不重试，报告启动失败和错误信息。
11. 子代理等待期间，主窗口可以做不依赖这次结果的事，没有可做的就结束回合；报告交回后继续。
12. Stop 钩子的提示文字改成下面这样，其余行为（每条命令每个会话只提示一次、只管运行中的 shell 类型后台命令、出错时一律放行）保持原样：
    ```
    后台命令还在运行：
    - <任务编号>: <命令>
    会自己结束的脚本（测试、构建、审查）：不要循环等待，直接结束回合，它结束时系统会通知你；之后这类脚本交给跑脚本的子代理启动。
    常驻服务（dev server、watch、tail -f）：不用等。全部是常驻服务时，直接结束回合。
    ```
13. `/git-push` 的 ocr 审查一律交给跑脚本的子代理（一次审查可能超过 10 分钟），审查结果文件路径随报告交回，主窗口照原来的规则逐条读代码核实；`/git-push` 的全量测试按约束 5 的 2 分钟分界处理。
14. 插件说明（`plugin.json`、`marketplace.json`）和 README 里的子代理清单写上跑脚本的子代理，钩子说明和新的提示文字一致，数量和实际一致。

## 验收
- [ ] 对应约束 1：跑脚本子代理的定义文件存在，模型为 sonnet，写明自己启动、等到结束、不改项目文件、不操作 git。
- [ ] 对应约束 2、3、4：定义文件里有输出文件的写法、800 和 3,000 两个上限、成功和失败两种报告各含哪几项。
- [ ] 对应约束 5、6、7：`/exec`、`/revise`、`/git-push` 的规则里写明 2 分钟的分界、主窗口不循环等待、常驻服务主窗口自己启动。
- [ ] 对应约束 8、9：定义文件里写明"连续 30 分钟没有任何新输出"才算卡死、卡死后只停自己启动的脚本、有输出就一直等。
- [ ] 对应约束 10：定义文件里写明启动失败不重试、直接报告。
- [ ] 对应约束 11：`/exec`、`/revise`、`/git-push` 的规则里写明等待期间可以结束回合。
- [ ] 对应约束 12：给钩子输入一条新的运行中 shell 任务 → 输出文本和约束里的格式逐字一致；同一会话同一编号第二次输入 → 无输出；非 shell 类型、缺字段、没有 `jq` → 无输出、退出码为 0。
- [ ] 对应约束 13：`/git-push` 的 ocr 审查一步写明派跑脚本的子代理并交回审查结果文件路径，全量测试一步写明按 2 分钟分界处理，文中没有前台循环等待的写法。
- [ ] 对应约束 14：两份插件说明和 README 里出现跑脚本的子代理，子代理数量和 `agents/` 目录下的文件数一致，钩子说明写的是新的行为。

## 验证路径
1. 用本分支的插件在一个全量测试超过 2 分钟的项目里跑 `/git-push` → 会话记录里主窗口派了跑脚本的子代理，交回报告不超过 800 字符（有失败时不超过 3,000）。
2. 同一份记录里数主窗口带 `sleep` 的循环等待命令 → 0 次。
3. 打开报告里的输出文件路径 → 文件存在，内容是完整的测试输出。
4. 让子代理跑 `sleep 2400`（没有任何输出）→ 约 30 分钟后交回"卡死"报告，`sleep` 进程已经不在。
5. 让子代理跑一个每 5 分钟打印一行、总共 40 分钟的脚本 → 子代理等到结束，报告成功。
6. 主窗口自己后台启动一个 3 分钟的脚本后结束回合 → 屏幕出现一次新的提示文字，主窗口没有循环等待，脚本结束后收到系统通知。
