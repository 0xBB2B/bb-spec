# 子代理报告限长

## 用户故事
### P0：作为用 bb-spec 做需求的用户，我想要子代理只把结论交回主窗口，以便主窗口不被过程细节塞满

**用例（主路径：全部通过）**
- 场景：`/exec` 派测试工程师子代理写 8 个测试用例，全部按预期失败（正确的 Red 状态），没有方案问题。
- 操作：子代理写完测试、跑完，交回报告。
- 预期：报告只有模板里的几项，每项一行：测试文件路径、用例数量、Red 状态、细节文件路径、方案问题写"无"。全文不超过 800 字符。每个用例的结果、每条约束对应哪个用例，写在细节文件里。

**用例（有问题）**
- 场景：实现工程师子代理跑完，14 个测试文件里有 1 个文件失败 1 条。
- 操作：子代理交回报告。
- 预期：报告写明通过和失败的数量，只展开失败的那 1 条（用例名、错误信息、位置）。通过的 13 个文件只报数量。全文不超过 3,000 字符。

**用例（审查全部合规）**
- 场景：合规审查子代理核对 12 条约束，全部合规，没有其他问题。
- 操作：子代理交回报告。
- 预期：报告只写总结那一行的各项数量和细节文件路径，不逐条列出 12 条合规项。全文不超过 800 字符。

**用例（报告超长）**
- 场景：某个子代理交回了 4,500 字符的报告。
- 操作：主窗口收到报告。
- 预期：主窗口照常使用这份报告往下走，不要求子代理重写。

## 约束
1. 下面每个子代理的定义里都写明报告长度上限：测试工程师、实现工程师、合规审查、分支规范自查、网页用例执行。
2. 报告里没有失败、违规、遗漏、方案问题时（全部通过）→ 报告不超过 800 字符，只按模板每项一行，不加模板以外的小节。
3. 全部通过时，通过或合规的条目只报数量，不逐条列出。
4. 报告里有失败、违规、遗漏或方案问题时 → 只展开有问题的条目，通过的只报数量，全文不超过 3,000 字符。
5. 字符数按报告正文算，标点和空白都算，不算系统在报告外面加的说明文字。
6. 不在报告里展开的细节（每个用例的结果、约束和用例的对应关系、完整的测试输出、逐文件的改动说明）写进缓存目录下 `reports/` 里的一个文件，报告里用一行给出它的完整路径。没有细节可写时不建文件，也不写这一行。
7. 下面几项无论长短都必须留在报告正文里：新建或改动的文件路径；「方案问题」小节（没有就写"无"；只要求报告模板里有这一节的子代理，即测试工程师、实现工程师）；有问题条目的 `文件:行号`。
8. 主窗口收到超过上限的报告 → 照常使用，不退回重写。
9. 派出子代理的流程（`/exec`、`/revise`、`/git-push`、`/test-webview`）在自己收尾时，删掉本次产生的细节文件。
10. 主窗口需要报告里没有的细节时，按路径读细节文件里需要的那一段，不整份读入。

## 验收
- [ ] 对应约束 1：五个子代理的定义文件里都能找到 800 和 3,000 这两个上限的规定。
- [ ] 对应约束 2、3：每个子代理定义的报告模板里，全部通过的写法是每项一行，通过或合规项只有数量。
- [ ] 对应约束 4：每个子代理定义里写明有问题时只展开有问题的条目。
- [ ] 对应约束 5：每个子代理定义里写明字符数的算法。
- [ ] 对应约束 6：每个子代理定义里写明细节文件放在缓存目录的 `reports/` 下、报告里给完整路径、没有细节时不建文件。
- [ ] 对应约束 7：每个子代理定义里写明保留文件路径和 `文件:行号`；测试工程师、实现工程师的报告模板里保留「方案问题」小节，其余三个子代理的定义写明这一节只在模板里有时才写。
- [ ] 对应约束 8：`/exec`、`/revise`、`/git-push` 的规则里写明超长报告照常使用。
- [ ] 对应约束 9：`/exec`、`/revise`、`/git-push`、`/test-webview` 的收尾步骤里写明删除本次的细节文件。
- [ ] 对应约束 10：`/exec`、`/revise` 的规则里写明按需读细节文件的一段。

## 验证路径
1. 用本分支的插件在一个有测试的项目里跑一次 `/exec`（至少 1 个 plan，Test、Impl、Review 都走到）→ 三份报告都交回，流程走通。
2. 读这次会话的记录文件，量每份交回报告的字符数 → 全部通过的不超过 800，有问题的不超过 3,000。
3. 打开报告里给出的细节文件路径 → 文件存在，里面有每个用例的结果。
4. `/exec` 结束后看缓存目录的 `reports/` → 本次产生的细节文件已删除。
