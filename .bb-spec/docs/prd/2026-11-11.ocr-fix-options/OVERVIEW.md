# ocr 审查的"修哪些"提问默认全部修复

## 背景与问题
`/git-push` 在本机装了 ocr（open-code-review，一个代码审查命令行工具）时，会跑一次 ocr 审查。Claude 逐条读代码核实，把成立的问题列进「建议修复」表并定级：🔴 是真实场景会触发、后果严重的；🔶 是会触发但后果有限的；🔷 是几乎碰不到或只影响可读性的。不成立的问题列进「不建议修」表。然后弹窗问用户修哪些。

现在弹窗的选项依次是「修全部 🔴🔶」（推荐）、「只修 🔴」、「建议项全修」、「都不修」。有三个问题：

- 默认推荐只修 🔴🔶。用户想把「建议修复」表里的问题一次修干净，每次都得手动选第三项。
- 选项不是按范围大小排的，范围最大的「建议项全修」排在第三。
- 「修全部 🔴🔶」和「建议项全修」名字相近，要读完才分得清哪个范围更大。

## 目标
- 默认推荐的选项修「建议修复」表里的全部条目。
- 选项按修的范围从大到小排，名字一眼能分出范围：全部、重点、核心。
- 每个选项后面的括号只写这次审查实际出现的等级。

## 非目标
- 不改「建议修复」表、「不建议修」表和总结行的内容与格式。
- 不改成立与否的判断标准和 🔴🔶🔷 的定级标准。
- 不改弹窗的问题文字。
- 不规定每个选项下面那行说明文字怎么写，仍由 Claude 按当次情况写。
- 不改「其他」里输入编号的用法，「不建议修」表里的条目仍然只能靠输入字母编号拉回来修。
- 不改选完之后的处理：选中的条目一次交给 `/revise` 修，修完不重跑 ocr。

## 依赖与交付顺序
单一子需求，无依赖。

## 整体验证路径
1. 在一个装了 ocr 的仓库里走 `/git-push`，审查核实后成立 🔴 1 条、🔶 2 条、🔷 1 条 → 弹窗选项依次是「全部修复（🔴🔶🔷）」（带推荐标记）、「只修重点（🔴🔶）」、「只修核心（🔴）」、「全不修复」。
2. 选「全部修复（🔴🔶🔷）」→ 4 条成立的条目全部交给 `/revise`，「不建议修」表里的条目没有交过去。
3. 换一次只成立 🔴 1 条、🔷 1 条的审查 → 选项依次是「全部修复（🔴🔷）」（带推荐标记）、「只修核心（🔴）」、「全不修复」。
4. 选「全不修复」→ 直接进入全量测试，没有调用 `/revise`。

## 决策记录
- **默认推荐改成全部修复**：用户在 2026-11-11 提出。质疑时指出代价：🔷 是几乎碰不到或只影响可读性的问题，默认全修会让每次推送多花修复时间，多花多少没有实测数据。用户仍要全修；不想修 🔷 时选「只修重点」即可，代价可控。
- **「全部修复」只指「建议修复」表**：用户在 2026-11-11 明确，「不建议修」表里的条目是误报或不值得修的，不算在「全部」里。
- **第四项叫「全不修复」**：用户在「都不修」和「全不修复」之间选了后者，和前三项的用词一致。
- **括号里按实际写**：用户在"每次固定写 🔴🔶🔷"和"只写这次实际出现的等级"之间选了后者，理由是更准确。代价是同一个选项的文字每次可能不同。
- **「只修重点」和「只修核心」范围相同时留「只修核心」**：只有 🔴 和 🔷、没有 🔶 时，两项都只修 🔴。用户看过原型后选了留「只修核心」。否掉了"一律留排在前面的"，因为那样会显示「只修重点（🔴）」，而 🔴 在选项里本来叫核心，名字和内容对不上。也否掉了"范围相同时一律留名字范围更窄的"，因为只有 🔴🔶 时会丢掉带推荐的「全部修复」。
- **没有先建 DESIGN.md**：这个弹窗由 Claude Code 绘制，颜色和排版不由本仓库决定。用户在 2026-11-11 决定这次不建，原型用外壳默认终端配色，只确认选项的文字、顺序和各种情况下剩哪几项。
- **功能名新起 `ocr-review`**：ocr 审查这一步是接入 PRD 流程之前加的，没有对应的功能名。
