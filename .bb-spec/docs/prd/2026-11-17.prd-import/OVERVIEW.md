# /prd 从现成需求文档导入

## 背景与问题
用户经常拿到别人写好的需求文档（同事、产品经理写的），希望用 bb-spec 实施。现在 `/prd` 的流程从对话开始：先复述问题，再质疑，再一个维度一个维度地问。用户执行 `/prd @某文档.md` 时，`/prd` 没有任何规则说明该怎么处理这份文档，结果全看模型当场怎么理解。

别人写的文档和对话里提的需求不一样，有四个隐患：

1. 作者不在场，文档里每一句都只是作者的说法，可能和现有功能冲突，也可能根本做不到。
2. 文档可能不符合 bb-spec 对 PRD 的要求：只写要什么、没写为什么；约束写成"要友好""要快"，没法写成测试；没写哪些事不做；把实现方式当成需求写。
3. 文档可能违反开发规矩。开发规矩有两个来源：项目根 `AGENTS.md` 的「项目约束」，以及 bb-spec 按技术栈生效的约束类 skill（比如 `database-constraints` 要求主键用应用层生成的 UUIDv7、删除用软删除）。
4. 整理过程中，原文某一条被删了、被改了，没人知道。

这些问题如果到实施时才由测试或审查发现，PRD、测试、实现都要返工。

## 目标
- 用户带一份或多份需求文档运行 `/prd` 时，原文的每一条都经过核查，并由用户逐条重新确认；冲突、做不到、不合规的条目在写 PRD 之前全部摊开，由用户裁决。
- 整理出的 PRD 符合 bb-spec 格式，原文没写到的维度（边界、出错处理等）照常补问。
- 原文每一条最后去了哪里（写成约束、写进非目标、删除、另开 PRD），记在 PRD 里，以后能查。

## 非目标
- 不新增命令。导入是 `/prd` 的一个入口，后面的落盘、`/plan`、`/exec` 与普通 `/prd` 完全相同。
- 不支持网页链接和 Word 文档。网页读取工具返回的是概括后的内容，保证不了每一条都覆盖到；读 Word 要依赖 bb-spec 之外的插件。
- 一次 `/prd` 只产出一份 PRD。原文含几个独立需求时，其余的以后另行运行 `/prd`。
- 不把原文复制进仓库，PRD 里也不链接原文；对照表只写文件名和章节作为出处。
- 不改 `/revise`。本分支 PRD 的修订照旧走 `/revise`。

## 子需求清单
| 序号 | 子需求 | 解决的子问题 | 优先级 |
|---|---|---|---|
| 01 | [读取原文并逐条核查](01-source-intake.md) | 原文怎么读、怎么拆成条目、每条和代码及开发规矩是否冲突 | P0 |
| 02 | [与用户逐条重新对齐](02-item-alignment.md) | 每条原文都要用户确认，有问题的条目逐条追问，原文漏写的维度补问 | P0 |
| 03 | [原文对照表](03-source-mapping.md) | 原文每条的去向记进 PRD，落盘后自检不漏条 | P0 |

## 依赖与交付顺序
01 → 02 → 03。02 用 01 产出的条目和核查结论出总表；03 记录的是 02 确定下来的去向。

## 整体验证路径
1. 准备两份原文：`a.md` 有两个章节，「订单导出」章节 4 条（一条"导出要快"、一条"主键用自增 ID"、一条"导出接口用 GET /export"、一条和现有代码已有能力重复），「登录改用验证码」章节 2 条；`b.md` 是补充说明，其中一条和 `a.md` 某条说法相反。
2. 运行 `/prd @a.md @b.md` → 步骤 1 列出拆分方案：「订单导出」「登录改用验证码」两个独立需求，各自包含哪些编号；用户挑「订单导出」。
3. 步骤 3 → 总表分批出现，每批不超过 5 行，每行有编号、出处、原文要点、核查结论、建议去向；"导出要快"标"写不成测试"，"主键用自增 ID"标"与约束类 skill 冲突"并引用规则原文，"GET /export"标"属于技术方案"，重复的那条标"现有代码已具备"并附 `文件:行号`，`b.md` 那条标"多份原文互相矛盾"。
4. 用户确认完全部批次 → 只对有问题的条目逐条追问；"主键"一条给出"按规矩改 / 保留原文写法"的选择；之后补问原文没写到的出错处理等维度。
5. 落盘后 → OVERVIEW「决策记录」里有原文对照表，`a.md`、`b.md` 每个编号都在，"登录改用验证码"的条目去向是"另开 PRD"，删除的条目都写了原因；步骤 8 自检通过。
6. 再运行 `/prd @a.docx` → 提示请导出成 Markdown 或 PDF 后停下，没有写任何文件。

## 决策记录
- **扩展 `/prd`，不新增命令**（用户 2026-11-17 选定方案 A）。问题只出在入口：输入从一句话变成一份文档，之后落盘、开分支、`/plan`、`/exec` 完全一样。否掉了"新增导入命令"：要么复制一份后续流程，要么再转交给 `/prd`，而 `/prd` 是新需求的唯一入口，两个入口的规矩迟早会改得不一样。
- **原文每一条都要用户重新确认，包括原文写得很清楚的**（用户 2026-11-17 提出）。原因：原文写得清楚，不代表它不和现有功能冲突、也不代表做得到。
- **先出总表逐行确认，再逐条追问有问题的条目**（用户 2026-11-17 选定）。否掉了"每条一问一答"：原文 30 条就要 30 轮以上，轮数太多容易让人疲劳而草草点头。
- **总表按原文章节分批，每批最多 5 行**（用户 2026-11-17 选定）。否掉了"一次出完整张表"：表长了容易看漏，也不符合用户"一组列表最多 5 条"的展示习惯。
- **原文对照表写进 OVERVIEW「决策记录」**（用户 2026-11-17 选定）。否掉了"不写进 PRD"：以后有人拿原文来问"第 5 条为什么没做"，只能在 PRD 里查到；不写的话这个信息对话结束就丢了。
- **原文含几个独立需求时拆成多份 PRD，这次只做一份**（用户 2026-11-17 选定）。每次 `/prd` 最后都在一个分支上自动开始实施，几件不相关的事放进同一个分支，PR 会混在一起，代码也没法按功能名查回各自的需求。否掉了"合成一份 PRD、各当一个子需求"。
- **原文里的技术方案逐条判断**（用户 2026-11-17 选定）。对外必须遵守的改写成行为约束；只是内部实现建议的删除并写原因。`/plan` 只读 PRD 和代码，看不到原文，必须遵守的东西只有写成约束才不会丢。否掉了"在 PRD 里加一节原样保留技术建议"：违反 PRD 只写行为的规定。
- **原文不符合 bb-spec 要求或开发规矩时，写进总表逐条处理，冲突一律由用户裁决**（用户 2026-11-17 选定）。开发规矩指 `AGENTS.md` 项目约束和 bb-spec 约束类 skill（用户 2026-11-17 确认）。否掉了"自动按规矩改写，只在总表注明"：原作者可能有意那样写（比如要兼容某个旧系统），自动改写会把它悄悄改掉。
- **只支持本地 `.md`、`.txt`、`.pdf`，可以一次带多份**（用户 2026-11-17 选定）。否掉了"支持网页链接"：拿不到原文就没法保证每条都覆盖。否掉了"只允许一份"：补充说明、会议纪要很常见，让用户先手动合并，矛盾就藏在合并过程里了。
- **原文读不出需求时停下**（用户 2026-11-17 确认）：文件不存在或为空 → 说明原因后停下；读出来但没有需求条目 → 告诉用户，并问要不要改用普通对话方式开始。
- **原文对齐完后，照常补问原文没写到的维度**（用户 2026-11-17 选定）。别人写的文档最常漏的是边界和出错处理，不补问就会在实施时被模型脑补。否掉了"只对齐原文写了的内容"。
- **新功能名 `prd-import`**：已有功能名里没有和"导入需求文档"相关的。
- **质疑结论**：值得做。用户本次提出了真实场景；不做的话冲突要到实施时才暴露，PRD、测试、实现都要返工。更便宜的替代"把原文一段段贴进对话里聊"容易漏条，也留不下原文每条的去向。
- **现状扫描只写原文条目的汇总，逐条明细放在步骤 3 总表里分批出**（用户 2026-11-17 在实施计划阶段选定）。否掉了"步骤 0 先逐条全列"：原文条目多时会先一次列出全部，再在总表里分批重复一遍，分批确认就失去了意义。
