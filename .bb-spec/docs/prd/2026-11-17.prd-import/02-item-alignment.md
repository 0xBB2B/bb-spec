# 与用户逐条重新对齐

## 用户故事
### P0：作为拿着别人写的需求文档来实施的用户，我想要原文每一条都经我确认，冲突和不合规的条目由我裁决，以便整理出的 PRD 是我真正要的、而且做得到

**用例（主路径）**
- 场景：导入的原文挑中的需求有 8 条原文条目，分属「功能」「接口」两个章节；其中 S3"主键用自增 ID"与 `database-constraints` 冲突，S5"导出要快"写不成测试，S6"导出接口用 GET /export"属于技术方案，其余 5 条无问题。
- 操作：进入步骤 3。
- 预期：先出「功能」章节的总表，不超过 5 行，每行有编号、出处、原文要点、核查结论（含依据）、建议去向；用户确认后再出下一批。全部批次确认完，依次追问 S3、S5、S6：S3 给出"按规矩改写成主键用 UUIDv7"和"保留原文写法"两个选项；S5 追问到能写成"什么输入 → 什么结果"；S6 先问它是不是对接方已经定死、必须遵守的。之后按维度检查表补问原文没写到的维度，比如导出失败时用户看到什么。

**用例（边界 / 异常）**
- 场景：一个章节有 7 条原文条目。操作：出这个章节的总表。预期：分成 5 行和 2 行两批出。
- 场景：用户在总表里推翻 S2 的建议去向，说"这条不做"。操作：确认这一批。预期：S2 的去向改成"非目标"，或按用户的说法改成"删除"并记下用户给的原因。
- 场景：用户对 S3 选了"保留原文写法"，并说"这个项目都要兼容老库，以后都这样"。操作：继续。预期：「决策记录」写明这条例外和原因，并提议在 `AGENTS.md` 加一条项目约束，用户同意后才加。
- 场景：S6 是对接方已经定死的接口格式。操作：用户确认"必须遵守"。预期：S6 改写成行为约束写进 PRD；如果用户说只是建议，S6 去向为"删除"，原因写"属于实现方式，由 /plan 根据现有代码决定"。

## 约束
1. 导入模式下，步骤 3 先出总表。总表按原文章节分批，每批最多 5 行；一个章节超过 5 条时拆成多批。每行有：编号、出处、原文要点、核查结论（含依据）、建议去向。
2. 建议去向只能是以下之一：写成约束、写进非目标、删除、另开 PRD。
3. 一批得到用户确认后才出下一批。用户推翻某行时，按用户的说法改这一行的去向；改成"删除"的，记下用户给的原因。
4. 每条原文条目，包括核查结论为"无问题"的，都要在总表里经用户确认；还有条目没确认时，不进入步骤 4。
5. 总表全部确认后，对核查结论不是"无问题"的条目逐条追问，一次追问一条。每条追问到能写成可验证的验收项，或者确定去向为止。
6. 核查结论为"与 `AGENTS.md` 项目约束冲突"或"与约束类 skill 冲突"的条目，给出按规矩改写后的写法，请用户在"按规矩改"和"保留原文写法"之间选。选"保留原文写法"时，「决策记录」写明这条例外和原因；用户表示这个例外以后要长期生效时，提议在 `AGENTS.md` 的「项目约束」增加一条；用户同意后先记下，到步骤 7 落盘时才写入（步骤 0~5 不写交付文件）。
7. 核查结论为"属于技术方案"的条目，先问用户它是不是对外必须遵守的（比如对接方已经定死的接口格式）。是 → 改写成用户能看到的行为约束写进 PRD；不是 → 去向为"删除"，原因写"属于实现方式，由 /plan 根据现有代码决定"。
8. 有问题的条目追问完后，按步骤 3 原有的维度检查表，补问原文没有写到的维度。
9. 写进 PRD 的约束按 bb-spec 的写法重写，每条都能写成"什么输入 → 什么结果"，不照抄原文措辞。

## 验收
- [ ] 约束 1：一个章节有 7 条时，总表分 5 行和 2 行两批出；每行五项齐全。
- [ ] 约束 2：总表里的建议去向只出现四种取值。
- [ ] 约束 3：前一批确认前不出现下一批；用户推翻的行按用户说法改了去向，改成"删除"的记下了原因。
- [ ] 约束 4：存在未确认的条目时，没有进入步骤 4。
- [ ] 约束 5：只追问核查结论不是"无问题"的条目，每轮只追问一条。
- [ ] 约束 6：开发规矩冲突的条目给出了"按规矩改 / 保留原文写法"两个选项；选保留时「决策记录」有例外和原因；用户没同意时 `AGENTS.md` 没有变化。
- [ ] 约束 7：技术方案条目先问是否必须遵守；"必须"的写成了行为约束，"不必"的去向为"删除"并带规定的原因。
- [ ] 约束 8：追问结束后，补问了原文没有写到的维度。
- [ ] 约束 9：PRD 里由原文转来的约束都能写成"什么输入 → 什么结果"；"导出要快"这类原文措辞没有原样出现在约束里。

## 验证路径
1. 用一份含 8 条条目（其中一个章节 7 条）的原文运行 `/prd`，挑中后进入步骤 3 → 第一批总表 5 行，确认后出第二批 2 行，再出下一个章节。
2. 在第一批里推翻一行，说"这条不做" → 这一行的去向按说法改了。
3. 全部确认后 → 只追问"主键用自增 ID""导出要快""GET /export"三条，一次一条。
4. "主键"一条选"保留原文写法"，说"以后都这样" → 弹出是否改 `AGENTS.md` 的提议；选"不改"后 `AGENTS.md` 没有变化，「决策记录」有这条例外。
5. "GET /export"答"只是建议" → 去向为"删除"，原因是"属于实现方式，由 /plan 根据现有代码决定"。
6. 追问结束 → 出现关于失败处理等原文没写到的维度的提问。
