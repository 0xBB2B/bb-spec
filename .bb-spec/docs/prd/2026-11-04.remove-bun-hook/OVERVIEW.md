# 删掉 bun 钩子

## 背景与问题
前端插件有一个钩子，在 Claude 跑 npm、yarn、pnpm 的安装命令时介入：项目里没有 lockfile 时弹权限确认窗，已有别的工具的 lockfile 时直接拒绝，而且拒绝时一律提示"改用 bun"。

这个钩子是按"强制 bun"设计的，和现在的规则冲突。现在的规则是：新项目优先建议 bun，但最终由用户决定；已有项目有什么 lockfile 就用什么工具。结果是：
- 项目只有 `yarn.lock` 时，Claude 照钩子的提示改用 bun，会多出第二份 lockfile，违反"禁止混用"。
- 为了让"用户能否决 bun"成立，钩子已经被改过一轮，又陆续查出新的问题。

这些选法前端规则里都已经写了，钩子只是多了一道和规则不一致的拦截。

## 目标
- 前端插件不再拦截、不再弹窗询问任何包管理器命令。
- 包管理器怎么选完全由前端规则决定：已有项目跟着它的 lockfile，新项目默认建议 bun、用户批准后才用。
- 插件说明里不再提这个钩子。

## 非目标
- 不改前端规则里已有的选法（已有项目按 lockfile 选工具，新项目默认 bun、经用户批准）。
- 不加别的防混用手段：混用只靠规则文字提醒，出了问题删掉多余的 lockfile 即可。
- 不处理 `npm-shrinkwrap.json` 的识别：钩子删掉后这个问题随之消失，规则里也没有要求识别它。

## 整体验证路径
1. 装上更新后的前端插件，在只有 `yarn.lock` 的项目里让 Claude 跑 `npm install` → 没有任何钩子提示或确认窗，命令照常执行（行为由 Claude 按规则自觉选择 yarn 来保证）。
2. 在没有 lockfile 的新项目里让 Claude 装依赖 → Claude 先按新技术清单列出包管理器，默认建议 bun，等用户批准；用户改用 npm 后直接执行，没有确认窗。
3. 查看 README 和插件描述 → 不再提 bun 钩子，被动 hook 的数量和实际一致。

## 决策记录
- **整个删掉，不保留"防混用"**：用户在 2026-11-04 看过两个方案后选择整个删除，原话："整个删掉，如果下载其他的项目有其他的lock应该优先使用哪些包管理，如果是新项目优先建议bun，但是最终需要用户决策"。否决了"钩子只保留防混用（已有别的 lockfile 时拒绝并提示对应工具）"。那样能多一道程序级拦截，但钩子的选法要和规则长期保持一致，前一轮已经证明维护成本高；混用出了问题也容易恢复。
- **不算破坏性变更**：用户确认。使用者不用改配置、不用迁移，只是少了一道拦截，按普通 feat 发版。
- **界面变化**：用户确认过原型。删掉后终端里不再出现钩子的权限确认窗和"PreToolUse:Bash hook error"拒绝提示。
- **质疑结论**：钩子和规则冲突有代码为证（拒绝时一律提示 bun，而规则要求按 lockfile 选工具），规则已经覆盖它的职责，值得做。
