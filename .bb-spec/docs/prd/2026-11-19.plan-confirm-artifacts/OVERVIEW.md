# plan 有技术变更时先确认再执行

## 背景与问题
用户用 bb-spec 做需求时，只在 PRD 上批准一次。之后 `/plan` 写完实施计划就直接运行 `/exec` 写代码，中途只在要引入新技术时停下来问。

PRD 只写需求，不写技术实现。数据库表结构、接口、配置都在 `/plan` 里定，以完整代码的形式写进 plan 文档的「成品定义」段，`/exec` 原样写进项目。程序读写的数据格式（如导出文件、消息的格式）不在「成品定义」的范围里，plan 里只有文字描述。

这些东西一上线就很难改：表结构改了要迁移老数据，接口和数据格式改了要对接方一起改。现在它们从写出来到进代码，用户一眼都没看过；新项目第一次出 plan 时，整套表和接口也是这样直接写进代码。

## 目标
- PRD 只负责对齐需求，plan 负责技术实现；plan 里的技术变更在写代码之前经用户确认。
- 用户能在一张清单里看到本次所有表、接口、数据格式、配置的新增和修改，并能直接跳到对应的完整代码。
- 没有技术变更的 plan 照旧自动跑完，不给用户增加负担。
- 对外的说明文字和实际行为一致。

## 非目标
- 不改新技术弹窗：它仍在写 plan 之前单独弹出，内容、问题、选项、流程都不动。
- 不改 `/exec` 的执行过程，也不改手动运行 `/exec` 续接的行为。
- 不给 plan 确认弹窗加"不做了"选项：不想做时由用户自己处理分支。
- 不另写展示用的文档：表、接口等完整内容只在 plan 的「成品定义」里有一份。
- 不改主页流水线图的箭头和图例。

## 整体验证路径
1. 走 `/prd` 做一个要新建表、改一个已有接口参数、新增导出文件格式的需求，PRD 通过 → `/plan` 写完后停下，简报里的技术变更清单列出这 3 项，每项带指向「成品定义」的 `文件:行号`，然后弹窗；此时 `git log` 里没有 plan 的 commit。
2. 选「需要修改」，说"status 改成枚举" → plan 被改，简报多出「本轮修改」，重新弹窗。
3. 选「已阅读，通过并执行」→ plan 被 commit，接着自动运行 `/exec`。
4. 再走一个只改函数逻辑、不动表、接口、数据格式、配置的需求 → `/plan` 写完直接 commit 并运行 `/exec`，简报里写「技术变更清单：无」，不弹窗。
5. 打开五份 README、主页、marketplace 和 plugin.json 的描述、`/prd` 弹窗选项说明 → 说法都是"PRD 批准需求；新技术先问；plan 有表、接口、数据格式、配置的新增或修改时再确认一次"。

## 决策记录
- **PRD 管需求、plan 管技术实现**：用户原话"PRD只负责需求对其，plan负责技术实现，如果有技术变更（包括项目第一次启动产生plan）都需要让用户确认"。
- **新增和修改都算技术变更**：改老表、改老接口的返工风险不比新建小。被否决：只算新增。
- **触发范围是表、接口（含参数和返回格式）、数据格式、配置四类**：这四类一上线就要迁移数据或让对接方跟着改。函数拆分写错了靠 `/revise` 改代价小，不触发。
- **新技术保留写 plan 前的单独弹窗，不并进技术变更清单**：用户先选过"合成一次"，看到原型后改为保留独立弹窗。保留的好处是否掉某项新技术时 plan 不会白写，也不动已合并的新技术审批规则。
- **完整内容留在 plan 的「成品定义」里，清单带 `文件:行号` 跳过去**：表和接口内容多，放不进弹窗。被否决：另写几份展示用的 md，因为同一段 SQL 会有两份，用户改了展示用的那份、`/exec` 照的却是 plan 里那份，会写错代码。
- **数据格式也写成完整成品**：只写一句文字描述，用户确认时等于没看。
- **清单用一行一项的列表，不用表格**：终端里中英文混排的表格列对不齐。
- **弹窗只有"通过"和"需要修改"**：到这一步 PRD 已经 commit，放弃时怎么处理由用户自己决定。
- **弹窗通过后才 commit plan**：和 `/prd` 一样，用户要改时直接改文件，不用重写 commit。
- **改动会改变 PRD 写的行为时，先改 PRD 再改 plan**：保证 PRD 和 plan 说的是同一件事，收尾的 `/doc-update` 不会报不一致。被否决：只改 plan。
- **没有技术变更时的简报也写完整路径**：两种简报一套规则。
- **修改循环的三个边界（exec 审查发现后用户在 2026-11-19 定）**：改到没有技术变更也照样简报和弹窗，因为"选通过之前不提交"要贯彻到底；改过 PRD 但还没提交时，每轮都带「PRD 改动」、选项说明都写「提交 PRD 改动和 plan」，和实际提交内容一致；修改意见要的新技术被否掉时回头问这一项改成什么，plan 不作废。被否决：改到 0 项直接提交执行、只看本轮是否改过 PRD、否掉新技术就整个停下。
- **主页去掉 /prd 节点的"唯一一次批准"小标签，DESIGN.md 跟着改**：卖点没了，改个说法留着标签只是把过期的东西换个名字。被否决：改成「批准后才继续」。
- **主页流水线箭头和图例不动**：箭头表示不用手动敲命令，确认后仍由 `/plan` 自己调用 `/exec`，说法仍成立。
- **质疑结论**：每个有技术变更的需求多一次确认、多读几段代码；换来的是最难返工的部分在写代码前有人把关，值得做。
- **不标 BREAKING CHANGE**：命令、参数、产出文件都没变，只是多一次确认。
- 原来"写完就执行、不请用户批准拆分方案"的规则来自 commit `f7b7aaa`（2026-10-16），那次没有 PRD，思路是"用户只在 PRD 上批准一次"。本次改动在保留"没有技术变更就自动跑"的前提下推翻了它的一部分。
- 本 PRD 的界面文字经原型确认（3 页：/plan 简报和弹窗、主页流水线区块、/prd 弹窗）。
