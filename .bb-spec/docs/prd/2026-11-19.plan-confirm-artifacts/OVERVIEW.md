# plan 含成品定义时先确认再执行

## 背景与问题
用户用 bb-spec 做需求时，只在 PRD 上批准一次。之后 `/plan` 写完实施计划就直接运行 `/exec` 写代码，中途只在要引入新技术时停下来问。

PRD 只写用户能看到的行为，不写表结构和接口。数据库表结构、接口格式、配置文件都在 `/plan` 里定，以完整代码的形式写进 plan 文档的「成品定义」段，`/exec` 原样写进项目。

这些东西一上线就很难改：表结构改了要迁移老数据，接口改了要对接方一起改。现在它们从写出来到进代码，用户一眼都没看过，发现不对时代码已经写完了。

## 目标
- plan 里有成品定义时，用户在写代码之前读到它，确认没问题才往下跑。
- 只有函数拆分、没有成品定义的 plan，照旧自动跑完，不给用户增加负担。
- 对外的说明文字和实际行为一致。

## 非目标
- 不改新技术弹窗：它的时机、内容、选项都不动。
- 不改 `/exec` 的执行过程，也不改手动运行 `/exec` 续接的行为。
- 不给弹窗加"不做了"选项：不想做时由用户自己处理分支。
- 不改 plan 文档的格式和成品定义的写法。

## 依赖与交付顺序
单一子需求，无依赖。

## 整体验证路径
1. 走 `/prd` 做一个要新建数据库表的需求，PRD 通过 → `/plan` 写完 plan 后停下，先列出全部 plan 文件路径并标出含成品定义的那份，再弹窗问是否通过；此时 `git log` 里还没有 plan 的 commit。
2. 选「需要修改」，说"把 status 字段改成枚举" → 改 plan 里的建表语句，重新列简报、重新弹窗。
3. 选「已阅读，通过并执行」→ plan 被 commit，接着自动运行 `/exec`。
4. 再走一个只改函数逻辑、不动表结构和接口的需求 → `/plan` 写完直接 commit 并运行 `/exec`，不弹窗。

## 决策记录
- **只在有成品定义时停，不是每次都停**：表结构、接口、配置一上线就难改，必须人看；函数拆分写错了，靠 `/revise` 改代价小。每次都停会让纯逻辑改动也多一次确认，用户选了只在有成品定义时停。
- **弹窗只有"通过"和"需要修改"两个选项**：用户选择不提供"不做了"。到这一步 PRD 已经 commit，放弃时要处理的东西由用户自己决定。
- **弹窗通过后才 commit plan**：和 `/prd` 一样，用户要改时直接改文件，不用重写 commit。
- **改动会改变 PRD 写的行为时，先改 PRD 再改 plan**：保证 PRD 和 plan 说的是同一件事，收尾的 `/doc-update` 不会报不一致。被否决的做法是只改 plan，代价是 PRD 和实际交付对不上。
- **对外说法改成"批准 PRD 一次，有表结构、接口、配置时再确认一次"**：原来的卖点是"只批准一次"，改完行为后继续这么说就和实际不符。
- **质疑结论**：用户在 PRD 之外多一次确认，代价是每个含成品定义的需求多读几份 plan；换来的是最难返工的部分在写代码前有人把关，值得做。
- **不标 BREAKING CHANGE**：命令、参数、产出文件都没变，只是多一次确认。
- 原来"写完就执行、不请用户批准拆分方案"的规则来自 commit `f7b7aaa`（2026-10-16），那次没有 PRD，思路是"用户只在 PRD 上批准一次"。本次改动在保留"纯函数改动自动跑"的前提下推翻了它的一部分。
