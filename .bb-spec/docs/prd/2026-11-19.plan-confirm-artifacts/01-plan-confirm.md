# 含成品定义的 plan 先确认

## 用户故事
### P0：作为用 bb-spec 做需求的开发者，我想要在写代码前看到 plan 定下的表结构、接口和配置，以便在它们进代码之前改掉不对的地方

**用例（主路径）**
- 场景：开发者做"订单导出"需求，PRD 已经批准，`/plan` 决定新建一张 `export_task` 表。
- 操作：`/plan` 写完 plan 并自检后，开发者读简报里标出的那份含成品定义的 plan，在弹窗里选「已阅读，通过并执行」。
- 预期：弹窗之前 plan 没有 commit；选通过后 plan 被 commit，`/exec` 自动开始。

**用例（需要修改）**
- 场景：同上，开发者读完觉得 `status` 字段应该用枚举。
- 操作：在弹窗里选「需要修改」，说"status 改成枚举"。
- 预期：plan 里的建表语句改好，重新自检、重新列简报、重新弹窗；没有 commit，`/exec` 没有开始。

**用例（改动牵涉 PRD 行为）**
- 场景：开发者读完接口定义后说"导出结果不要返回文件大小"，而 PRD 写着用户能看到文件大小。
- 操作：在弹窗里选「需要修改」写这条意见。
- 预期：先改本分支 PRD 里对应的约束和验收，再改 plan，然后重新简报、重新弹窗；简报里写明 PRD 改了哪几条。

**用例（没有成品定义）**
- 场景：开发者做的需求只改一个函数的判断逻辑，plan 里没有成品定义段。
- 操作：`/plan` 写完 plan。
- 预期：和现在一样，直接 commit plan 并运行 `/exec`，不弹窗。

## 约束
1. `/plan` 写完 plan 并通过自检后，本次主题目录下任一份 plan 含「成品定义」段 → 不 commit plan、不运行 `/exec`，先输出简报再弹窗。
2. 本次所有 plan 都没有「成品定义」段 → 不弹窗，commit plan 后直接运行 `/exec`。
3. 简报列出本次主题目录下每份 plan 文件的完整路径；含成品定义的那几份单独标出，每份写一句它定了什么（例如"新建 `export_task` 表"、"新增 `POST /exports` 接口"、"新增 `export.yaml` 配置"）。
4. 弹窗只有两个选项，顺序为「已阅读，通过并执行」（标推荐）、「需要修改」。
5. 选「已阅读，通过并执行」→ commit plan，然后运行 `/exec`。
6. 选「需要修改」，或在「其他」里直接写意见 → 问清要改什么，就地改 plan 文件，重新自检，再重新简报、重新弹窗；在用户选通过之前不 commit plan、不运行 `/exec`。
7. 用户要改的内容会改变本分支 PRD 写的行为 → 先改本分支 PRD 对应的约束和验收，再改 plan；简报写明 PRD 改了哪几条；commit 时 PRD 的改动和 plan 一起提交。
8. 新技术弹窗的时机和规则不变：它仍在写 plan 文档之前弹，和本弹窗各自独立。
9. 手动运行 `/plan` 和由 `/prd` 自动运行 `/plan` 遵守同样的规则。
10. 对外说明和行为一致：五份 README、介绍主页、marketplace 插件描述、`/prd` 弹窗里「已阅读，通过并执行」的选项说明，都写成"读完 PRD 批准一次；plan 里有表结构、接口、配置时再确认一次，其余自动跑完"；全仓搜"只批准一次""只有要引入新技术时才停下"这类说法无命中。

## 验收
- [ ] 含成品定义时，简报和弹窗出现在 commit 和 `/exec` 之前（约束 1）。
- [ ] 没有成品定义时不弹窗，直接 commit 并运行 `/exec`（约束 2）。
- [ ] 简报列出全部 plan 文件完整路径，含成品定义的单独标出并各写一句定了什么（约束 3）。
- [ ] 弹窗恰好两个选项，顺序和推荐标记正确（约束 4）。
- [ ] 选通过后 plan 被 commit，`/exec` 开始（约束 5）。
- [ ] 选需要修改或写意见后，改文件、重新自检、重新简报和弹窗，期间没有 commit（约束 6）。
- [ ] 改动牵涉 PRD 行为时先改 PRD 再改 plan，简报写明 PRD 改动，PRD 和 plan 一起 commit（约束 7）。
- [ ] 新技术弹窗仍在写 plan 之前，规则未变（约束 8）。
- [ ] 手动 `/plan` 行为相同（约束 9）。
- [ ] 五份 README、介绍主页、marketplace 描述、`/prd` 弹窗选项说明的措辞一致，搜不到"只批准一次""只有要引入新技术时才停下"一类旧说法（约束 10）。

## 验证路径
1. 准备一个本分支有新 PRD、需要建表的测试项目，运行 `/plan` → 看到简报列出全部 plan 路径并标出含建表语句的那份，弹窗两个选项；`git log` 里没有 plan 的 commit。
2. 选「需要修改」并写意见 → plan 被改，重新出简报和弹窗，仍无 commit。
3. 写一条会改变 PRD 行为的意见 → PRD 对应条目先改，简报写明改动。
4. 选「已阅读，通过并执行」→ PRD 改动和 plan 一起 commit，`/exec` 启动。
5. 换一个只改函数逻辑的需求运行 `/plan` → 不弹窗，直接 commit 并启动 `/exec`。
6. 在仓库里搜"只批准一次""只有要引入新技术时才停下"等旧说法 → 无命中。
