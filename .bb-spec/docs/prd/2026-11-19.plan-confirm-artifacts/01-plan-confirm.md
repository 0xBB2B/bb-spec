# 技术变更先确认

## 用户故事
### P0：作为用 bb-spec 做需求的开发者，我想要在写代码前看到 plan 定下的表、接口、数据格式和配置，以便在它们进代码之前改掉不对的地方

**用例（主路径）**
- 场景：开发者做"订单导出"需求，PRD 已经批准，`/plan` 写了 3 份 plan：新建 `export_task` 表、新增 `POST /exports` 接口、把 `GET /orders` 的 `date` 参数拆成 `date_from` 和 `date_to`、新增导出的 CSV 文件格式。
- 操作：`/plan` 写完 plan 并自检后，开发者按简报里每项的 `文件:行号` 打开 plan 读成品定义，在弹窗里选「已阅读，通过并执行」。
- 预期：弹窗之前 plan 没有 commit；简报的技术变更清单是 4 项；选通过后看到「✓ 已 commit plan：…」，然后 `/exec` 自动开始。

**用例（新项目第一次出 plan）**
- 场景：一个空项目第一次出 plan，有 `config.yaml` 配置、`orders` 表、`POST /orders` 和 `GET /orders` 两个接口。
- 操作：`/plan` 写完 plan。
- 预期：清单 4 项全标「新增」，后面是同样的弹窗。

**用例（需要修改）**
- 场景：同主路径，开发者读完觉得 `status` 字段应该用枚举。
- 操作：在弹窗里选「需要修改」，回答"export_task 的 status 改成枚举"。
- 预期：plan 里的建表语句改好，看到一句改了什么和「自检通过。」，再看到完整简报，清单后多一条「本轮修改：」，然后重新弹窗；没有 commit，`/exec` 没有开始。

**用例（改动牵涉 PRD 行为）**
- 场景：开发者读完接口定义后说"POST /exports 不要返回文件大小"，而 PRD 写着用户能看到文件大小。
- 操作：在弹窗里选「需要修改」写这条意见。
- 预期：看到说明「PRD 写着用户能看到文件大小，这条意见会改变 PRD 写的行为，所以先改 PRD、再改 plan。」；先改本分支 PRD 对应的约束和验收，再改 plan；简报多一条「PRD 改动：<PRD 文件完整路径>」，逐条写「约束 N：旧 → 新」；弹窗选项 1 的说明开头是「提交 PRD 改动和 plan」；选通过后 PRD 改动和 plan 在同一个 commit 里。

**用例（没有技术变更）**
- 场景：需求只改一个函数的判断逻辑，plan 不新增也不修改任何表、接口、数据格式、配置。
- 操作：`/plan` 写完 plan。
- 预期：不弹窗；看到「✓ 已 commit plan：…」，简报里文件清单写完整路径，有一行「技术变更清单：无」，然后自动运行 `/exec`。

## 约束
1. **技术变更**指 plan 新增或修改以下四类东西之一：表（表结构及其迁移）、接口（含路径、参数和返回格式）、数据格式（程序读写的文件格式、消息格式等）、配置（配置文件和配置项）。只改函数逻辑不算。
2. plan 里的每项技术变更都在那份 plan 的「成品定义」段里写出完整内容；数据格式和表、接口、配置一样写完整成品，不能只写文字描述。
3. `/plan` 写完 plan 并通过自检后，本次有任一项技术变更 → 不 commit plan、不运行 `/exec`，先输出简报再弹窗。
4. 本次没有任何技术变更 → 不弹窗：先 commit plan，再输出简报（含一行「技术变更清单：无」，「下一步：自动运行 /exec <主题>」），然后运行 `/exec`。
5. 两种简报的文件清单都列出本次主题目录下每份 plan 的完整路径和一句话描述。
6. 有技术变更时，简报在文件清单之后有「技术变更清单（N 项，/exec 会照成品定义原样写进项目）：」，一行一项、不画成表格，每项两行：
   - 第一行「序号. [类别] 名字 — 新增」或「序号. [类别] 名字 — 修改：<改了什么>」，类别只有表、接口、数据格式、配置四种；
   - 第二行是那份 plan 的完整路径加行号，指向「成品定义」里对应的代码块。
7. 有技术变更时，简报最后一行是「下一步：请按上面 N 项的 文件:行号 打开 plan 阅读成品定义，在弹窗里确认」。
8. 弹窗标题「技术变更」，问题「我已阅读上面技术变更清单（N 项）指向的成品定义，plan 通过并开始执行吗？」，只有两个选项，顺序为：
   - 「已阅读，通过并执行」（标推荐），说明「提交 plan，然后自动跑 /exec → /doc-update；表、接口、数据格式、配置照 plan 里的成品定义原样写进项目」；
   - 「需要修改」，说明「告诉我哪一项要改，改完重新自检、重新列清单、重新弹窗确认」。
9. 选「已阅读，通过并执行」→ commit plan，看到「✓ 已 commit plan：<commit 号和标题>」，然后运行 `/exec`。
10. 选「需要修改」，或在「其他」里直接写意见 → 问清哪一项要改，就地改 plan，重新自检，重新简报（清单后多一条「本轮修改：」，每行「第 N 项 名字 — 改了什么」）、重新弹窗；用户选通过之前不 commit plan、不运行 `/exec`。
11. 用户要改的内容会改变本分支 PRD 写的行为 → 先说明原因，再改本分支 PRD 对应的约束和验收，然后改 plan；简报再多一条「PRD 改动：<PRD 文件完整路径>」，逐条写「约束 N：旧 → 新」「验收 N：旧 → 新」；弹窗选项 1 的说明开头换成「提交 PRD 改动和 plan」；选通过后 PRD 改动和 plan 放在同一个 commit，看到「✓ 已 commit PRD 改动和 plan（同一个 commit）：…」。
12. 新技术弹窗的时机和规则不变：仍在写 plan 之前单独弹出；技术变更清单不列新技术。
13. 手动运行 `/plan` 和由 `/prd` 自动运行 `/plan` 遵守同样的规则。

## 验收
- [ ] 技术变更的判定覆盖表、接口、数据格式、配置的新增和修改，只改函数逻辑不触发（约束 1）。
- [ ] 数据格式类技术变更在「成品定义」里有完整内容（约束 2）。
- [ ] 有技术变更时，简报和弹窗出现在 commit 和 `/exec` 之前（约束 3）。
- [ ] 没有技术变更时不弹窗，先 commit，简报含「技术变更清单：无」，然后运行 `/exec`（约束 4）。
- [ ] 两种简报的文件清单都是完整路径加一句话描述（约束 5）。
- [ ] 技术变更清单标题、每项两行的格式、四种类别、`文件:行号` 指向成品定义代码块，都和约束 6 一致。
- [ ] 「下一步」一行文字和约束 7 一致。
- [ ] 弹窗标题、问题、两个选项的名字、顺序、推荐标记和说明和约束 8 一致。
- [ ] 选通过后 commit plan 并运行 `/exec`（约束 9）。
- [ ] 选需要修改或写意见后，改文件、重新自检、简报多「本轮修改」、重新弹窗，期间没有 commit（约束 10）。
- [ ] 改动牵涉 PRD 时先说明、先改 PRD 再改 plan，简报有「PRD 改动」，选项 1 说明开头换字，PRD 和 plan 同一个 commit（约束 11）。
- [ ] 新技术弹窗仍在写 plan 之前，清单里没有新技术（约束 12）。
- [ ] 手动 `/plan` 行为相同（约束 13）。

## 验证路径
1. 准备一个本分支有新 PRD、需要建表、改接口参数、新增导出文件格式的测试项目，运行 `/plan` → 简报的技术变更清单 3 项以上，每项第二行的 `文件:行号` 打开后正好是成品定义里的代码块；弹窗两个选项；`git log` 里没有 plan 的 commit。
2. 选「需要修改」并写意见 → plan 被改，简报多「本轮修改」，重新弹窗，仍无 commit。
3. 写一条会改变 PRD 行为的意见 → 先看到原因说明，PRD 对应条目先改，简报有「PRD 改动」，选项 1 说明以「提交 PRD 改动和 plan」开头。
4. 选「已阅读，通过并执行」→ PRD 改动和 plan 在同一个 commit，`/exec` 启动。
5. 换一个只改函数逻辑的需求运行 `/plan` → 不弹窗，先 commit，简报写「技术变更清单：无」，然后启动 `/exec`。
6. 在需要新技术的需求上运行 `/plan` → 写 plan 前照旧弹出新技术弹窗；之后的技术变更清单里没有新技术。
