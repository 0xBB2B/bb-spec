# 流程规则

下文的"外壳"指随插件发布的统一原型外框；"框"指外壳中间显示正式页面的区域。

## 用户故事

### P0：作为用插件做需求的用户，我想要每份原型都是同一种排版，以便不用每次重新适应

**用例（主路径）**
- 场景：用户用 `/prd` 提了一个改界面的需求。
- 操作：`/prd` 在澄清阶段出原型。
- 预期：原型用外壳做成，框里只有正式页面，说明和切换都在框外。

**用例（主路径）**
- 场景：用户用 `/revise` 修一个会改变界面的 bug。
- 操作：`/revise` 在改代码前出原型。
- 预期：原型同样用外壳做成，排版和 `/prd` 出的一样。

### P0：作为选方案的用户，我想要选定后原型里只留一个方案，以便后面的对比只有一个标准

**用例（主路径）**
- 场景：原型有方案 A、方案 B，用户选了方案 B。
- 操作：用户说选方案 B。
- 预期：AI 把方案 A 从原型里删掉，只留方案 B，再请用户确认。

### P0：作为验收实现的用户，我想要界面对比只比正式页面，以便不被说明文字干扰

**用例（主路径）**
- 场景：`/exec` 收尾时拿实际界面和原型对比。
- 操作：逐项对比。
- 预期：只比框里的布局、文案、状态和交互结果，外壳的文字不算作实际界面缺失的内容。

**用例（边界：原型里的假数据）**
- 场景：原型的「只在原型里成立」写着订单是假数据，实际界面显示的是真实订单。
- 操作：对比。
- 预期：订单内容不同不算不一致。

## 约束

- C1：`/prd` 的界面预览 → 必须用外壳出原型，并且只往外壳里填内容，不改外壳本身。
- C2：`/revise` 的界面预览 → 必须用外壳出原型，并且只往外壳里填内容，不改外壳本身。
- C3：`/prd`、`/revise` 的界面预览 → 正式页面只放进框里，说明写进底部三列，切换写进左栏；框里不放任何说明或切换用的控件。
- C4：同一次设计有多个方案时 → 放进同一份原型里切换，不拆成多个文件。
- C5：用户选定方案后 → 把没选中的方案从原型里删掉，再请用户确认。
- C6：`/exec` 收尾和 `/revise` 回归验证的界面对比 → 只比框里的内容，外壳的左栏、框上方提示、底部说明都不参与对比。
- C7：界面对比时 → 「只在原型里成立」里写明的假数据和假操作，与实际界面不同不算不一致。
- C8：`/prd` 把确认过的原型写进约束和验收时 → 只写框里的内容，外壳不写成产品功能；`/revise` 把确认过的界面作为期望行为时同样如此。

## 验收

- [ ] C1：`/prd` 的「界面预览」写明用外壳出原型、只填内容不改外壳。
- [ ] C2：`/revise` 的「界面预览」写明用外壳出原型、只填内容不改外壳。
- [ ] C3：`/prd`、`/revise` 的「界面预览」都写明三类内容各放哪里，并禁止在框里放说明或切换控件。
- [ ] C4：`/prd`、`/revise` 的「界面预览」都写明多个方案放同一份原型。
- [ ] C5：`/prd`、`/revise` 的「界面预览」都写明选定方案后删掉没选中的方案，再请用户确认。
- [ ] C6：`/exec`、`/revise` 的「界面对比」都写明只比框里的内容。
- [ ] C7：`/exec`、`/revise` 的「界面对比」都写明假数据和假操作不算不一致。
- [ ] C8：`/prd` 步骤 4 和 `/revise` 的期望行为说明都写明只取框里的内容。

## 验证路径

1. 读 `/prd` 和 `/revise` 的「界面预览」 → 都要求用外壳，并写清内容放哪、多方案怎么处理。
2. 读 `/exec` 和 `/revise` 的「界面对比」 → 都写明只比框里的内容，假数据不算不一致。
3. 运行 `tests/validate.sh` → 全部通过，外壳文件随插件一起被检查到。
