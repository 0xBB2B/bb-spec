# 原型交给子代理做，设计规范用展示页确认

"原型"是改界面前给用户确认用的单文件 HTML 页面。"主对话"是用户直接对话的那个 Claude。"子代理"是主对话派出去单独干活的另一个 Claude：它看不到主对话的内容，只拿到派工时给它的那段话，干完交回一份报告。"DESIGN.md"是放在用户项目根目录的设计规范文档。"外壳"是所有原型共用的 HTML 外框，"框"是外壳中间显示正式页面的区域。

## 背景与问题

现在出原型的全过程都在主对话里做：读 DESIGN.md、读项目源码、写 HTML、按用户意见一轮轮改。用户遇到两个问题：

- 原型常常要改好几轮。用户说"可以"之后，读过的源码、改过的 HTML 对后面写 PRD、出计划、执行都没用了，却一直留在主对话里，挤掉后面能用的空间。实测 2026-11-05 至 2026-11-11 两个项目的 6 个对话、7 次出原型：每次出原型让主对话多出 4.9 万到 24.6 万 token，中位数 6.7 万；7 次里有 4 次改了 2 到 5 轮。3 次界面对比各多出 1.3 万到 3.4 万以上。
- 项目没有 DESIGN.md 或者要改 DESIGN.md 时，现在是把规范草稿的 Markdown 全文贴在对话里请用户确认。用户不想读 Markdown，只想看到颜色用哪些、按钮长什么样、悬停和点击时什么样。

## 目标

- 出原型和界面对比的过程留在子代理里，主对话只留下派工说明、子代理每轮的简短报告、用户的意见。
- 用户照旧能一轮轮提意见，改到明确说"可以"为止。
- 新建或修改 DESIGN.md 时，用户看一个画出来的展示页就能确认，不需要读规范全文。
- `/prd`、`/revise`、`/exec` 调用 `/prototype` 的方式和参数保持原样。

## 非目标

- 不改外壳。展示页是框里的一种页面。
- 不改 `/exec` 里写测试、写实现、审查三个子代理的做法，也不处理 `/exec` 阶段主对话变长的问题。
- 展示页不画 DESIGN.md 的「布局与断点」和「无障碍」两节：页面框架在正式页面的原型里能看到，对比度写在每个色块下面。
- 不提供"小改动由主对话自己出原型"的快捷做法，改动再小也派子代理。
- 不处理 Claude Code 自己发的子代理完成通知占用的空间，这部分插件管不了。
- 已经生成在缓存目录里的旧原型文件不迁移。

## 依赖与交付顺序

01 → 02。展示页由原型子代理来画，所以先有子代理。

## 整体验证路径

1. 在一个有界面代码、没有 DESIGN.md 的项目里运行 `/prototype <主题>` → 主对话派出原型子代理，自己不读项目源码、不写原型文件。
2. 浏览器打开原型，左栏有「设计规范」一页，画着颜色、字号、间距、圆角、组件各状态和动效；有不达标项时并排画着现状和建议。对话里没有贴 DESIGN.md 全文。
3. 用户说"可以" → DESIGN.md 写入项目根目录，「设计规范」一页从原型里消失，左栏换成要设计的页面。
4. 用户对要设计的页面提一条修改意见 → 主对话把这句原话发给同一个子代理，子代理改完交回简短报告，主对话原样转给用户。
5. 用户说"可以" → 子代理交回一份确认内容清单，`/prototype` 结束并告诉用户原型文件路径。
6. 实现完成后运行 `/prototype --compare <原型文件路径>` → 主对话派子代理对比，返回"一致""不一致""没跑起来"三种结果之一。

## 决策记录

- **为什么交给子代理**：上面的实测数据说明出原型的过程占主对话 4.9 万到 24.6 万 token，确认后这些内容没有用处。交给子代理后这些内容从头就不进主对话。
- **被否决：出原型留在主对话，PRD 确认后清空上下文再继续**。清空只能由用户手动敲命令，"批准一次后自动跑到底"会断成两段；而且是先占用再清理，没有解决占用本身。用户想用时仍可以自己手动清空。
- **为什么所有问题都由主对话问用户**：Claude Code 官方文档（code.claude.com/docs/en/sub-agents）写明所有子代理都没有向用户提问的工具。所以子代理只把要确认的事写进报告，由主对话问。
- **为什么能一轮轮改**：同一份文档写明，主对话可以用 SendMessage 工具给跑完一轮的子代理发消息，子代理保留之前全部上下文。这只在同一个会话里有效，所以规定了发不出去时新派一个子代理、让它读已有原型文件接着改。
- **子代理的模型写 fable**：用户指定。官方文档列出的子代理模型取值里有 `fable`。使用者账号用不了这个模型时会怎样，文档没有写，没有验证；所以规定派不出去时把报错原文告诉用户，由用户决定。
- **确认内容用文字清单交回，不让主对话读最终原型文件**：用户选定。清单比整份 HTML 短得多。代价是清单漏写的内容 PRD 也会漏，要到实现后做界面对比时才会发现；界面对比直接拿原型文件比，不依赖清单。
- **改动再小也派子代理**：用户选定。规则只有一条，不用定"多小算小"的界线。代价是小改动也要等子代理从头读一遍 DESIGN.md。
- **设计规范用展示页确认**：用户提出。用户不读 Markdown 全文，只看画出来的样子。原有的"风格样张"（全新项目选风格时每套风格画一页）并入展示页，做法统一。
- **展示页放进同一份原型、确认后删掉**：用户选定。只开一个文件；删掉是因为界面对比只比正式页面。被否决的是单独一个 HTML 文件，每次要开两个文件。
- **新建和修改 DESIGN.md 都出展示页**：用户选定。被否决的是只在新建时出、修改时仍用文字列。
- **有不达标项时按建议值画、并排标出现状**：用户选定。被否决的是按现状画、问题只在对话里列，那样用户看不到改好后的样子。
- **标记样式固定，不跟项目配色走**：橙色虚线框表示不达标，紫色虚线框表示本次修改。这样不管项目用什么配色，标记都认得出来。用户已在预览里确认。
- **对比另派一个新子代理，不复用出原型的那个**：对比通常发生在实现完成之后，多数情况下已经不在出原型的那个会话里；新派的子代理没看过出原型的过程，只拿原型文件和实际界面比。
- **临时文件统一用 `<日期>.<主题>` 开头**：用户提出。原型、设计规范草稿、待写入的设计规范、对比截图目录都用同一个名字开头，和 PRD 目录同名。`/revise` 的原型原来叫 `revise-<日期>-<主题>.html`，改成 `<日期>.revise-<主题>.html`：格式和别的一致，也不会和同一天同主题的 `/prd` 原型重名。
- **`.DESIGN.draft.md` 只表示用户还没同意**：用户提出。以前没同意的内容只贴在对话里，这个文件装的是"已同意、等 `/prd` 写 PRD 时再写进项目"的内容；这次没同意的内容也要存文件，两种内容不能共用一个名字。已同意待写入的改叫 `<日期>.<主题>.DESIGN.md`。被否决的是"`/prd` 里也同意就立刻写进项目"：那时可能还在 main 分支上，用户在 PRD 确认弹窗选"不做了"时也没人撤销它。
- **不标 BREAKING CHANGE**：用户选定。`/prd`、`/revise`、`/exec` 调用 `/prototype` 的方式和参数都不变。
