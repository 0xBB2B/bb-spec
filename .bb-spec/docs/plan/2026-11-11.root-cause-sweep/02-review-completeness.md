# 审查附带同类位置，测试缺口当轮补

## 目标
审查每指出一个问题同时给出别处的同类位置；审查指出的测试缺口在当轮补上，补不了就停下问用户。

## 业务规则（来源：PRD 02-review-completeness）
- 要附同类位置的问题：审查子代理指出的"实现不符合期望行为"的问题、鲁棒性和安全问题。代码纪律问题和设计规范对照的问题不附。
- 同类位置怎么找：在变更文件之外搜整个仓库，找两类：调用了出问题那段代码、会受同一缺陷影响的位置；别处独立写的同样错误写法。
- 报告写法：每条要附的问题下面多一行"同类位置"，逐个列 `文件:行号` 和一句理由；没有时写"同类位置：已搜，无"。
- 审查子代理仍然只读，只列出不改。
- `/exec`、`/revise` 拿到报告后逐个读代码核实同类位置：成立的和问题本身同一轮修完，每个位置至少一条测试；不成立的在完成简报写明位置和理由。
- 审查指出的每条测试缺口（"实现合规但没有测试覆盖"和报告"遗漏"一节的条目）都在本轮派测试子代理补上，补完交审查子代理复查。
- 补出来的测试直接通过算补完；失败按"实现不符合期望行为"在本轮改实现直到通过。
- 写不出能自动跑的测试时（如要依赖真实的外部服务，或要搭的环境超出这次改动范围）停下说明卡在哪，弹一次窗：问题"这 N 条测试缺口当轮补不了，怎么办？"，预设选项依次是"不补"（说明：简报里记下没补和原因）、"换个办法补"（说明：你告诉我用什么办法测）。
- 用户选"不补"：完成简报"待解决"写明哪一条、补不了的原因、用户在哪天定的。除此之外"待解决"里不出现测试缺口。
- `/git-push` 分支自查指出"有实现但没有测试"时，和违规项一起交 `/revise` 在推送前补上，处理方式相同。
- 决策理由：实际经过里审查当场发现 3 处同类问题却被记成范围外；一条测试缺口留到事后单独开了一个 PR。
