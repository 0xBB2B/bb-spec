# 无关发现收尾清单

## 目标
干活时碰到的无关发现先记下不动手，收尾时合成一张清单、弹一次窗；选中的在当前分支修完，进同一个 PR。

## 业务规则（来源：PRD 03-unrelated-findings）
- 无关发现：干活过程中碰到的、和这次要解决的问题不是同一个根因的问题。来源包括 Claude 自己读代码看到的、子代理报告里提到的、审查报告备注里提到的。同根因位置不算。
- 发现时 Claude 和子代理都只记不改。
- 每条写编号、位置（`文件:行号`）、一句话问题、不处理的后果、估计用时；没验证的推测标"未验证"并写怎么验证。
- 清单分两段：能在当前分支修的（修代码错误、清过期内容、改不准的文档）；要另开需求的（要新增功能，或要改变已有功能的行为）。
- 在哪问：`/exec` 收尾、`/revise` 收尾各一次，在完成简报之后；`/git-push` 在推送之前一次。同一个会话里问过的条目不再问。
- 怎么问："能在当前分支修的"不为空时弹一次窗，问题"上面 N 条无关发现，处理哪些？"，预设选项依次是"全部处理"（说明：在当前分支修完，进同一个 PR）、"都不处理"（说明：留在简报的待解决里）；在"其他"里填编号（如 `1,3`）只选几条。
- 两段都为空：简报写"无关发现：无"，不弹窗。只有"要另开需求的"有内容：也不弹窗。
- 选中的一次全部交 `/revise`，在当前分支修完并本地提交，不新开分支。没选中的带位置留在"待解决"。要另开需求的写进"待解决"，标明要走 `/prd`。
- `/git-push` 推送前选了处理：修完、重跑全量测试通过后再推送。
- 被 `/exec` 或 `/git-push` 调用的 `/revise` 自己不弹窗，把记下的无关发现交回调用环节一起问。
- 修无关发现时又发现新的：这一轮修完后再问一次，只问新的。
- PR 合并之后才发现的：同样合成一张清单一次问；选中的放进同一个新分支、同一个 PR。
- 决策理由：实际经过里无关发现一件一件零散地问，合并后剩的两件小事和一条测试各自单独开了 PR。
