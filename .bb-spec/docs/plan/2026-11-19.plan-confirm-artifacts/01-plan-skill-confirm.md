# /plan 有技术变更先确认

## 目标
`/plan` 写完 plan 后判定技术变更：有就列技术变更清单并弹窗，用户通过后才 commit 并运行 `/exec`；没有就直接 commit 并运行 `/exec`。「成品定义」的范围加上数据格式。

## 业务规则（来源：PRD plan-confirm）
- 技术变更 = plan 新增或修改表（表结构及其迁移）、接口（路径、参数和返回格式）、数据格式（程序读写的文件格式、消息格式等）、配置（配置文件和配置项）之一；只改函数逻辑不算；新技术不算（另走写 plan 前的新技术弹窗，时机和规则不变）。
- 每项技术变更都在那份 plan 的「成品定义」里写完整内容；数据格式也写完整成品。
- 有技术变更 → 不 commit、不运行 `/exec`，先简报再弹窗；没有 → 先 commit，再简报（含「技术变更清单：无」），再运行 `/exec`。
- 两种简报的文件清单都写每份 plan 的完整路径加一句话描述。
- 技术变更清单一行一项、每项两行：「序号. [类别] 名字 — 新增」或「— 修改：<改了什么>」；第二行是完整路径加行号，指向成品定义里对应代码块。
- 弹窗标题「技术变更」，两个选项「已阅读，通过并执行」（推荐）、「需要修改」；「其他」里写意见按需要修改处理。
- 需要修改：改 plan、重新自检、重新简报（多「本轮修改：」）、重新弹窗；改动会改变本分支 PRD 写的行为时先说明原因、先改 PRD 再改 plan，简报多「PRD 改动：」，选项 1 说明开头换成「提交 PRD 改动和 plan」，通过后 PRD 改动和 plan 同一个 commit。
- 手动运行 `/plan` 和由 `/prd` 自动运行遵守同样的规则。

### 步骤 7：判定技术变更

**技术变更**指 plan 新增或修改以下四类东西之一：

- 表：表结构及其迁移
- 接口：路径、参数和返回格式
- 数据格式：程序读写的文件格式、消息格式等
- 配置：配置文件和配置项

只改函数逻辑不算。新技术已在步骤 3 单独确认，不算技术变更。按这四类逐份判断 plan 改了什么，不按 plan 有没有「成品定义」段判断：成品定义里放的其他内容（如规程文本）不算技术变更。

每项技术变更记下：类别（表、接口、数据格式、配置之一）、名字、新增还是修改（修改写一句改了什么）、所在 plan 的完整路径和行号。行号在 plan 定稿后用 `grep -n` 取，指向「成品定义」里对应代码块的第一行；每轮修改后重新取。

- 没有技术变更 → 跳过步骤 8，进步骤 9
- 有技术变更 → 进步骤 8

### 步骤 8：技术变更清单 + 弹窗确认

这一步不 commit plan、不运行 `/exec`。先输出简报：

```
## Plan 完成简报
- 主题：<YYYY-MM-DD.主题>
- 产出：N 份 plan，分 M 个阶段
- 文件清单：
  - <每份 plan 的完整路径> — <一句话描述>
- 技术变更清单（N 项，/exec 会照成品定义原样写进项目）：
  1. [<类别>] <名字> — 新增
     <那份 plan 的完整路径>:<行号>
  2. [<类别>] <名字> — 修改：<改了什么>
     <那份 plan 的完整路径>:<行号>
- PRD 覆盖：<全部约束与验收已覆盖 / 未覆盖项列表>
- 待解决：<问题列表 / 无>
- 下一步：请按上面 N 项的 文件:行号 打开 plan 阅读成品定义，在弹窗里确认
```

技术变更清单一行一项，不画成表格：终端里中英文混排的表格列对不齐。

接着调用 AskUserQuestion，header 写「技术变更」，问题写「我已阅读上面技术变更清单（N 项）指向的成品定义，plan 通过并开始执行吗？」，只有两个选项，按下面的顺序：

| 选项 | 选项说明 | 选了之后 |
|---|---|---|
| 已阅读，通过并执行（标推荐） | 提交 plan，然后自动跑 /exec → /doc-update；表、接口、数据格式、配置照 plan 里的成品定义原样写进项目 | 进步骤 9 |
| 需要修改 | 告诉我哪一项要改，改完重新自检、重新列清单、重新弹窗确认 | 按下面「需要修改」处理 |

用户在「其他」里直接写意见时，按「需要修改」处理。本轮改过 PRD 时，选项 1 的说明开头换成「提交 PRD 改动和 plan」，其余不变。

**需要修改**：

1. 在正文问「哪一项要改？」，问清用户要改什么；用户已经写了意见就直接用
2. 意见会改变本分支 PRD 写的行为（PRD 的约束、验收、用户故事里写着的、用户能看到的行为）→ 先在正文说一句原因，格式为「PRD 写着<原行为>，这条意见会改变 PRD 写的行为，所以先改 PRD、再改 plan。」，然后改本分支 PRD 对应的约束和验收，再改 plan；不会改变 PRD 写的行为 → 只改 plan
3. 意见要改用项目里没有的新技术 → 先按步骤 3 列新技术清单、单独弹窗批准，再改 plan
4. 改完重跑步骤 6 自检和步骤 7 判定，在正文写一句改了什么，结尾写「自检通过。」；改过 PRD 时写「已改 PRD X 条、plan Y 份。自检通过。」
5. 改完后仍有技术变更 → 重新输出简报、重新弹窗。简报在技术变更清单后面多一条「本轮修改：」，下面每行写「第 N 项 <名字> — <改了什么>」；本轮改过 PRD 时再多一条「PRD 改动：<PRD 文件完整路径>」，下面逐条写「约束 N：<旧> → <新>」「验收 N：<旧> → <新>」
6. 改完后没有技术变更了 → 进步骤 9

用户选「已阅读，通过并执行」之前，不 commit plan、不运行 `/exec`。

### 步骤 9：本地 commit + 自动执行

先 `git branch --show-current` 确认分支（**在 main 上则跳过自动 commit**，提示按 git-workflow 先建分支）；只提交本次涉及文件（主题目录内的 plan 文档 + 主题 INDEX + PROGRESS；步骤 8 改过本分支 PRD 时，PRD 的改动放进同一个 commit）；message 遵循仓库历史风格（先 `git log --oneline -10`），不硬编码类型前缀，带 `Requirement: <本次 PRD 目录名>`（单独一行写在 commit 说明末尾）；多仓库时 plan 提交在文档仓库；**仅本地不自动 push**。

commit 后在正文写一行：

- 只提交了 plan → 「✓ 已 commit plan：<commit 号> <标题>」
- PRD 改动和 plan 一起提交 → 「✓ 已 commit PRD 改动和 plan（同一个 commit）：<commit 号> <标题>」

从步骤 7 直接来（没有技术变更）时，接着输出简报：
